兼容依据是已发布的数据契约和行为语义，不是应用大版本号、Rust结构体布局、枚举顺序、模块路径或第三方库版本。重构不得自动成为破坏旧数据的理由。

| 数据 | 保存范围与归属 | 更新时的要求 |
| --- | --- | --- |
| 可编辑项目 | 原始Asset、文档／图层／组件、独立音效、配置、输出映射 | 保留身份、原字节、编辑语义与未知内容；不只保存当前导出文件 |
| 完整历史 | 根、全部分支／节点及其状态、关系、手动／保护检查点各自的头与导航、提交事实 | 保存捕获时的整棵树，不只保留当前头的祖先；重开按明确策略激活后继续Undo／Redo／检出 |
| 可迁移用户偏好 | 语言、主题、稳定动作ID对应的快捷键、自定义展示资料等 | 独立版本化，保留用户显式选择和未知可保留项；不进入皮肤项目／项目历史 |
| 本机设置 | stable／Songs／默认皮肤路径、设备选择、显示器绑定等 | 不随项目传播；换机器允许重新绑定，不要求旧设备／路径仍有效 |
| 工作区恢复状态 | 面板、视口、打开位置等 | 独立轻量格式；目标失效可回到安全布局，不能损坏项目或丢弃分支 |
| 崩溃恢复／备份 | 已提交内容与历史的恢复快照、来源保存代次 | 可校验、可选择恢复；不能把未提交草稿或取消声音重新激活 |
| 派生缓存 | 缩略图、RGBA、PCM、GPU／着色器缓存、重建索引 | 可清空重建，不是用户原始数据的唯一副本；缓存不兼容不能删项目 |
| 凭据与运行状态 | 认证秘密、请求回执、Voice、GPU句柄、设备／任务代次等 | 不进项目；秘密使用独立受限存储，运行时身份不从旧文件复活 |

“历史持久化”不等于历史能无限增长，也不等于同时打开多个可写分支视图。首版仍不包含协同编辑或分支合并；历史删除／覆盖／裁剪则是长期禁止的行为，不能作为用户高级选项。容量不足须提前诊断／停止新增，保留已提交记录及资源，不能删旧分支以完成保存。

### 1.1 不可变历史与可变标签

| 部分 | 允许的变化 | 必须保持 |
| --- | --- | --- |
| 已提交节点本体 | 追加新节点，不替换旧节点 | 稳定身份、直接父关系、原始操作及对应内容状态；所有分支和恢复依赖 |
| 节点标签 | 独立添加／移除／更新标签元数据 | 节点本体、地址及过去的图像／声音／配置状态不变 |
| 导航／保存保护元数据 | 切换活动头、移动合法保存／保护指针、更新有效Redo偏好 | 先前节点仍存在且可查询／恢复，不因指针移开而成为可删除数据 |
| 派生索引／物理承载 | 重建索引、去重、搬移或无损重编码 | 逻辑历史和原始资源完整；不能通过漏索引节点实现变相删除 |

用户删除当前图层、移除库条目或替换素材会创建新节点；旧节点中的对象和原始资源仍保留。Undo／Redo／Checkout只改变活动位置。失败／NoChange不创建节点，未提交草稿仍可取消；丢弃未入历史的候选／缓存不是删历史。不得提供删节点／删分支／清空历史／压缩合并掉操作的UI、AI或应用接口。

标签通过application的专用历史元数据用例修改并校验来源／修订，不暴露任意节点字段setter；有效修改纳入待持久化元数据，但不为此修改SkinProject或创建内容历史节点。系统保存标签来自真实手动保存，当前／分支／末端等来自导航或拓扑；若提供自定义标签，则在授权范围内编辑，不能把自定义文字当作系统保存事实。检出旧节点不回滚当前标签；重开显示最近成功持久化的标签／系统事实，编辑中尚待持久化的标签也应如实显示。标签不拼进永久地址。

这里的不变性针对逻辑历史，不要求每个数据库页永远禁止重写，也不宣称能阻止编辑器外的文件破坏；事务、校验及备份负责相应的数据保护。无损格式迁移可以调整承载编码／引用索引，但不能借迁移改写既有节点的编辑含义或原始资源；无法保持时拒绝正常工程保存，保留原件。

## 2. 推荐的逻辑项目结构

面向**自包含的单一工程文件**：保存全部项目素材库（包括尚未被图层／音效使用的已登记素材）、原始图片／音频／附件、编辑结构与参数、配置／输出映射、完整历史及其恢复元数据。不能以“当前未导出／未使用”为由省略已属工程的内容。个人偏好、本机来源、预览歌曲／Voice和缓存仍按第1节独立管理；“完整工程”不等于打包整个进程的内存或用户机器。

以下保留初稿的逻辑条目示意，不是要求用户手动管理的目录；P3-0已选择SQLite表／记录承载，不按这些路径打包ZIP。自制fixture和用户项目分别存放，项目不依赖全局缓存才可打开。逻辑工程完整与物理写入量不同：完整代次可以引用文件中已经存在的块，不要求每次重写它们。

```text
manifest.json                         格式／能力、项目／历史身份、保存代次与入口
project/states/<digest>.json           一个内容状态的根描述，引用共享元数据块
project/chunks/<digest>.json           文档、树、资源表、音效、配置和输出等不可变块
history/root.json                     小型入口：树根／索引根、手动／保护检查点及元数据引用
history/index-pages/<digest>          有界分块索引，避免每次改写全树列表
history/nodes/<persistent-node>.json   稳定节点、直接父、内容状态引用及必要摘要
blobs/sha256/<prefix>/<digest>         该保存中所有分支可达的原始字节
extensions/<namespace>/...            有声明的扩展／不透明附件
```

P3-0已约定`.oskproj`、SQLite容器和头字段，见[格式第1节](PROJECT_FORMAT_V1.md#1-版本与识别)；上面的路径是逻辑分层示意，不是实际ZIP条目。正式项目状态字段尚未实现。manifest必须能识别格式家族、容器版本、项目schema、历史schema、必要能力及其版本、状态入口、当前保存代次和上一代次；应用版本仅用于来源诊断，不能代替能力判断。

原始资源按摘要和长度共享，同一Blob可被多个Asset和历史状态引用。元数据也可共享，节点不复制原图／音频，不逐节点存完整祖先路径。哈希校验针对条目的**实际原始字节**；不能把Rust Hash、格式化JSON后的偶然结果或文件名当成跨版本内容身份。相同语义的不同编码可以有不同摘要，不因此变成不同的历史节点身份。

历史节点记录保持不可变；新增子节点不原地改写旧节点内容，子边／顺序等查询由分块索引维护。上述路径只是逻辑地址，落成事务型页存储时可以是表／记录，不要求每个JSON都成为独立物理文件或每次重写整份manifest。

内部条目只用固定ASCII路径、稳定ID和摘要，素材显示名作为UTF-8元数据保存，不能直接拿用户文件名拼存储路径。容器须拒绝绝对／越界路径、重复条目和边界绕过；不把宿主路径分隔符或大小写行为当格式规则。导出文件名另外按目标支持范围检查冲突／非法名称，不能静默重命名以掩盖差异。

skin.ini原始记录、未知配置和附件保留原字节及顺序，不能为了写入JSON先做有损Unicode转换、改换行或合并重复配置。原字节可作为独立块引用，已解析含义只是受版本约束的解释；元数据JSON本身的重复键等歧义则应明确拒绝，不依赖解析库“取最后一个”的偶然行为。

### 历史状态不依赖旧命令可执行

推荐保存可独立恢复的版本化状态描述及共享块；历史操作名／摘要只供说明，不能要求新版本重新执行旧Command、脚本、资源路径或旧UI事件才能恢复节点。当前私有Patch、Arc／BTreeMap布局、API v6请求和去重回执都不是磁盘协议。

初期不为兼容预先引入通用事件溯源框架。若后续为体积采用持久化差量，差量自身必须有稳定schema、检查点、明确基线和有界恢复成本，不能直接序列化当前私有Patch。先用10000深度／多分支样例核对共享状态方案的磁盘、内存和恢复成本，再决定实现粒度。

### 全部分支与资源闭包

保存捕获中所有节点引用的状态、所有Asset原始字节及必要不透明附件都必须存在。仅旧分支还引用的声音／图片也在闭包内；不因当前头没有它就回收。临时联合选择、预览谱面／音乐、外部默认皮肤、头像和本机路径不因同一进程使用而成为项目资源。

原始字节驻留预算不等于项目磁盘容量。现有BlobLease契约允许非驻留保管，但P2的Entry实际上持有Vec；持久资源适配须验证文件保管租约与受预算驻留缓存分离、后台读取和迟到拒绝，不能靠调大128 MiB内存池承载长期历史。资源不受支持、超限或损坏时保留原文件并明确诊断，不能部分打开后默认覆盖保存。

## 3. 历史身份、短地址与文件复制

审阅修订2：n／b显示映射不属于永久节点摘要，映射重分配需新的address_epoch；持久状态的Schema升级追加StateView，原节点state／record_version／checksum不变。详细版本分派与迁移引用规则见[格式第6.1节](PROJECT_FORMAT_V1.md#61-跨schema迁移不重绑定历史节点)，当前实验版本及加载实测见[本轮审阅](P3_0_LOAD_REVIEW.md)。

需要区分下列概念。**增加持久身份，不复用当前HistorySessionId来假装跨重开兼容。**

| 身份 | 生命周期与用途 | 建议 |
| --- | --- | --- |
| ProjectId | 逻辑项目；改名／移动／正常另存为不改变 | 现有128位值；首版存储前替换普通宿主固定1和UI盲目递增分配 |
| HistoryId | 持久历史树；跨关闭和打开保持 | 新的固定宽度身份，与打开会话分离 |
| 持久节点ID | 同一节点跨重开／迁移／复制保持，新增节点不可与分歧副本混同 | P3-0采用128位身份；文本／短键见格式第2节 |
| n／b短显示地址 | 当前打开文件中便于UI和AI选择 | 保留有界短显示；必须带上下文，不能充当跨文件永久主键 |
| HistorySessionId／打开epoch | 每次项目打开／恢复激活均为新值；不是每次普通Undo都换会话 | 继续用于拒绝旧请求、草稿、音频、GPU及导入结果，不从文件复用 |
| revision、RequestId、DraftId | 当前运行／去重／草稿上下文 | 不当作永久书签；不靠恢复旧回执维持文件历史 |
| 文件谱系／绑定、SaveId | 区分逻辑项目、实际保存目标和一次成功文件提交 | 保存指针按绑定归属；不用绝对路径当持久项目身份 |

### 为什么不只把现有u64计数器存进去

同一项目复制成A、B后，两边都可能从相同next_node继续编号，产生不同内容却同为n42的节点；单文件锁不能阻止两个不同文件这样分歧。ProjectId＋HistoryId＋旧计数也不能解决这点。首版不支持合并，并不意味着可把有歧义的地址公开成永久引用。

推荐未来使用新的持久128位节点主键，由宿主身份源／application准入协调；同一已存在节点的副本保留ID，两个副本的新节点各自取得新ID，遇到冲突明确拒绝。domain不引入时钟或随机依赖。n短号作为文件上下文中的别名，可保存映射以方便重开；b坐标仍只是辅助位置，复制后新增的同名短号不代表相同主键。

P3-0定约：持久ID固定32位小写十六进制，紧凑单节点文本用k＋base36（最多26字符），永久引用用hp1三段身份（固定102字符）。**不把新长值偷偷按旧n协议解释。** 复制／传输时使用带版本的`{project_id, history_id, node_id}`结构；解析到当前打开上下文后，再生成带新session和expected revision的编辑请求。永久地址本身不是写权限。

主键扩为16字节不要求每个节点储存三段格式化字符串；项目／历史上下文只在根记录一次。仅比较单个ID，65536项从8改为16字节增加512 KiB原始ID数据；若另存8字节短别名再增加512 KiB。此为字段算术，不是总内存／文件成本测量，父引用、索引和编码开销仍须实测。

另一可选路线是保留64位节点并引入写者命名空间；它同样需要新持久键、复制规则和版本化解析，不能靠现有计数器自然获得唯一性。P3-0已选择128位路线，不并行实现两套协议；当前产品尚未升级。当前v6的n≤14／b≤28和所有测试保留，实施时明确提升契约版本、记录旧请求处理，不以文档宣布已完成。

### 复制、另存为与迁移

- 改名／移动：不改变ProjectId、HistoryId或节点身份；本机文件关联重新解析。
- 正常另存为：复制完整历史，保留逻辑项目／历史身份，建立新的目标绑定／保存谱系；原文件不受影响，不把旧目标保存指针冒充新目标。
- 用户在文件系统复制：保留共同来源，两个文件可分歧；每次打开仍有新session，不自动合并或猜同名短号。永久节点身份方案须经此回归。
- 显式“复制为新项目”：另立项目／历史身份，说明与普通另存为的区别；对象ID可在新项目作用域内保留，引用上下文随之改变。首版若没有此入口则明确未提供，不暗中根据路径猜测。
- 无损格式迁移：保留ProjectId、HistoryId、节点身份及关系，可重编码块和重建索引。确实改变编辑含义／导出结果的转换须明确说明，保留旧状态或另存转换副本，不能原地改写已显示的旧节点。

## 4. 保存整棵树、保存标记与未保存状态

保存开始时捕获同一不可变截面：当前头、全部已有节点／分支、状态与资源闭包、导航偏好、保存元数据、必要版本及目标绑定／预期SaveId。不是后台线程遍历不断变化的活动会话。捕获后产生的新节点可以继续留在内存，但不冒充已被这次保存写入。

树根、父子关系、短号映射／分配水位及各检查点的头／Undo后分叉Redo偏好需要明确恢复；恢复偏好须核对为真实直接子节点。手动保存／曾手动保存记录按无私人路径的目标谱系区分；当前／起始／末端／分支标签按实际激活头与拓扑计算，不存六份可互相冲突的布尔值。

身份准入状态也属于恢复约定：对象在一个有效事务中创建后又删除，其ID即使不出现在最终快照，也不能因重开而重新分配。须保留必要的已用／退役身份登记或等效的可验证分配记录；只扫描当前头、甚至只合并各节点可见对象集合都不一定完整。它不要求持久化旧RequestId／请求回执；登记体积另受元数据预算和规模测试约束。

将这次SaveId、提交来源及捕获截面的提交事实放入**待提交文件版本**；只有实际文件提交成功，该版本和相应检查点才生效。仅手动来源更新传统保存位置／标签，自动和退出补存更新保护事实；成功后立刻退出仍能从文件核对。失败、未完成或提交前取消不增加事实；文件已提交后的取消不能否认已发生的提交。

捕获完整截面是逻辑一致性要求，不是要求每次遍历／重新编码整棵树、读取所有原图或做整文件哈希。存储适配器可按上次已提交代次、已验证块和变化记录准备增量；首次保存、外部文件冲突、完整校验或迁移的成本单列。

未保存判定至少分为：

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| 内容状态差异 | 当前头与该目标已保存头不同 | 提示项目未保存；不靠渲染像素相等抹除历史语义 |
| 历史／文档元数据差异 | 从A建B分支后撤回A，而B尚未写入文件；导航／用户历史注释改变 | 即使head回到已保存节点，仍不能显示“全部已保存” |
| 偏好／工作区差异 | 换主题、设备、面板或视口 | 走独立设置／工作区保存，不创建项目内容节点 |
| 派生数据变化 | 重建缩略图、PCM或GPU资源 | 不令项目变脏 |

因此不能只比较`head == saved_node`判断关闭是否可丢弃。保存完成后仅确认捕获截面已写入；期间新增分支、导航或后续设置变化仍分别待保存。保存与Undo／Redo不为此新建项目内容节点，更新元数据只能通过application专用用例。

### 4.1 历史自动保存的写入边界

历史节点不是只有操作名和连线；它引用的内容状态、配方和原始字节也必须可恢复。自动提交只写本轮缺失／变化的数据，但这些数据须构成完整闭包，不能先承诺“历史已保存”，再等手动保存补齐素材。

| 上次提交后发生的事情 | 本次需要提交 | 复用的已有数据 |
| --- | --- | --- |
| 只移动／旋转图片或修改音效增益 | 新节点、变化状态块、相关索引页及提交入口 | 未变化原图／音频、其他状态与旧节点 |
| 导入新PNG／声音／附件，或建立引用新内容的分支 | 新原始字节、素材／状态块、新节点与索引、提交入口 | 文件中已验证存在的原始字节和旧分支 |
| Undo／Redo／检出，没有新内容节点 | 当前头、有效导航偏好及相关持久元数据 | 所有内容块和原始字节 |
| 增加未使用但已登记的库素材 | 新素材字节、素材库状态和对应历史数据 | 其他素材与状态；不能因尚未引用就省略新素材 |
| 没有待持久化变化 | 不创建仅因计时到期而产生的空代次 | 整个已提交工程 |

常规手动保存与历史自动保存共用一致性／增量提交机制，以来源区分，不维护一套可能只保存树壳的旁路。未提交草稿不会因自动保存而变成内容节点；手动保存遇到活动手势时须明确等待完成／处理草稿，不能悄悄保存与可见草稿不同的旧内容并显示全部已保存，具体交互在文件UI定案。

周期、停顿触发及一般调度合并的推荐方案见第4.3节，尚待审阅；默认重开头与退出补存已按第4.2节确定。后续调度须有界、按目标串行，不把每次计时无限排队；自动提交完成后只确认其捕获截面，期间的新编辑仍待后续提交。

持久状态分别表达最新成功提交代次、最近手动保存检查点、最新保护检查点及提交来源，不压成一个指针。自动／退出补存成功是真实落盘事实，但不是一次手动保存，不移动手动保存位置或把其节点冒充用户手动确认。保存类标签明确关联手动保存，自动保护事实独立记录；保护状态的具体图标／面板和自动周期后续定案，本轮不实现UI。

### 4.2 不保存退出、默认重开与主动恢复

一个工程文件可以同时保存完整历史、手动保存的A和更晚保护的C。**文件中最新的数据，不必就是正常打开时默认激活的项目状态。**

| 持久／运行状态 | 含义与变化 |
| --- | --- |
| 最近成功手动保存检查点 | 对当前文件绑定手动保存真实提交的节点及相应内容／导航上下文；正常打开的默认位置。自动保存、退出补存和“打开最新”都不推进它 |
| 最新成功保护检查点 | 已完整提交的最新手动／周期自动／退出保护截面，可显式恢复；记录提交顺序与来源，不能只按时间戳或最大NodeId猜 |
| 最新文件提交代次 | 当前可读的完整持久入口；可能是历史／保存元数据提交，不等同于手动保存节点或活动头 |
| 活动头／打开来源 | 当前会话正在编辑哪个节点，以及来自默认打开、主动恢复或显式导航；不是用文件中的最新指针直接覆盖 |

“检查点”是包含节点、必要导航及截面引用的存储元数据，不产生新的项目内容节点；具体字段／编码随schema冻结。默认激活A时使用A的完整项目状态，不把C的新图层／素材库内容混入A，但整棵已保护历史及C的资源仍保留，可查询／主动检出。面板布局、选中对象、Voice和设备不是这里的“上次保存状态”，继续按工作区／运行约定处理。

关闭操作：

1. 选择“保存并退出”：完成捕获与真实手动提交，更新手动保存及保护检查点后关闭。失败不标成功、不悄悄退出。
2. 选择“不保存”：含义为“不把本次工作确认成新的手动保存版本，仍保护历史”。由application协调关闭，停止新的项目写入和计时任务准入，处理在途回执及活动草稿，捕获最后已完成的编辑／显式导航；通过同一增量事务完成退出保护，再关闭。新检查点来源标为退出保护，手动位置仍为A。
3. 选择“取消”：保持工程打开并恢复正常写入准入；未发生真实提交的工作不能因关闭对话框出现而被当成手动保存。若取消发生在保护已提交后，不否认该事实，但仍不推进手动位置。

退出保护不隐式提交未完成／已取消的草稿，不序列化运行会话；草稿经既有入口明确结束／取消后才捕获。并发AI写入也受关闭门控，不能在捕获C后又接纳D并把它无声丢弃。补存失败或结果未知时保持工程打开，先核对／重试、取消退出或另存完整恢复副本；不提供“丢弃已提交历史后强退”的正常退出入口，用户也不能以此绕过历史保留。界面须说明历史仍被保留；不提供清空／删除这些历史的另一个显式动作。未提交草稿的取消与已提交历史区别处理。

正常重开先验证最新持久代次和完整历史，再按手动保存检查点激活A，并提供“打开最新保护状态”入口；如需区分周期／退出来源可展示来源信息，不能伪称都来自手动保存。选择打开最新C不会自动手动保存，不删除A或其他分支；从A或C继续编辑均遵循原分叉／修订／资源规则。

示例：手动保存A→编辑到B并周期保护→继续编辑到C→“不保存”退出。退出补存成功后，文件保留A／B／C及所有分支资源；下次普通打开为A，主动打开最新为C。若最后一次手动保存实际捕获的是更早节点，则以那次真实回执为准，不能拿收到回执时的头替代。

还须覆盖三种边界：

- **默认打开不覆盖最新保护位置。** 打开A且没有新的编辑／显式导航，再遇到计时器或关闭，不应产生空提交把原有最新C改成A；保留C供主动恢复。后来从A实际编辑到D并保护后，最新变为D，C仍是可达历史。选择“打开最新”本身也不创建内容节点或使手动位置前移。
- **新工程尚无手动保存。** 不能虚构“上次保存A”或自动把最新状态标为手动保存。未选文件目标时，退出保护可保存到独立、持久的未命名工程恢复区，使用完整工程格式与资源闭包；后续提供明确的恢复入口，不擅自生成用户未指定位置的普通工程文件。用户给定路径后的常规保存仍进入同一自包含工程。此特殊恢复路径不是一般已命名工程的外置必需日志。
- **损坏／缺失检查点。** 若手动检查点无法验证，不静默打开最新C并冒充A；诊断后由用户显式选择其他可验证状态／恢复副本。不完整历史须进入明确恢复流程，不能当作正常无损打开或自动覆写原件。崩溃后也可提示恢复最新，但不能未经选择把默认手动状态改掉。重新激活始终生成新运行epoch，不恢复旧草稿／声音／请求。

### 4.3 自动保存周期与触发建议（待审阅）

推荐“有变化才调度、短暂停顿触发、持续编辑有最久等待、普通自动写入限流”的组合。唯一的参数表、触发分类、有界队列、失败退避、偏好与AP01–AP13验证计划见[自动保护策略](AUTOSAVE_POLICY.md)，本轮仅设计，不把推荐数值加入AGENTS或现行运行配置。

正常目标是及时发起后台增量保护；实际完成还受任务／存储／故障影响，不能承诺一个未经验证的最大丢失秒数。主线程只做短捕获，不依赖GUI帧率或音频回调供给定时；普通保存不触发GPU回读／整库解码，无变化撤销唤醒。合并保存需求不合并历史节点，旧回执不能清掉其捕获之后的新工作。

已确认的退出补存和默认手动位置规则不随推荐周期变化。编辑期间后台保护开关、最长等待等属于独立用户偏好；关掉后台调度也不等于取消手动保存或已承诺的退出保护。具体参数与候选性能目标需用户审阅和P3验证后冻结。

## 5. 偏好、本机设置与工作区结构

建议使用独立于项目的用户数据根，按平台“配置／持久本机状态／缓存”类别由小型适配器解析；不把某个Windows盘符写进协议。实际系统API与目录在实现前逐平台确认。

```text
用户配置根/profiles/<profile-id>/preferences.json   可迁移偏好及用户显式覆盖
本机状态根/profiles/<profile-id>/machine.json       外部路径、设备选择和本机关联
本机状态根/workspaces/...                           文件上下文的视图／窗口恢复
本机状态根/recovery/...                             有来源及完整性校验的恢复记录
缓存根/<cache-family>/<version>/...                  可重建派生缓存
```

这是职责划分，不要求首版做多用户档案管理器；先用一个固定默认档案也可以。头像等用户资料若复制保管，进入独立用户资料区；皮肤项目不隐式携带这些内容。设置导出默认不带本机路径、设备、最近文件、私人头像或认证；未来若提供显式迁移包，列清包含项再由用户选择。

偏好键使用稳定含义，例如`editor.theme`、`editor.layer.delete`动作绑定；不能直接保存Rust枚举序号、egui Id、窗口句柄或OS设备当前数组下标。动作改名保留迁移／别名，缺失动作标为暂不可用并保留自定义绑定；文本／IME及冲突路由规则仍由统一输入系统负责。

用户显式选择与未设置必须可区分；`null`／清空与缺失字段不混用。新增版本改变默认值时，不覆盖已设值；旧字段缺失按其来源版本定义解释，再显式迁移，避免“同一文件无变化却换了设置含义”。平台不支持的快捷键／设备值保留待重绑，不转换成会误删图层的绑定。

外部路径迁移失败可退回“未配置／需重新选择”，保留原值用于用户修复，不扫描认证或任意个人目录寻找替代。布局失效可使用安全默认并保留原记录；不能把布局版本不兼容当作清空全体偏好的理由。设置损坏时可临时使用安全默认，但禁止启动后自动用默认覆盖唯一原件。

## 6. 独立版本、未知内容与兼容方向

| 版本轴 | 负责什么 | 不等于什么 |
| --- | --- | --- |
| 应用发布版本 | 产品发布、诊断来源 | 不直接决定数据能否读写 |
| 容器／manifest版本 | 条目读取、完整性、入口和基本能力 | 不等于图层或音频语义 |
| 项目／历史schema | 项目状态、节点、关系和保存元数据 | 不等于MODEL_VERSION或API_VERSION |
| 图像／音频配方语义、兼容配置档 | 变换、合成／色彩、增益与受支持的stable规则解释 | 同一JSON结构不保证结果相同 |
| 设置／工作区／恢复格式 | 各自数据及迁移 | 不随项目格式被迫一起升级 |
| application／外部传输API | 请求、结果和能力协商 | 磁盘历史不能依赖它永久可重放 |

避免给每个无关字段都加版本；按真实独立数据家族版本化。所有持久整数ID／大计数有明确文本编码，浮点仅接受有限值并要求往返；矩阵顺序、单位、角度、alpha／色彩及音频增益含义写入格式语义，不能由内部类型名猜测。枚举使用稳定文本tag，不依赖声明顺序。

每个发布版必须给出实际的“可读取／可无损编辑保存／可导出／可迁移”矩阵和旧fixture。目标是新版本继续读取所有已发布正式格式，经无损迁移继续编辑；无法兑现的版本不能无提示断开支持，须保留原数据并提供受测迁移路线或明确只读限制。现在没有已发布文件格式，不能虚构已支持的旧版本。

旧应用遇到未来格式，不承诺能编辑所有新功能：

- 能完整理解版本及所有必要能力，才允许常规编辑保存。
- 已知外壳中的明确非语义扩展／附件，只有按协议声明可不透明保留，且能保留资源闭包时才可原字节透传。
- 未知的必要能力、图层／效果／历史状态语义或普通未声明字段，默认禁止覆写；可安全浏览时只读，否则明确拒绝打开。不能仅靠保留JSON键就声称能正确合成／编辑。
- 已知的Opaque原始素材可保留，不要求解码。未编辑音频按原字节输出；不能处理的编辑或隐藏编码需诊断，不能漏文件或零字节代替。
- 自动降级、删除未知字段／未支持图层／旧分支均禁止。目标格式无法保留完整历史与内容时，不提供通过“兼容工程副本”裁剪记录的旁路；原件保留并明确不支持。皮肤导出是独立产物，不携带编辑历史不等于可以删改工程历史。

初版存储实现对未知历史语义采用保守只读／拒绝路线；不为容许局部编辑预建复杂不透明历史执行器。配置／偏好中已声明为可忽略的扩展保留原始子块；整体未知格式不能被默认设置重写。

数据兼容和像素／样本表现兼容分别验收。重构或依赖升级不得静默重解释旧配方；需要时保留旧语义解释器或做可说明的转换。修正渲染错误、舍入或兼容规则若造成表现变化，记录范围与回归容差，不能承诺未经验证的逐平台逐位相同。

## 7. 安全保存、迁移与恢复

常规保存：捕获→核对上次提交及外部修改→预算／资源闭包检查→写入新增／变化块及索引页→校验该增量并确认引用完整→原子提交新入口／代次→返回真实回执→关联保存事实。新入口引用既有块与新块，代表完整工程；**“原子提交”不等于“每次完整重写文件再重命名”。** 提交边界及持久化强度由平台／文件系统验证，不能把仅写完临时数据当成功。

每次目标提交必须保持历史单调：新入口包含目标上一成功代次的全部节点，同一ID不得换成不同的逻辑操作／内容／父关系，所有依赖继续可用。相同不可变记录的幂等复用可以接受，不同内容的同ID须拒绝。标签及合法导航／保存元数据走独立写集，不让通用覆写接口接触节点本体。

保存旧内容节点A或较早捕获，不代表可以把文件中已经存在的较新历史C移除。自身串行提交可在保留原捕获A的手动位置及确认范围的同时，保留已验证存在的历史记录，必要时重准备索引；过期捕获／外部修改不能自动合并覆盖，无法验证时拒绝并协调。另存到已有工程、恢复旧备份覆盖较新工程也不能减少／替换目标历史；冲突应换新目标或保留原件，不能提供用户强制破坏历史的选项。

较旧的标签截面也不能因迟到保存而意外覆写较新元数据，应按修订校验重准备或报告冲突；保存内容节点A不等于请求回滚标签。用户后来明确提交的合法标签修改与这种过期写入区别处理。

事务失败、写一半、入口提交前取消或进程中断，仍应能读取上一成功代次；不能恢复出新索引加旧素材的混合工程。保存回执须确认同一工程文件中的新代次可完整读取。若物理存储使用临时日志／锁文件，须验证其归还／整合；不能把最新历史仅留在不可缺少的外置日志／缓存，却宣称主工程文件自包含。编辑中任意时刻直接复制底层文件不自动等于一致备份，正式另存／备份必须捕获受验证截面。

首次创建、另存到新文件、显式格式迁移及独立的空间整理可以需要完整写入，成本与普通增量提交分开。整理只回收已证明不被任何保留代次／全部历史／扩展及读租约使用的物理垃圾，不删除操作节点或旧分支资源。旧索引页／冗余物理镜像可在无引用后回收，不等于允许裁剪逻辑历史；不能每次自动保存都顺带全量整理。具体触发后续定案，不先自行实现一套数据库／日志引擎。

同一目标写入有界串行，外部进程／文件变化使用锁和代次／指纹冲突保护，不能无提示后写覆盖。项目只读、锁被占用或有损格式时提供诊断／另存入口，不扩大权限强写。网络盘、同步盘、跨卷和异常文件系统不直接继承受支持本地存储的保证；进程中断和断电保证分别说明。

若提交已可能发生但回执丢失／结果未知，按目标SaveId与完整性重新核对后协调保存事实，不能假定“报错就一定没写入”或盲目再次覆盖；未确认时显示未确认状态，保留恢复材料。

迁移在独立候选／副本执行，先保留原版本，再分步转换、全历史校验、往返与表现检查，最后由明确保存提交新代次。失败不能留下半迁移文件或只剩一条分支；不能启动时就改写用户原件。自动无损内存迁移与是否写回磁盘分开，转换来源及必要诊断可查。

打开／恢复须验证：版本和能力、总字节／条目／解压后大小／引用访问预算、路径边界、摘要／长度、唯一身份、单根／父子一致／无环／可达、每个节点状态、旧分支资源闭包、分配水位及Redo偏好。历史深链用迭代验证，不能按10000层递归压栈；不分配巨型GPU或PCM来证明原始资源存在。

后台生成脱离的受验证候选；只有application加载用例在处理当前未保存内容和活动草稿后激活，不给UI／AI一个通用项目替换setter。新打开epoch让旧异步结果失效，资源接管／失败回滚遵守原租约；同一ProjectId／节点被重新打开也不能接纳旧任务。

备份／崩溃恢复默认只捕获已提交的内容和完整历史，恢复后以新epoch打开，不恢复旧回执、草稿或声音。恢复记录关联来源SaveId，不能自动盖过用户稍后已保存的另一版本；正常保存、恢复副本和Git Commit是不同操作。备份／恢复副本保留策略有可见容量，不自动删项目内历史资源；不得把可清除的缓存当唯一备份。

## 8. 模块边界与实施顺序

domain继续只定义纯值与不变量，不直接依赖文件／JSON／数据库。application拥有保存捕获、加载激活、历史元数据和设置用例的窄端口；infrastructure提供格式DTO／解析、受限文件、迁移和存储实现；desktop组装异步任务，UI显示状态。文件DTO与运行模型显式转换，不使用Rust内存转储或由UI直接serde整个会话。

P3采用以下**数据契约冻结步骤**：第1–2项的身份／容器子集现有P3-0证据；完整codec、正式集成和迁移仍须后续验证。

1. 审阅持久节点身份／短地址、另存为及保存标记归属、偏好范围和自动调度建议；确认schema字段和能力分类。自动策略先用fake时钟／受控门闩验证，不能以GUI帧或sleep猜测期限。
2. 用自制fixture验证物理容器候选：优先验证可增量事务提交的单文件存储；其他容器只有能满足有界增量更新、完整性和失败保护才保留候选。需要每次全量重打包的方案不符合常规自动保存要求，不同时维护多套产品容器。比较10000深历史、分支、随机节点读取、每次变化的读写字节／放大、保存／中断／迁移、磁盘／内存和依赖成本，再冻结格式及扩展名；不凭文档选型宣称跨平台原子性。
3. 先完成无窗口格式／旧fixture／身份与完整历史恢复，再接完整保存事务、故障和迁移；独立验证设置保存和未知值保护。
4. 最后接桌面文件UI与静态导出，复查P2资源／输入／声音来源门槛。真实stable与端点验证仍按原范围，格式工作不冒充玩法实现。

首版建议使用共享状态块而非重放命令；文件式非驻留Blob保管、状态按需读取及元数据限额的具体粒度由第2步规模结果决定，保持资源可用不等于所有字节永久驻内存。不得把不够预算改成静默裁剪，也不因历史可落盘就宣称当前回执容量问题已解决。
