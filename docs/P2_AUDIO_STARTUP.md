# P2-A2：起始192帧欠载与空闲交接

2026-10-22。接续[热修改计量](P2_AUDIO_EDIT.md)。本轮重现并修复起始静音段192帧缺口；当前Windows设备的重复轮无欠载，已就绪短音p95守住20 ms。旧失败轮、初版修复的延迟失败与原证明均保留，不能由新轮覆盖。源码／二进制、日志、门槛与范围见[P2_AUDIO_STARTUP_PROOF.json](P2_AUDIO_STARTUP_PROOF.json)。

## 受控复现与原生证据

原队列稳定目标768帧，混音块128帧。受控执行两个连续480帧回调、期间不供给，第二个回调恰好缺192帧；插入供给则没有缺口。这验证了具体交错，不等于所有设备都按480帧回调。

原生只捕获前32次回调的有界窗口，每行包含“请求帧数、入口可见队列帧数、空帧数、供给批次”。重现轮的第三／四次回调为`[480,768,0,18]`和`[480,288,192,18]`，供给批次没有变化，与受控复现一致。第一回调1056帧已有2048帧预填充，没有缺口；另轮无缺口。缺口并不要求WAV解码慢或一次长于前送时长的供给停顿。

窗口由调用端在播放前显式启用，固定32条；后续回调不进入该启动窗口，累计欠载计数仍全程保留。回调只写预分配原子值，不取时钟、分配、等待或记录用户声音；读取窗口和JSON输出在诊断宿主。批次能证明交错关系，尚不能区分操作系统、后端或驱动导致回调突发的原因。

## 修复及维护边界

| 环节 | 当前策略 |
| --- | --- |
| 初始预填充 | 仍在play前填满固定2048帧队列，不排除前几秒或重置已有欠载 |
| 空闲判定 | 两通道均无Voice、无已排音频事件，背景未运行；不从PCM的数值零、增益或文件名推断。场景运行标志与音频活动分离，独立模拟时钟仍推进 |
| 空闲储备 | 根据当前后端报告的period取`max(768,2×period)`，在既有环内保留舍入余量及一个768帧替换批次；过大／未知失败明确诊断。period是规划提示，不是回调大小的保证 |
| 活动播放 | 前送目标仍768帧／块128帧；不把整个活动通路加大到更高延迟 |
| 退出空闲 | 在剩余环容量允许时追加完整768帧PCM，先用安全的rtrb chunk一次发布，再发布单调cutover；容量不足时保留Voice游标等待实际空位，不提前消耗样本 |
| 旧空白交接 | 回调只在cutover之前裁去已确认不承载有效声音／时间的旧帧，并保留`空闲储备−768`帧前缀作为突发余量。裁去数量单独计数，不重分类或抹除真实空队列 |
| 保护条件 | 有效Voice／未来事件的通道标记或有效背景位置均禁止裁去；旧代次声音仍按既有门控失效。零值背景仍有位置，必须保留；未输出的旧声音取消／历史清理不依赖GUI刷新 |

当前设备period480，空闲目标960、实际占用至多1087帧；保留192帧前缀并追加768帧后能覆盖两个480帧回调。回调的额外丢弃工作总量上界为环容量2048帧，PCM所有权仍留在控制端。并未获得任意长度回调突发或无限调度停顿的保证。

一个被舍弃的尝试把“只有场景时钟运行”也标为受保护音频，虽然无欠载，但场景触发p95约28 ms，超过20 ms。最终策略由实际Voice、未来音频事件与背景决定保留范围；这些真实时间来源不能被裁去。Runtime场景时钟不是设备消费时钟或权威游戏时钟，未因此实现歌曲定位、stable判定或新统计语义。

所有变化限于纯audio的只读活动查询及infrastructure原生交接，host提供显式诊断。application唯一项目写入口、模型2／Command5／AudioEditorPort2等契约不变；没有新依赖、平台FFI或渲染改动。SoundPlan增益与导出样本处理未变，不新增持久格式。

原生环仍只有六个float负载／帧和两个128帧暂存块，共用既有PCM额度。新增帧序号／活动标记及32条观测属于固定元数据，进程计量另覆盖；没有第二个PCM池或全音效副本。核心、旧帧、PCM、GPU的所有权边界保持不变。

## 最终结果

核心174项（44项Python＋130项Rust行为／编译拒绝／文档），桌面130项，共304项自动检查通过。格式、Clippy全目标、依赖边界及构建通过。新回归覆盖真实起始序列重放、两回调无供给／有供给、原子发布前后、首音容量不足时保留游标、切换时取消、有效零值背景、未来事件、非法period／序号耗尽及固定观测窗口。

全部普通性能轮使用同一release二进制、锁文件与默认Windows输出，48 kHz双声道F32、period480。每项重复两轮；没有同时编译、GPU回读或窗口捕获。分位数采用nearest-rank。
