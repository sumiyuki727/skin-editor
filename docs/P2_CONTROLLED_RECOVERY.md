# P2-A3：恢复分支的受控原生验证

2026-10-23。接续[迟到供给候选](P2_SUPPLY_RECOVERY.md)。本轮实际执行恢复补充，区分触发时机的延迟代价。**409项默认检查通过，四进程原生计划完成，验收未通过。** 恢复与声音同时接纳的短轮通过；恢复完成后到来的短音p95约29.5–29.7 ms，确认越过原20 ms门槛。旧策略对照另出现新的416帧欠载。候选不晋升默认，32 Voice及300秒复验仍在此关口之后。证明见[P2_CONTROLLED_RECOVERY_PROOF.json](P2_CONTROLLED_RECOVERY_PROOF.json)。

## 方法和边界

新增显式capture下的`diagnostic_recovery_probe`，只通过已有有界控制队列交给同一供给所有者。输出须选择RecoverLateWake并启用capture；空闲、旧来源、失败触发、关闭及已有待执行恢复均拒绝或撤销对应请求。仍共用16份控制额度，回执释放后才归还。普通UI／application项目接口未接入此诊断，项目写入口、来源及历史不变。

诊断显式置一次恢复请求，执行原恢复分支；不伪造owner唤醒时刻、不注入OS睡眠或阻塞回调，不声称重现了系统调度停顿。分别计数恢复尝试、实际提交批次和提交帧数。环满导致0帧时只能算尝试，不能充当恢复成功。逐探针保存三个计数的前／后值，核对连续性、每次确有提交及最终总和。

固定四个独立进程，每进程160次／通道：

1. FixedAhead正常相位扫描。
2. WithTrigger：同一控制在校验来源后触发Voice，并在本轮pump做恢复补充。
3. AfterRefill：先等待恢复控制的pump后回执，再发出新的短音请求。
4. FixedAhead正常相位扫描。

两种受控条件各320次实际PCM提交；不把正常样本混入受控样本稀释p95。AfterRefill的短音计时从真正发出短音请求开始，先前恢复控制的等待不计入该请求；恢复后队列对新请求造成的等待全部计入。原观察上界及逐Voice精确完成上界均须p95≤20 ms，任何欠载失败。CPU、内存、共享预算及关闭清理继续检查。所有失败保留，没有重复挑选轮。

可复现入口（输出目录须未存在，先准备release二进制；播放低音量自制声音，无GUI／GPU、无玩家媒体）：

```text
python tools/measure_controlled_recovery.py --binary desktop/target/release/skin-editor-desktop.exe --output artifacts/p2/new-controlled-recovery
```

两种受控模式的恢复目标最大均1280帧，诊断尝试及提交数均320，未额外出现自然迟到恢复。四轮的相位／逐Voice身份、调度快照、CPU≤15%、进程内存≤512 MiB和共享预算通过。PCM峰值5619200字节，原始字节峰值2784704字节，关闭后均0；停止后Voice为0。这里只是音频小进程成本，不能继承到图形组合或宣布完整生命周期通过。

WithTrigger精确完成上界p95为19.6995／19.7811 ms；新Voice已在生成恢复批次前接纳，能从该批次前部开始，因此没有等待整个恢复储备消耗。仍有单次超过20 ms的观察，p95通过不保证每次都通过。

AfterRefill精确p95区间为28.0507–29.7501／28.3733–29.5101 ms，下界已超过20 ms。新Voice首次生成所对应pump的开始，距请求p95约20.3364／20.3455 ms；提交后至回调入口的等待p95约9.8752／9.5911 ms，回调入口后观察上界余量约1.8401／1.6961 ms。各分段p95不是同一探针，不能直接相加重建总p95；它们结合逐Voice区间确认，主要新增等待落在恢复队列消耗、允许新样本生成之前。不能扣除观察余量追认通过，也不是解码慢造成的新候选准备等待。

结论是：同一条预混队列中的恢复储备会占据新触发前方的时间。恢复动作与触发同时接纳能通过本轮，但不能保护恢复后才到来的输入；这个候选不能完整满足既定低延迟要求。

## 新的416帧现场

轮01在phase_scan标签下捕获单次416帧欠载。前三次连续耗尽队列的480帧回调，入口队列依次1024→544→64，供给完成pass均19，间隔0.1482／1.2362 ms，合计约1.3844 ms；第三次缺416帧，未进行旧空白重定时。阶段标签不代表声音一定活跃。

此前回调入口间隔38.6078 ms，但该间隔内已有14次供给pump完成；最新几次供给的休眠至运行约2.02–2.96 ms，全轮没有超过20 ms的供给完成间隔。pass19完成在欠载入口约2.566 ms之前，队列达到当时目标而未补充。现场支持“回调长间隔后突发、没有足够储备承接三次请求”，不支持把这次缺口归为供给线程长停顿。

这与既有无窗口三回调用例形成同型证据，但只是**本轮新的416帧事件**。不能用相同数字追认此前缺现场的旧416帧原因。回调为何形成突发的OS／后端原因仍未知；仅检测owner进入间隔的候选也不会自动识别这个供给仍健康的条件。

## 下一步决策

本轮关闭“恢复分支没有原生执行”的证据缺口，并拒绝将单一预混队列的扩容候选晋升默认。零欠载、20 ms、CPU／内存门槛不变，宿主停顿及surface初始化继续独立定位；不通过直接加大目标或重复长测掩盖矛盾。

下一增量先建立小型确定性方案，验证如何把设备／连续内容的储备与新皮肤声音的接纳及生成分开。必须保留有效旧声音、背景位置与两通道代次，不能通过丢弃有效PCM、补静音或回退时间换延迟；继续约束32 Voice、共享PCM预算及回调无分配／等待／最后PCM释放。具体选择事件交接或混音执行位置尚未确定，不能直接把项目Runtime或解码搬进回调。

模型应同时覆盖“owner迟到后先补充”“补充完成后新触发”和“owner健康但回调突发”，先证明所有权、取消／暂停和延迟边界，再进入受控原生、32 Voice和300秒组合复验。当前没有新的正式音频架构落地，也没有完成真实歌曲、设备恢复、B01／完整B05／B09或P3导出。
