## 缺口与关闭契约

此前`NativeExecutor::stop(self)`在未收到端点时返回字符串错误并丢弃返回接收句柄；`EditorAudio::close`同时取走供给端，不能继续接纳迟到归还。原生Callback仍可能持有真实端点，不能将一次失败视为清理完成，也不能只保留错误标志而丢弃清理能力。

产品关闭路径现在使用不消费所有者的`try_stop(&mut self)`。先关闭输出门控并销毁OS流，再非阻塞检查返回通道：`Pending`保留接收句柄及已join的供给所有者；`Disconnected`或重复接纳`AlreadyReceived`保持终止故障。普通停止与设备错误分别记录，停止后数据回调静音，不推进复制位置，也不释放最后PCM所有权。旧消费式便利函数仍供独立诊断使用，产品不再用它处理可能失败的关闭。

待归还期间禁止启用、恢复、试听、重新准备和来源同步；界面报告冻结／错误，不将已停止供给端显示为正常播放。可继续关闭并接纳实际迟到的端点；仅有返回回执还不能退还PCM，必须通过同一BackgroundOwner的身份核对和finish。若端点收到但归属／最终复制锚点／供给清理不符合要求，则保留端点及供给端，持续拒绝新工作，不在错误映射时析构端点。

上轮将音频关闭失败笼统作为Terminal；本轮按真实返回结果细分：Pending可以继续清理，通道断开、重复接纳和finish失败仍为Terminal。完整原会话及历史保留在窗口恢复slot中；运行时清理完成与Renderer／surface／整个旧Instance退休仍是两个准入门槛。没有快照重建项目、补偿Command、新项目写入口或默认恢复策略变更。

## 受控范围

| 范围 | 具体控制及必须满足的结果 |
| --- | --- |
| 无设备原生边界 | 使用同一Callback／OutputConsumer及真实预算；端点所有者未退出时连续try_stop返回Pending，回调静音且复制锚点／预算不变。退出后只接纳一次，实际finish后额度归零 |
| 归还通道断开 | 明确断开接收路径，仍保留真实端点；反复关闭／启用和失败投递不能清掉错误或退还存活资源。只有实际所有者退出后才能回收，不提供自动恢复 |
| 错误端点 | 两个独立Runtime互换返回端点，接纳明确失败；保留返回值，不把身份相似视为同一所有者，不提前释放；项目／历史不变 |
| 真实Windows窗口 | 默认feature冻结release，真实WAV／供给worker／CPAL输出；Callback实际析构后，单槽诊断门闩保留其StoppedOutput，令正常返回接收通道实际为空。确认待清理及重试封锁后，再明确投递同一个端点并完成清理和窗口恢复 |

真实设备入口为`python tools/measure_present_fault.py --endpoint-return --binary <冻结release> --build-receipt <构建回执> --out <新绝对artifact目录>`，固定执行一次`endpoint-held`，不自动重跑失败轮次。端点保留由额外单槽通道实现，只用于明确选择的诊断；普通输出仍只有原返回通道。数据回调不等待门闩，门闩只在render之外保留／投递实际端点，不伪造错误或释放计数。

前后两代完整Editor各有场景／显式试听32次、resize、软件缩放、原生DPI与最小化恢复。中间初始化尝试返回受控AppCreation错误；连续三次继续清理、音频Enable和图形新后端准入均须拒绝。核对原会话快照、全部历史节点内容／关系／地址／Redo记忆、实际PCM／原始资源保留；投递后先完成供给与GPU清理，再退出旧Instance，才能用同一会话重试。重试仍暂停并保持背景复制锚点，旧FrameKey及设备／端点失效信号被拒绝。

归还通道断开及错误端点的跨层回归使用真实软件端点、供给线程、资源预算和项目历史，不打开OS设备；实际Windows短轮验证迟到归还。两者不能互相冒充，均不等于真实设备拔插、驱动停止失败或声学静音。
