# P2 C4：故障隔离与受控重建

2026-10-27–28，继续P2收尾，不实施P3。**C4尚未通过：当前图形重建的私有提交580.75 MiB超过512 MiB。** 音频组件及图形状态／旧代次／受管资源检查已有实测结果；完整窗口／真实硬件掉线恢复不继承它们。C1–C3旧证据保留自身构建范围。

## 已确认的问题与修复

音频回归先在活动Voice下复现：设备错误标志置位后，下一回调仍复制两个0.01样本。失败保留在`artifacts/p2/fault-rebuild/audio-before-active.log`。最初只有零背景的用例没有识别它，保留该记录，改成活动声音后才构成有效回归。

原生错误通知现在通过端点专属的粘性信号关闭复制门控，再设置错误；下次回调直接清零，既不等待UI，也不解码、分配或释放最后PCM。原有复制检查点仍拒绝复制前失效。信号只持有计量及原子控制元数据，旧后端迟到通知不能关闭新后端。

EditorAudio观察故障后关闭供给／准备、停止设备并取回唯一端点，清掉旧请求／回执／Voice；明确保留错误并撤销旧播放意图。恢复锚点取自端点返回后的最终CopyClock，不使用可能滞后的GUI／供给状态，也不冒充设备消费位置。背景来源须重新打开并恢复这个位置，缺少来源、未知锚点或格式／长度不匹配明确拒绝；采样率／声道转换未实现，不自动变为空背景。本轮诊断由调用者重开同一自制文件；格式和长度不能代替内容身份，实际歌曲来源身份须随未来受限歌曲接口落地。新端点保持冻结，重新选择当前项目来源后才接纳新的声音；UI也保留暂停，不让重新启用继承故障前的播放意图。

音频准备线程的关闭检查记录实际join结果，panic不能当正常退出；候选端点归还若缺少正常准备线程退出则明确失败。取消中的预算依旧等真实分配释放后退还。

图形设备失效信号属于单次NativeHost设备寿命；活动帧、缩略图和已捕获Draw的prepare／paint都核对它。确认失效后发出取消，以非阻塞方式检查单准备worker是否实际退出，之后才join及清理派生缓存；完成前保持准入／资源占用并请求退休刷新。门闩回归确认UI故障轮询不等待被阻塞的任务，也不提前退还它的资源。迟到结果丢弃而不在旧设备上创建绑定，不等待永远不会到达的旧GPU回执。旧CPU绘制仍持有真实资源引用，未释放时显式重建拒绝。替换宿主保留项目／原始资源、上传策略和递增FrameKey，新设备不会复用旧key或接受旧失效通知。

普通准备／poll错误不擅自当作“设备已销毁”提前回收GPU在途资源。失效回调的安装权属于设备／框架所有者；本轮只在自有离屏设备上安装，不覆盖eframe既有钩子。整个窗口的设备重建、surface恢复和纹理重登记仍需后续接线。

重建接口随后收紧为`NativeHost::into_rebuild_seed`：先确认准备任务正常退出、所有旧绘制租约释放，再销毁整个旧NativeHost，返回只含Images／egui Context／上传策略和递增key的`RebuildSeed`。其中没有Device／Queue／pipeline／纹理；新设备在这次交接之后才创建，不通过先构建替换对象再覆盖旧对象制造重叠。忙时返回原宿主，调用者须保留它并继续观察，不能丢弃忙的宿主来假装完成。最终离屏方案还在打开替换设备之前释放旧Adapter／Instance，保持同一GPU、默认配置及像素。完整窗口还必须由设备所有者同时退休旧eframe Renderer／surface和其他GPU引用；离屏交接不能证明这部分已经接线。

## 固定原生计划

完成核心／桌面检查和两次一致的默认feature发布构建后，冻结源码，顺序执行一个离屏图形进程和一个音频进程，不自动重试：

1. 图形（当前schema4）：真实GPU合成、保留egui绘制、真实准备完成待收；主动销毁本进程自己的wgpu设备，在原5秒期限内继续poll推进并等待实际DeviceLost通知。核对旧帧立即不可呈现、准备退出、未释放Draw阻止重建；丢弃旧CPU绘制并取得不含GPU的重建数据，销毁旧宿主及父上下文后才打开新Device。没有额外静置、等待进程计数降至某个值或修改默认分配策略。失效后的旧key绘制请求须被拒绝；比较重建像素、FrameKey和旧信号隔离，再交错32次尺寸／视口代次请求，最终正常关闭归还。此处不是物理DPI／最小化测试，也不再把旧CPU输出喂给新Renderer。
2. 音频：48 kHz双声道、真实WAV和有界持续背景，分别在重建前后完成每通道32次完整请求→精确Voice首次复制观察；检查暂停时显式试听与背景锚点隔离。带活动声音及未读控制注入同一原生错误通知路径，关闭后PCM归零；第一次重新打开背景，恢复最终复制锚点并保持冻结，旧通知不得影响新端点。第二次故障后核对最终原始字节／PCM和旧读取缓冲归零。此处不要求用户插拔设备，也不宣称发生了真实硬件错误。

图形活动与重建后各固定保留2秒供PID资源采样；音频请求按固定80 ms错相，硬件状态以实际回执／复制记录和有界超时判断，不用sleep猜竞争。采集只读取自己创建的进程；不需要UAC、窗口捕获、外部stable或用户媒体。两进程顺序执行不是图形／音频组合负载，不能替代C2。

## 保留的诊断失败与计划修正

第一版冻结构建`55b158e8…`的图形通知等待超时，未开始音频。只调用一次非阻塞poll后阻塞等待，不能持续推进仍在队列中的操作。锁定wgpu-core 30.0.1的`src/device/global.rs:1945–1966`说明destroy先将设备置为无效，DeviceLost通知待队列完成且maintain推进后触发。修正诊断在同一5秒期限内持续poll，没有延长门槛或把超时判为成功；后续真实取得Destroyed通知。普通GPU回读通过、与C3逐字节一致，不抵消该失败。

第二版schema1完整执行通知／旧帧／像素／释放检查，但私有提交采样峰值557.3203 MiB、GPU dedicated414.0625 MiB，**预算失败，音频未开始**。诊断保留旧CPU绘制时就创建新Renderer并回放，造成两套默认图形资源重叠；重建段随后虽下降到约218 MiB dedicated，也不能扣除或隐藏先前超限。schema2改为遵守呈现契约：先真正丢弃旧输出，再进入新Renderer；旧key／晚到结果拒绝、实际释放和所有阶段峰值照常检查。工具拒绝将旧schema1重新解释为schema2；两份原始失败均保留，默认GPU策略／上传／声音供给与资源门槛不变。

判据沿用[预算v2](RESOURCE_BUDGET.md)：正常声明播放内零欠载、双通道每阶段提交p95≤20 ms、工作集／私有提交各≤512 MiB及PID GPU dedicated≤256／shared≤128 MiB。故障注入的device_fault必须与计划相符，不豁免渲染错误／观察溢出；回调返回前后的资源所有权单列。CPU15%仍为优化目标，本轮不运行独立CPU参考，不宣布达成。

第三版schema2先丢弃旧CPU输出，功能检查通过，但私有提交峰值555.9883 MiB、GPU dedicated349.9961 MiB，仍失败；独立执行此前未启动的音频案例通过，不与图形失败合成整体通过。它进一步暴露旧`rebuild`接口要求先取得新Device、随后才能替换旧宿主：删除旧输出还不足以结束旧设备所有权。schema3采用上述先退休旧宿主再打开设备的交接，将GPU dedicated降为216.2734 MiB，但私有提交仍555.2734 MiB。最终schema4继续释放旧父上下文，GPU峰值仍216.2734 MiB，私有提交反而580.75 MiB；没有据此宣称父上下文销毁解决了私有提交问题。所有失败和各自构建保留，未挑选某个阶段低值重判通过。

## 私有提交区域对照：仍未归因

不改变产品／分配策略，另在同一冻结构建上运行一次明确标记的诊断。只对自建图形子进程使用VirtualQueryEx，分别在活动／重建阶段首次被观察后固定1秒读取映射元数据；不读取内存内容，不用诊断成绩追认原生预算通过。两次各622／639次查询，耗时16／15 ms，观察扰动单列。

MEM_PRIVATE／MEM_COMMIT区域总和284.9375→574.0078 MiB；它与GetProcessMemoryInfo私有提交不是同一统计，不能相减当误差。读写＋写合并保护（0x404）合计222.8125→382.8125 MiB；旧的222.8125 MiB仍在相同地址／大小／保护下保持提交，新增同类160 MiB。所有完全相同区域合计235.8906 MiB；其中≥16 MiB大区域合计211.25 MiB。普通读写区域也发生释放／拆分／新增，不能把全部净增都说成同一种泄漏。

自建进程同时加载vulkan-1.dll、nvoglv64.dll、nvgpucomp64.dll、nvspcap64.dll、NvCameraAllowlisting64.dll；模块在场不证明这些区域由它分配。当前证据只能把“受管项目对象已释放”与“进程提交仍保留／新增”分开，**尚缺分配调用栈或分段分配对照，无法区分具体后端、驱动、覆盖层或堆保留责任**。没有擅自释放非自有区域、改系统／驱动设置或提高512 MiB上限。

## 验收范围

最终核心444项（310 Python＋134 Rust）、默认桌面398项及可选feature406项通过格式、Clippy、无窗口测试和模块／源码边界检查；两组桌面测试重叠，不相加。本增量新增6个工具测试、7个Rust测试，并扩展取消后worker关闭检查。96份旧JSON逐项核对不变；没有新依赖、项目格式／Command接口变更或普通声音／GPU策略晋升。

工具`tools/measure_fault_rebuild.py`固定输出`c4_accepted=false`；组件通过不能自动关闭C4。仍需完整Editor／eframe的resize、DPI、最小化与在途绘制交错、设备上下文／surface重建、当前声音路线在该窗口中的故障联动。真实输出设备变化、格式适配和设备消费／声学边界分别按现有计划验证，不从主动销毁或错误通知注入推断。

下一步先固定这份失败基线，给设备创建、管线、上传及回读加明确阶段，关联大块提交首次出现的位置，再验证受控分配配置候选；数值、像素和旧资源条件均保持。通过后再接完整窗口恢复与图形／音频故障联动。C5人工交互仍开放，CPU≤15%仍为未验收的优化目标。没有自动暂存、提交或推送Git，P3暂缓。
