# P2-A3：框架、呈现与完整UI基线

2026-10-25。已完成有效的同条件F／P／E／E／P／F对照：保留原声音负载时，最小呈现CPU为13.0896%／13.2585%单核，完整UI为18.4862%／19.4685%，后者仍超15%。六轮均零欠载，提交观察p95最高12.6726 ms，内存及旧资源清理通过。**基线已建立，未实现产品CPU优化，P2-A3未验收。** [结构化证明](P2_FRAMEWORK_BASELINE_PROOF.json)保留全部结果及前两次无效对照，44份旧证明不变。

## 三种模式及边界

| 模式 | 测量阶段绘制 | 保留的共同负载 |
| --- | --- | --- |
| F：framework | 一个实心背景四边形，无编辑器控件、无自有预览PaintCallback | 同一设备／surface、原音频／背景／32 Voice、供给／读取／观察线程、项目预览请求、后台合成及资源回收 |
| P：presentation | F加同一预览纹理的正式PaintCallback，位置与尺寸相同 | 同上 |
| E：editor | 完整原EditorUi及预览 | 同上 |

**F是固定声音场景中的框架公共路径基线，不是纯框架空进程。** 同时记录主线程的框架／呈现／应用段和全进程CPU，不能将F的总占用全部归给egui，也不能把F／P的低读数替代完整编辑器验收。P与E的差额包含控件构建、网格生成及绘制工作量变化，不能直接当作某个函数的精确CPU。

三种模式在加载阶段均运行完整UI，确定相同画布、目标像素尺寸和视口代次；进入测量后才按模式切换。F/P继续使用原post-UI更新路径，避免复制暂停／场景／音频／预览规则。GUI回调次数与实际完整UI次数、预览绘制次数、最小绘制次数分开记录；不能靠伪造计数隐藏仍在运行的完整UI。

新增host私有 `gui_baseline` 与显式命令行入口，不增加用户设置、项目命令、依赖或源格式。`Editor::complete_ui`只提取原有后处理供三种路径共用；项目写入仍通过application。普通运行和既有诊断入口不启用控制模式。

## 固定计划与有效性

`tools/measure_framework_baseline.py` 固定执行F／P／E／E／P／F，全部使用相同观察。普通runner创建全部目标，UAC仅提升两个只读采集器。新正／反序严格参考先停止排空、全部通过，产品才准入；源码、锁文件和二进制在测量前后及每次准入时核对，不在采集中构建或改码。

对照要求同一实际GPU／后端／目标格式、1180×800窗口、DPI、画布位置、目标尺寸、视口代次和音频格式／设备周期。三种模式都使用原16 ms播放重绘请求；UI与呈现边界的实际密度均须在55–65次／秒且全组最大／最小之比≤1.05。该5%范围是预先声明的对照一致性检查，不是帧率调整、CPU归一化或产品预算容差。

真实输入／焦点在原受控GUI焦点覆盖之前观察；出现输入、立即重绘或焦点不一致，整组比较无效。诊断控制格式3统一请求不激活创建和鼠标穿透，普通窗口保留原行为。基线窗口不接受物理编辑，动作仍由同一受控GUI脚本分发；它不能替代真实输入、前台／全屏或人工UI验收。

本机锁定winit 0.30.13在Windows的 `window_state.rs:300–301` 将忽略鼠标命中映射为transparent／layered窗口属性。因此穿透模式有明确的平台范围：全部F/P/E共享该窗口条件，但不能把它当作普通交互窗口的纯框架下限或直接晋升普通窗口性能结论。后续优化仍须回到普通编辑器窗口做完整A/B复验。

CPU≤15%单核、零欠载、原生提交观察p95≤20 ms和资源检查均保持原样。E的两轮必须独立通过全部原谓词和独立CPU检查；控制模式通过不授权产品通过。原始进程计数、独立调度值、边界不确定性及诊断成本分别保留，不扣除差值或挑选窗口。

## 已保留的无效对照

首次冻结构建的六轮在设备、窗口和刷新密度上匹配，但第一轮发生焦点变化，随后部分窗口真实焦点不同。整组比较无效；两轮完整编辑器CPU仍为19.0204%／18.6905%，不能从这些条件不同的窗口精确相减。原记录保存在 `artifacts/p2/framework-baseline/native/`，源码与二进制另存attempt-1。

第二个冻结构建统一不激活创建，六轮真实焦点均为否；首个窗口收到76次指针移动、71次立即重绘，UI／呈现密度升至93.5903次／秒，整组比较仍无效。其余较平稳窗口不被抽取为替代成绩。记录在 `native-v2/`，源码与二进制另存attempt-2。输入记录只有种类和数量，不包含位置／按键值，也未使用窗口捕获。

之后仅为显式控制窗口增加鼠标穿透，并加强正常窗口默认不变的回归；控制格式升级到3。参考和完整六轮须针对新冻结构建重新运行，不复用前两次产品阶段。所有版本的15%／零欠载／20 ms门槛、声音供给和刷新请求间隔均未放宽。

## 优化选择与限制

当前证据支持把下一候选放在**编辑器UI的重复构建及其派生排版／网格工作**。E的主线程约10.51%–10.94%，P约5.25%–5.37%；其中应用UI约3.42%–3.74%，框架UI／网格由P的约0.42%升至E的约1.78%。共同呈现段仍约4.3%–4.9%，需要保留足够余量。

本轮不支持将一个预览PaintCallback视为主要超限来源。F的总量略高于P，不能解释成“画预览会节省CPU”或给该回调计算负成本；短窗调度和其他共同线程仍有波动。E/P差额也不是全部可回收的浪费，不直接从E的预算中扣除。

选择的第一候选是：先对音效面板与场景栏复用有界、稳定的展示数据和文字／布局派生结果，再依据实测评估网格复用。保持每帧输入处理、热区、IME、音频同步与预览刷新，按完整来源／修订、选择、字体和DPI失效；不跨帧缓存可变项目或绕过application，不跳过UI交互来降低数字。**这只是已选择的验证方案，本轮未引入缓存或取得CPU收益。**

候选必须先以普通交互窗口做小范围A/B，检查输入／DPI／草稿／历史、像素和资源所有权，再按原零欠载／p95≤20 ms／单核CPU≤15%复验。最小呈现本次仅剩约1.74–1.91个百分点余量，而完整UI距离15%仍差约3.49–4.47个百分点；不能预设一个小缓存就足够。收益不足时重审UI与呈现集成方式，不用不断重跑或更改门槛代替优化。

本轮基线的价值是定位和选择候选，不是普通交互窗口、所有硬件或完整产品达标证明。首次UI长帧、最终两轮300秒标准组合、稳定空闲／20轮资源循环、设备重建、GPU总预算及其他平台仍开放；Linux实测继续暂缓，默认未晋升，P3输出未验收。
