# P2-A3：GUI 分段、线程周期及启动模块

2026-10-24。本轮把新采样中活跃的未命名线程定位到 `nvoglv64.dll` 的启动地址，并补充应用逻辑、UI 构建及框架帧耗时。两个固定四进程短计划均通过原门槛：零欠载、提交观察上界 p95≤20 ms、各稳定阶段单核 CPU≤15%、进程内存≤512 MiB，声音和资源清理通过。**这没有关闭原 15.4461%／17.4285% 等失败，也没有证明 P2-A3 整体验收通过。** 证明见 [P2_GUI_CPU_ATTRIBUTION_PROOF.json](P2_GUI_CPU_ATTRIBUTION_PROOF.json)，前轮见 [线程采样对照](P2_THREAD_SAMPLING.md)。

## 计量与身份

当前 Python 为 3.9.6；在本机，`monotonic` 使用 GetTickCount64，报告分辨率 15.625 ms，`perf_counter` 使用 QueryPerformanceCounter，报告分辨率 100 ns。原 CPU 门槛继续使用原进程时间／原观察窗口；额外保存高精度跨度，不回算成更容易通过的成绩。

只通过自有 Popen 子进程及已核对 PID、创建时间的线程句柄读取周期、内核／用户时间；复用前轮最多128个累计句柄的观察器。周期保持原始单位，不换算成时间或CPU百分比；CPU定时服务可能因处理器实现而不同。[QueryThreadCycleTime 文档](https://learn.microsoft.com/en-us/windows/win32/api/realtimeapiset/nf-realtimeapiset-querythreadcycletime)明确区分周期和时间；进程周期使用 [QueryProcessCycleTime](https://learn.microsoft.com/en-us/windows/win32/api/realtimeapiset/nf-realtimeapiset-queryprocesscycletime)。

启动地址使用只在 tools 中动态解析的可选 [NtQueryInformationThread](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntqueryinformationthread)，无法调用或查询失败时标明未知，不成为产品运行依赖。通过同一自有 PID 的有界模块清单映射地址，只保存模块名／偏移，不保存模块完整路径，不读取进程内存或采集调用栈。模块上限512、线程上限128；阶段内短暂线程仍可能未被发现，线程／进程查询并非原子快照，负的周期计数缺口也原样保留。

新采样中，主要未命名线程启动地址落在 `nvoglv64.dll`；少量周期落在 `nvwgf2umx.dll`。这只是线程的启动模块，不能当作每个周期实际执行的函数或栈，也不能事后映射已经退出的旧超限进程。`graphics-hook64.dll` 启动线程的该窗口周期增量为0，但不排除 hook 在GUI或呈现线程执行，因此不能宣称覆盖层没有成本。

## 应用逻辑、UI 与框架帧

显式 `--verify-profiled-gui` 新增固定大小记录；普通编辑器及普通诊断不增加这些工作时钟。应用逻辑记录自己的墙钟，UI 构建沿用原记录；框架记录来自 `Frame::info().cpu_usage`，按上一帧提交的阶段归属，以 egui 累计帧号去重，首帧缺失和非法值分别处理。

核对已锁定 eframe 0.37.0 源码：该字段来自 Stopwatch 的帧耗时减去框架记录的 vsync 等待，包含 UI 与渲染，并不是线程 CPU 计数。新字段因此明确命名为 `frame_wall`；保留各列，不相减生成“驱动 CPU”。

八轮32 Voice阶段的均值范围：应用逻辑约0.081–0.086 ms／次，UI构建约0.603–0.653 ms／帧，框架上一帧约1.210–1.312 ms／帧。阶段仍绘制128–130次，未降低帧率。结果支持继续细分框架／呈现路径，而不支持将主线程全部成本归因于两行读数；这些墙钟也不能从进程CPU中扣除。

第一固定计划为“进程周期观察／线程详细观察／线程详细观察／进程周期观察”，全部开启相同的显式回调／GUI工作计量：

| 轮次 | 32 Voice 单核 CPU | 场景／试听提交观察 p95（ms） |
| --- | --- | --- |
| 进程观察1 | 12.0308% | 12.6375／12.4184 |
| 线程观察1 | 10.3162% | 11.5307／11.3084 |
| 线程观察2 | 11.9033% | 11.6384／11.9538 |
| 进程观察2 | 10.5269% | 11.6163／11.6366 |

两轮线程详细观察的进程周期分别约10.819亿／10.824亿，高精度跨度约1.980秒，进程CPU时间却分别为0.203125／0.234375秒。相近周期不等于相同CPU时间；量化、调度、频率及计数实现均可能影响，不能凭这一对观察将旧失败全归因于计数误差。

## 排除额外 OpenGL 初始化的控制

本地已锁定 egui-wgpu 0.37.0 默认在没有环境覆盖时使用 `PRIMARY | GL`。为缩小变量，最终控制保留 Windows 的 Vulkan／DX12，仅排除GL，而非强制只剩Vulkan。只在诊断 Python 进程内暂时设置子进程继承的 `WGPU_BACKEND=vulkan,dx12`；退出和错误均恢复原值，不修改系统环境或产品默认。

新增实际适配器身份后，按第二个独立冻结构建运行“默认／排除GL／排除GL／默认”，四轮均实际选择同一 RTX 2060、NVIDIA 560.94、Vulkan。不能用请求掩码代替该身份确认。

| 初始化 | 32 Voice 单核 CPU | 进程周期增量（约亿） | 生命周期工作集／私有提交采样峰值（MiB） |
| --- | --- | --- | --- |
| 默认1 | 11.1153% | 10.313 | 187.2383／213.5234 |
| 排除GL1 | 8.6631% | 10.668 | 171.7891／197.5625 |
| 排除GL2 | 14.1759% | 10.551 | 170.8828／209.4609 |
| 默认2 | 9.4506% | 10.729 | 187.5898／214.5547 |

排除GL时累计观察线程由45–46降为42，进程内存较低，但活跃的 `nvoglv64.dll` 线程仍在，周期及CPU没有一致下降。**不能把这些线程都称为未使用的OpenGL成本，也不采纳排除GL作为CPU修复。** 内存收益仅是本机短轮候选，没有新GPU dedicated／shared、像素、故障回退或其他平台成绩，不改变默认。

供给策略、480帧设备周期、32 Voice和工作量相同。该差异支持优先校验周期性工作下的CPU计数偏差，而不是继续猜测混音回退。但自有回调不包含整个CPAL／WASAPI线程，墙钟还含抢占；没有把125 ms全部判成虚假，也没有从进程预算扣除。下一步用有界自有参考负载及更长诊断窗口验证计数可靠性，再选择可信口径细分GUI／呈现；原验收数值和旧失败继续保留。
