2026-10-22，Windows。承接[提交／冷准备分段](P2_SUBMISSION_STAGES.md)，本轮选择单槽映射暂存复用，保留原 `Queue::write_buffer` 路径作为同构建对照。普通应用默认仍为原设备配置和原上传路径；候选通过显式诊断入口注入，不写入 SkinProject、Command 或历史。声音的 768 帧活动前送、owner 2 ms 休眠、观察侧 1 ms 休眠和全部原验收门槛未改。

## 方案与生命周期

`rendering::ReusableUpload` 最多缓存一个 `MAP_WRITE | COPY_SRC` buffer。原图仍先按共同计划验证、打包；候选把字节写入已映射暂存，解除映射后提交复制，再按原顺序提交 compute。所有原图写入／合成继续经过 compositor 的提交互斥，旧输出纹理不原地修改，合成语义／shader 未改。

单独的暂存租约在原生分配前以原子额度预留，总存活逻辑字节上限 80 MiB；同一分配被缓存、复制回执和映射回执共享时只计一次。标准负载占 40 MiB。这个上限描述暂存分配，不代替进程私有提交、驱动驻留或总 GPU 预算；原有 512 MiB／256 MiB 等验收值保持不变。

状态只有 Mapped、Submitted、Mapping。再次写入前先对该槽执行异步重新映射，并由准备调用方等待上次复制 submission 的完成，单次 poll 超时为 3 秒；普通 GUI 和音频回调不执行该等待。映射失败、超时或尚未完成返回明确错误，保留状态与租约，不假装腾空槽或启动另一份不受限的上传。不会等待整条持续呈现队列清空。

增长先确认旧复制／映射实际完成，释放旧槽后再预留新槽；缩小继续复用原容量。清空缓存只移除缓存引用，在途 GPU／map 回执仍持有同一个分配及预算租约，实际归还后才退还额度。取消草稿／历史切换继续由单 worker、完整候选来源核对和原生宿主回收处理，不能把半份原图发布给新来源。没有增加解码 worker、上传线程、通用池框架或第三方依赖。

本轮没有实现分块上传。把一次 40 MiB 写拆成若干同时在途的小写并不能自动消除总暂存积累；单槽方案先验证明确的分配和回收边界。也没有扩大 MemoryUsage 分配器的内存块来换取速度。

## 自动检查与真实 GPU 回归

351 项自动检查通过：核心 61 Python＋130 Rust，桌面 160 Rust，包含格式、Clippy、无窗口行为和依赖／源码边界。新增测试保护共享完成租约、取消缓存后的额度保留、超限／无效输入拒绝，以及实际启用的上传策略／计数校验。候选无法用错误配置、缺失计数、越界额度或未释放资源冒充通过；20 ms 门槛不因候选速度改善而改变。

显式 GPU 回读还执行原始 A、变色 B、较大源、A、B 的顺序，在最终显式 wait 前清空缓存，再逐一与 CPU 合成对照；要求旧输出不被后续写入修改。测试刻意对独立 renderer 输入复用标签以压力验证分配身份，未改变真实资源的内容哈希语义。每条路径原图 buffer 分配两次／内容上传五次；候选暂存分配两次／复制五次／重新映射四次，增长后缩小没有重新分配，最后暂存字节归零。另保留原暂停草稿、取消、分支恢复、过期视口及 CPU 持帧跨 shutdown 的固定七帧检查。

真实设备丢失、map 失败及三秒超时尚未做 GPU 故障注入，不能把额度 fake 或成功映射测试冒充这些平台故障已验收；它们仍属设备／故障关口。当前原生成功路径和不提前退还额度分别有独立证据。
