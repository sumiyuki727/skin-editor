## 提交测量的含义

原探针保存请求、回执、最后阴性读取前／首次阳性读取后时刻。首次阳性仍是 20 ms p95 验收使用的上界；原始区间继续保留，不能用新下界或扣除某个全局轮询间隔把失败改为通过。

显式组合诊断现在在每个通道保存最新一份生产端和回调端固定原子行。生产端记录首个非零 Voice 贡献所在批次的 pump 开始、commit 前／后、首个样本 serial、队列深度及批内位置；回调只复制 CPAL 已提供的 callback 时间戳、相同 Voice／epoch／serial、回调序号、尺寸及首个贡献位置，不读取自己的时钟，不分配、等待或释放最后 PCM 所有权。普通运行未启用该采集。读取最多尝试三次，不完整行或身份不匹配不能被接受；每通道最多归档 64 个探针。生产端在 commit 后发布诊断可能晚于回调，观察器可以等完整行，但冻结首次阳性上界，不因此把等待诊断的时间算入验收。

宿主在每次探针前调用该 NativeStream 的 `now()`，使用调用前／后的 `Instant` 校准同一流的时基。当前锁定 CPAL 0.18.2 WASAPI 的 `now()` 与 callback 使用同一 QPC 来源及 100 ns 网格，额外保留 ±100 ns 舍入余量。没有假设两种时钟原点、不同流或不同平台的时基相同；Linux／macOS 精度未验证。

`submission_causal_ms` 每行 13 项，依次为：pump 开始、commit 前、commit 后、回调开始下／上界（以上相对请求，ms），入批前队列帧数、批次帧数、首个贡献批内位置、首个贡献回调内位置、回调帧数、serial、epoch、回调序号。Voice 及完整来源仍由运行时激活／清理规则管理；这些计量字段不替代来源校验或成为项目身份。

必须分别解释以下量：

- 请求至 pump 包含控制准入／owner 调度和等待下一次可生成批次，不能直接叫命令执行时间。
- commit 后至回调开始的非负差给出已入队后真实等待的保守下界。回调可能早于 commit 开始并在执行中取得新帧，此时下界记 0，另计重叠次数。队列深度是生产端瞬时观测，不能无条件换算成墙钟延迟。
- 回调开始至首次阳性包含后端分发、回调工作／调度以及观察线程轮询。它不是纯观察误差，更不是声学延迟。
- 原阴性／阳性区间宽度继续表示提交观察不确定性。设备消费、硬件残余缓冲与声学输出不在本轮结论中。

## 冷准备分段与同构建交错控制

单 worker、单 credit 和取消／资源租约规则保持不变。增加 job 入队、worker 开始／结束、宿主接收、GPU 完成通知及发布时刻；GPU 完成时间在 ready 发布前设置。通知包含后端完成回调的调度及资源释放成本，不是硬件 timestamp query。上传 API 另分原图缓存锁、提交锁、pack、`write_buffer`、显式 `submit([])` flush 及首次 buffer 创建。计时是 wall time，不冒充线程 CPU 时间；各分项 p95 不能相加代替每请求总耗时。

冷控制按 Performance → MemoryUsage → MemoryUsage → Performance 顺序，在四个独立进程中使用同一 release、同一标准 100 PNG／10 文档／500 层／16 WAV。每轮 14 秒，把原有 20 次文档切换缩短到每 600 ms 一次，产生 21 个冷发布；同时继续普通呈现与独立音频供给。它用于归因，不是 300 秒验收；没有用缩短控制替代标准负载。

原图锁／提交锁 p95 ≤0.0003 ms；每轮只创建一次原图 buffer，后续按原容量复用。暖发布 p95 为 4.5975／3.4284／5.0172／4.8849 ms。四轮零欠载。实际冷发布可重复增加集中在 `write_buffer`，不是后台准入拥塞或 UI 等待。先前 97–99 ms 记录中的解码／pack 也较慢，而本轮四种顺序均约 31–35／7–8 ms，因此不能把跨构建／跨时间的全部差异归给 MemoryUsage。CPU 频率、调度及系统环境的具体贡献没有独立测量。

锁定依赖源码提供的机制解释（事实与推断分开）：

1. wgpu-core 30.0.1 `device/queue.rs::Queue::write_buffer` 每次创建暂存 buffer，写入／flush 后交给 pending writes；`resource.rs::StagingBuffer::new` 包含原生创建及映射。这段计时不只是一次 memcpy。
2. wgpu-hal 30.0.1 `lib.rs::AllocationSizes::from_memory_hints` 将 Performance 的 host 块配置为 64–128 MiB，MemoryUsage 为 4–32 MiB；Vulkan adapter 将配置交给 gpu-allocator。
3. gpu-allocator 0.28.0 `vulkan/mod.rs::MemoryType::allocate/free` 对超出当前块尺寸的请求创建 personal block，并在空闲时销毁；标准 40 MiB 原图暂存超过 MemoryUsage 的 host 最大块尺寸，Performance 可以走较大的通用块。

因此，**重复大暂存分配／映射及其页成本是本轮额外上传成本的主要机制线索**，与 write_buffer 分段及保留容量差异一致。这是源码路径与受控测量形成的归因推断；没有在驱动内部逐项计量 allocate、map、触页、copy、unmap 或销毁成本，也没有拿 PDH 驻留减去 allocator 保留容量推算驱动。此轮未修改上传实现或扩大内存块，后续优化须单独验证有界暂存复用／分块上传的像素、旧输出和全部预算。
