# P2-A3：线程采样开销与应用 CPU 对照

2026-10-24。已确认原外部线程观察器成本很高，但**它不是应用 CPU 超限的完整解释**。同一产品二进制的 12 轮固定对照中，普通进程观察、逐次枚举、复用句柄三组各有一轮超过单核 15%；计划整体失败。所有轮次零欠载，提交观察上界 p95 最高 12.7775 ms，内存与声音／资源清理检查通过。原 15.4461%／17.4285% 记录仍未通过；P2-A3 和默认晋升继续开放。结构化记录见 [证明](P2_THREAD_SAMPLING_PROOF.json)，前轮实现见 [32 Voice CPU 优化](P2_VOICE_CPU.md)。

## 原两次超限能确认什么

原计量器通过自己启动的子进程句柄读取 GetProcessTimes，不将 Python 观察进程的 CPU 加进应用。两次超限的稳定线程集合、线程时间之和与进程时间增量相符，计数缺口均为 0：

| 原轮次 | 32 Voice 单核 CPU | GUI 主线程 | 原生输出 | 未命名线程 | 其余有计数线程 |
| --- | --- | --- | --- | --- | --- |
| 仅线程枚举，第 1 轮 | 15.4461% | 9.7555% | 2.4389% | 2.4389% | 供给 0.8130% |
| 线程枚举＋区段时钟，第 2 轮 | 17.4285% | 9.0931% | 4.5466% | 3.0310% | 提交观察 0.7578% |

因此不能将这两笔预算失败解释为“把外部观察器算进应用”。GUI 主线程包含 UI、框架及呈现调用；原生输出还包含 CPAL／系统工作。未命名线程没有函数栈或模块归属证据，不能直接命名为显卡驱动或覆盖层。后台读取／供给不是这两次计数的主要部分；短窗中的 0 也不表示无成本。

该机记录中的 CPU 增量呈 15.625 ms 台阶。约两秒窗口一个台阶约占 0.75–0.8% 单核；线程与进程查询又不是原子快照。它限制了精细归因，不能据此扣除余量、放宽门槛，或追认旧超限通过。

## 观察器变更及确定性测试

`tools/measure_thread_sampling.py` 对原查询路径分别记录墙钟、观察进程在查询期间的 CPU、清单耗时、刷新次数和持有句柄数。普通进程观察继续使用原 WindowsSampler；逐次枚举保留原查询顺序作为诊断参照。所有成本分别报告，不从应用预算、提交延迟或音频区段墙钟中相减。

新增的复用方式只在观察阶段切换时刷新线程清单；阶段内复用已经校验 PID 和创建时间的句柄。线程退出后仍持有原线程对象，避免旧句柄跟随复用的 TID 指向新线程，并能继续读取终止计数。累计持有上限为 128；重复、错误、超限和关闭路径均释放相应句柄。它仍会读取系统线程清单的元数据，只对匹配的自有子进程打开线程及读取名字／计数，不查询其他进程的线程内容。

复用不能保证发现阶段中短暂创建又退出的线程，记录中明确标为“阶段边界发现”；不能把集合稳定等同于完整覆盖。线程计数缺口保留原值。阶段首笔清单仍会阻塞观察器，不能只展示稳定查询的低耗时便声称整个观察无扰动。普通验收观察器、产品回调、供给策略、GUI 帧率、项目接口、共享预算和依赖均未改变；未新增运行时服务。

14 项无窗口测试覆盖：句柄复用与阶段刷新、退出及 TID 复用、PID 竞争、不再可打开的线程、容量拒绝、查询／描述失败、反向计数、关闭异常后的其余清理、显式关闭失败、首次查询区间口径、固定计划，以及既有读取／回调／内存／句柄清理检查。使用受控 fake，不依赖设备或 sleep。核心格式／Clippy／依赖与源码边界检查通过；最终默认检查为 583 项（131 Python＋130 核心 Rust＋322 桌面 Rust）。桌面 Rust 未改，沿用同源码的本轮桌面检查及前轮冻结 release 二进制。

## 同一二进制的固定原生对照

预先固定顺序为 `普通／逐次枚举／复用／复用／逐次枚举／普通`，完整重复两组，不因结果重试或筛选。均运行既有 `--verify-streamed-gui`，关闭回调区段计时；保留原阶段时长、最短采样跨度、全部稳定阶段 CPU、p95≤20 ms、零欠载及 512 MiB 进程内存检查。运行期间没有构建、测试或源码修改，产品二进制与前轮摘要一致。

| 观察方式 | 四轮 32 Voice 单核 CPU | 每次查询墙钟 p50（四轮范围） | 超限轮次 |
| --- | --- | --- | --- |
| 普通进程观察 | **15.0385%**／12.7827%／11.2789%／11.9389% | 0.0755–0.0771 ms | 1 |
| 逐次枚举 | 8.2080%／14.2866%／**16.1558%**／12.2130% | 58.7039–67.8985 ms | 8 |
| 阶段刷新、复用句柄 | **15.8710%**／11.1097%／11.1097%／11.1097% | 0.4276–0.5547 ms | 3 |

逐次枚举的大部分时间位于线程清单读取；约两秒的 CPU 观察区间内，观察进程在这些查询期间累计消耗 0.6875–0.78125 秒 CPU，约为单核的 33.6–37.3%。这是明确的诊断负担。复用稳定查询低了约两个数量级，但阶段首笔仍耗约 59–83 ms，四轮该阶段查询 p95 均由这笔首查询决定。普通／复用组查询期间的观察进程 CPU 增量记录为 0，受计数粒度限制，不能解读为免费。

三组应用 CPU 的算术均值分别约 12.76%／12.72%／12.30%，仅用于描述。普通组也失败，说明逐次枚举不是发生超限的必要条件；复用组仍失败，说明减少枚举不能保证应用达标。每组四轮、不同进程、不同窗口起点和计数台阶不足以估计严格因果效应，也不能证明枚举没有任何扰动。复用组计量跨度约 1.969 秒，普通组约 2.078–2.094 秒，均按原计数／实际跨度计算，未统一重算成“更容易通过”的窗口。

新的复用超限轮中，GUI 主线程约 10.3162%、未命名线程约 3.1742%、原生输出约 2.3807%；逐次枚举超限轮对应约 9.2319%、3.8466%、3.0773%。GUI 构建墙钟均值约 0.64 ms／帧，其他通过轮也相近，不能把全部主线程增量归因到两行读数或 UI 构建。下一步应继续区分 GUI 主线程的应用／框架／呈现和未命名线程成本，并对照 CPU 计数粒度；不需要再次改动已分离的音频供给来解释这些数值。

## 清理、证据和边界

12 轮全部原生健康、双通道／暂停／恢复／热替换连续、草稿取消及历史切换清理通过。工作集／私有提交的全生命周期采样峰值为 188.8633／232.0938 MiB，均低于 512 MiB；PCM 峰值 2435072 字节、退出归零，读取缓冲峰值 8192 字节、退出归零。受管回调析构为 0、范围内端点交还为 0、范围外交还为 1；最多 2 个存活输出目标，不等同于 GPU dedicated／shared 预算通过。复用观察器累计持有 45–46 个线程句柄，关闭后登记数归零。

原始录制和源码快照保留在忽略的 `artifacts/p2/thread-sampling/`。原 32 份证明保持字节不变；未改写原比较计划或旧失败。原生比较结束后只加强诊断容量／关闭错误处理及既有资源检查的接线；用同一批原始录制补验读取和回调清理，未重跑或追认 CPU。这些后续保护的测试身份与原生采集身份分别存入证明，不将最终工具误标为已经另跑一遍原生测试。

**本轮整体性能仍未通过。** 两轮 300 秒标准图形组合、GPU dedicated／shared 与像素、真实歌曲选择、设备消费／残余、其他设备／平台和 P3 文件导出没有新增验收成绩。Git 未暂存、提交或推送。
