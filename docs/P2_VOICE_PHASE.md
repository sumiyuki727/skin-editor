最终[证明](P2_VOICE_PHASE_PROOF.json)绑定118个源码／工具／配置文件、release SHA-256 `23c34c9711cc3802ddb123d34a9f9511ae283f13aa96e3977db5ea390748a53c`及原始报告哈希；18份旧证明保持原字节。机器为Windows 10 19045、RTX2060／Vulkan，默认音频48 kHz／双声道、报告周期480帧。格式／Clippy／无窗口测试及模块边界通过；75项Python、130项核心Rust和167项桌面Rust均不依赖真实设备。原生结果与这些默认检查分开登记。

## 测量边界与改动

原探针读取`submitted_voice_ids[lane] >= voice`，随后核对精确producer／callback轨迹。新的只读`VoiceSubmission`明确区分Pending、Complete、Unknown、Superseded、Invalidated；更高ID不能替代目标Voice，不稳定读取不能推进阴性下界。Complete包含Voice、epoch、首个有效serial、后端提供的回调入口时间戳、有效样本在缓冲中的偏移、帧数及回调序号，并与请求ID和producer轨迹逐一核对。

完成标记在整个输出缓冲写入及回调统计更新之后发布，另有固定一行的回调进度供控制端记录请求相位。回调不调用时钟、不分配／等待／访问项目，新增元数据不持有PCM。声音生成、混音、解码、准入、768帧活动目标、2 ms owner休眠及1 ms观察休眠保持；普通应用未启用捕获时不写诊断行。没有新增依赖、后台服务或项目写入口。

精确身份不等于提高时钟分辨率：外部观察仍用每次读取前后的Instant夹住标记，保留首次阳性和最后一次有效阴性；等待producer的迟到遥测不得推迟首次阳性。后端提供的入口时间戳只作下界；精确标记确认自有render完成，**不确认CPAL之后的底层API返回、设备消费或声学发声**。旧探针上界仍是原门槛，精确标记另列；不能用新标记、回调入口或扣除统一观察余量追认旧失败。

宿主增加有界诊断入口`--verify-voice-phase`：20个请求相位、每相位8次、每通道160次；请求顺序按固定排列交错。控制端用当前流时基及已完成回调的入口参考，提前安排未来相位，沿用1 ms休眠。每个探针有明确收集回执后才能发下一次，不用等待固定时长猜测轨迹已被收集。原生相位实验与确定性回归分开：前者测调度／设备事实，后者用虚拟四分之一毫秒刻度重放480帧回调／2 ms owner交错，不依赖sleep或真实设备。

真实请求时记录最近已完成回调、校准区间和实际达到的相位；超出参考周期的旧／在途参考列为未分类，不取模折回“好相位”。扫描资格预先要求实际覆盖至少8个归一化十分周期区间，并分别显示全部桶计数；这仅是新诊断的覆盖条件，不改变产品延迟或预算门槛。标准300秒探针也增加同样的请求参考，但不要求标准脚本天然覆盖所有相位。

## 相位与真实排队

标准场景每125 ms触发一次，探针只采第`5 + 32n`次，间隔4000 ms；试听探针也是4000 ms间隔。当前报告周期为10 ms，4000 ms是其整数倍。新轮01的64次场景请求全部集中于周期4–6 ms；试听50次在0–1 ms、11次在9–10 ms，另3次因参考年龄跨周期而未分类。轮02的场景主要集中于2–3 ms，试听主要为7–8 ms。实际记录证实本轮标准采样集中于少数相位；不同进程起点会改变分布。旧20.2616 ms轮没有请求相位参考，不能追溯认定它恰好命中哪个相位。

两轮真实扫描的20个请求相位均完整执行，场景和试听各160次标记精确匹配；实际10桶均有样本，被采到的请求参考及目标回调均为480帧。原上界p95分别为场景19.5850／19.3967 ms、试听19.4127／19.8355 ms。精确标记的区间仍约1–2 ms宽，有单次跨20 ms，不能保证任意相位、单次或环境都满足目标。

| 独立扫描的场景相位 | 轮01原提交上界p95 | 轮02原提交上界p95 | 请求至pump p95（轮01／02） |
| --- | --- | --- | --- |
| 周期0–1 ms | 21.637 ms | 21.273 ms | 11.702／11.661 ms |
| 周期9–10 ms | 12.949 ms | 12.671 ms | 3.139／3.354 ms |

这是按实到相位分桶的描述，桶内样本数不等，不作为新的验收分布。总体p95通过不能掩盖某些相位桶的p95超过20 ms，更不能用均匀扫描替换原标准队列来“修复”验收。虚拟时间回归也表明相位会改变真实等待：owner每2 ms醒来不等于每2 ms必然生成PCM，队列达到768帧目标时会等回调腾出空间，再生成并排队。既有供给代码保持原字节；当前证据支持生成前和入队后都存在真实等待。

## 标准组合与精确完成区间

两轮沿用MemoryUsage＋ReusableStaging候选、100张1024²自制PNG、10文档／500层、2400次场景触发、300次草稿提交和20次文档切换；每通道64次已就绪探针。原采样日程和全部19项组合门槛不改。原生程序均完成报告，但轮01工具按原门槛返回失败；轮02全部19项通过。

## 新欠载的证据缺口

第一轮整个声音生命周期报告一次欠载、416帧，第二轮为0；两轮最终原字节／PCM均归零。因此首轮即使p95通过也不能整体通过。现有扫描报告没有保存该欠载的回调大小、排队量及所处阶段；被探针采到的480帧记录不能代表那个未命中的回调，不能认定它发生在启动、扫描或停止中的哪一步。原生端已有固定欠载轨迹，后续需补入这个独立扫描的报告再定位，不改供给策略或抹掉本次失败。

性能轮全部结束后，通过当前产品公开的output／Runtime／PcmBudget接口作无设备重放：空闲储备1024帧，连续三次480帧回调之间不供给，回调前队列依次为1024、544、64帧，第三次精确缺416帧，释放后PCM为0。原始结果及重放源码／库哈希见证明的`burst_replay`。这只给出一种能产生同样数字的路径，**不证明现场真的发生了三回调突发**。标准两轮实际最大回调为1056帧，也说明报告周期不是所有回调大小的保证；下一步应先导出扫描既有欠载轨迹和阶段计数，再按捕获事实决定修复，不能仅凭416反推原因。

## 复现

默认`tools/check_core.py`及`tools/check_desktop.py`仍不使用真实设备；以现有离线工具链构建release后显式运行：

```powershell
python tools/measure_voice_phase.py --binary desktop/target/release/skin-editor-desktop.exe --output artifacts/p2/new-voice-phase
python tools/measure_combined.py --binary desktop/target/release/skin-editor-desktop.exe --output artifacts/p2/new-voice-combined --memory-usage --reusable-staging
```

独立像素对照沿用`measure_combined.py --pixel-controls --reusable-staging`。所有入口要求新的artifacts目录；仅观察和必要时终止自己创建的子进程。原始数据位于`artifacts/p2/voice-phase/`，不纳入Git。普通GPU默认未晋升，音频供给策略未改变；完整UI空闲、B01／B09、设备丢失、实际歌曲／设备消费锚点、Linux／macOS和文件导出仍分别开放。没有暂存、提交或推送Git。
