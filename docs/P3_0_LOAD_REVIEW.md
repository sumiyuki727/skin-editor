## 审阅意见的判断与落地

两条意见都必要，第一条指出了实际耦合：首轮node.v1摘要中包含n别名、分支号和序号，未来重分配会改变摘要。本轮在未发布格式阶段修正为node.v2，只绑定永久节点身份、父身份、**原始状态**摘要和原始操作字节；record_version明确为2。显示绑定移到addresses表，有独立摘要和持久address_epoch。

普通编辑、检出、标签和UI排序不重分配显示地址。显式维护时原子替换完整映射、更新address_epoch，节点／内容／操作和checksum保持；旧n／b上下文被拒绝。k／hp1引用直接用永久身份，仍指向同一节点。工具Node是组合查询条目，其地址字段不进入node.record()；这不是修改当前产品API6或实现分支合并。

第二条避免将来迁移时被迫重写nodes.state。节点永远保留创建时的origin状态引用和记录版本，原状态块及资源保留；迁移追加StateView和新表示，以(origin摘要、目标schema、转换器版本)为键。读取器按明确目标及已验证转换器选择，不按最新一条猜测。新转换器可以追加另一表示，不能覆盖旧转换记录。迁移后的编辑创建新节点，旧父节点仍保持原摘要。

实验仅实现fixture.project schema1的step→schema2的edit_index，保留未知JSON成员和全部依赖；它证明引用方式，不是完整SkinProject迁移器，也没有迁移／覆写上一轮实验数据库。

工程扩展名统一为 **.oskproj**；.osk仍是皮肤分发产物，两者用途不同。识别以文件内容／版本为准，扩展名不是完整性凭证。新增Git忽略规则覆盖用户工程及journal／WAL／SHM边车；没有改变已跟踪文件。正式皮肤导出仍未实现。

## 文件如何决定读取版本

文件版本独立于应用发布版本、Rust模型版本和API版本。当前实验的识别组合为：

| 轴 | 当前值／用途 |
| --- | --- |
| application_id / family | SKEP / skin-editor-project，识别本项目文件 |
| SQLite user_version / container_version | 2，决定物理表／记录承载规则 |
| profile | p3-0-r2，明确为实验文件，不能当正式项目profile |
| project_schema | 1，项目状态家族外壳版本，不强迫所有子块同版 |
| history_schema | 2，历史／地址／检查点整体约定 |
| nodes.record_version | 2，选择该节点frame的校验解释 |
| 状态块kind／schema | 当前fixture.project支持1／2；其他实验块为1 |
| required features | storage.core:2、state.p3-fixture:2，声明不能忽略的能力 |
| StateView converter | fixture.step-to-index.v1，明确转换规则版本 |

因此未来更改操作树时，编辑器可以先根据容器和历史版本选择读取器，再按节点记录版本校验旧／新记录，并按必要能力决定是否可编辑。新的历史结构不能简单把旧节点改成新record_version并重算摘要。实际新增版本仍须实现读取器／迁移器和旧fixture，**版本号本身不会自动产生兼容能力**。

例如未来history_schema=3可以声明允许记录2／3混存，schema3读取器再按record_version分派；原来的记录2仍按node.v2校验。当前schema2读取器会拒绝未知历史3，不会将它误当成历史2解析。现在没有预先实现合并DAG或通用读取器注册框架。

当前版本2识别器明确拒绝直接读写未发布的实验容器1；旧读取规则仍在提交fbea6b3中，可回退重现。正式格式发布后须兑现已发布版本的受测读取／无损迁移路线。未知容器／历史结构拒绝，已知结构但未知必要能力只读诊断；不会用当前应用版本去猜旧文件含义，也不自动写回。

## 加载性能的原因与优化

首轮完整打开的剖析观察到约14.28万次Python到SQLite调用、14.21万次JSON解析。主要成本来自逐节点重新查询／解码状态，以及对每个块逐条查询引用；不是读取128MiB资源本身占满全部时间。剖析带诊断扰动，不直接与未插桩墙钟比较。

本轮做了以下受限优化：

- 状态块与两类引用按摘要排序、以三个游标流式核对，每块只解析一次，不保留整棵树的JSON缓存。
- kind／schema／project_id派生列必须先与原始块核对；随后节点JOIN使用这些已核对信息。节点、父深度、地址绑定一次联查，省去逐节点往返。派生列不是新的真实性来源。
- 原始资源仍分块读取并校验完整SHA-256／长度，所有分支与已登记迁移表示都检查；不只校验当前头。
- 结构检查升级为 **integrity_check＋foreign_key_check**。旧quick_check不核对唯一约束和索引内容一致性，见[SQLite说明](https://www.sqlite.org/pragma.html#pragma_quick_check)。参考和优化路径均使用增强检查，未靠减少检查提速。

当前实现保留reference诊断路径，和streaming共享同一套后续校验规则。破损原字节、派生列、地址、引用、原始状态、检查点和计数都不能被一条合法迁移表示掩盖。

## 一致性、取消与失败保护

校验在同一个读取事务内完成，避免多条查询看到不同文件代次。回滚日志模式的并发写者可能遇到Busy；程序明确失败或取消，不睡眠猜测锁的释放。相关隔离边界见[SQLite事务说明](https://www.sqlite.org/isolation.html)。事务直到完整校验成功才结束，失败不发布可用Store。

阶段循环按固定数量／资源chunk提供进度与取消检查；长SQLite语句通过progress handler响应取消，回调只检查取消状态，不重入连接，见[官方接口约束](https://www.sqlite.org/c3ref/progress_handler.html)。连接配置失败、SQL中断、块／原字节扫描取消均释放事务／连接；完成后移除progress／trace回调。验证还核对打开前后的文件身份，目标被替换时拒绝发布。

这仍是同步工具原型。正式GUI加载要放到有界后台任务，并在application完整验证后发布新运行会话；本轮没有接入桌面打开、保存、自动保护、音频或渲染。
