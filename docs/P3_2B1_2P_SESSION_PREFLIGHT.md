# B1-2P 初始恢复会话与原打开文件的只读核对

宿主在登记文件并激活恢复会话后，可以在安装保存协调器之前核对两者是否来自同一次打开。打开时还没有保存票；申请一次 Manual 保存来检查资格，会先占用待安装的协调槽。新入口直接借用已激活的会话和原文件观察，因而可以在第一张保存票签发之前执行。

## 核对依据与持有期

`preflight_session` 版本 1 接受登记槽、期望登记戳、原 Reader、活动会话及取消信号。application 从会话内取得恢复来源、当前持久元数据、根和选中节点的持久身份、真实节点数、admission 数和原件数。准入要求原打开的目标、项目、历史、预期提交和代次相符，编辑及导航修订均为零。活动草稿、仍被工作或快照持有的捕获、已占用的协调槽都会阻止此次核对。[应用侧借用](../crates/application/src/file_profile.rs)

文件侧认证实际创建的私有 Provider，核对持续持有的文件观察身份、原打开请求、根、选中节点、原文件 SHA-256 和 features 根。以既有域 3 编码重新计算当前持久元数据，并与文件记录比对；最新提交、手动位置、保护位置及三项计数也分别核对。成功值只能在会话和登记槽都被借用时使用，可读取来源和计数。配对结束后，再次使用时须基于当前登记重新核对。一次配对不会消耗保存身份或产生保存回执。[文件登记核对](../desktop/infrastructure/src/project_storage/file_facts/registration/session.rs)

## 两处预算边界

| 适用路径 | 已核对的额度 | 尚需证明 |
| --- | --- | --- |
| 初始会话配对 | 从同一 Reader 的 512 KiB 控制池提前预留固定返回值、元数据编码空间和临时事实值。返回值释放时退还其额度，登记槽及来源各自按所有者寿命计费。 | 创建登记观察时已经存在的恢复、验证及 SQLite 成本。 |
| 完整恢复的状态块解码 | 每个节点遍历其引用到的不同块，按原始载荷长度检查单状态上限和跨节点累计剩余字节。全部准入后才借出这些缓存块，再由读取器复制为解码 bundle。同一节点内共享只计一次，不同节点分别解码时分别扣额。 | 遍历容器、块表、JSON 展开、项目与恢复候选并存的实际分配，以及 SQLite 工作区和临时文件。 |

回归在自制工程上分别核对 Manual 与 Latest 打开、首次保存序号、两处编译期借用约束、同参数重新打开、伪造公开来源、请求取消和编码末段取消、待清理、真实草稿和导航往返。Reader 控制池测试覆盖足额和差一字节，分开观察配对、文件观察及登记槽释放。状态块测试从已存行独立计算每个闭包长度，检查不足时额度和可达集合原样保留、足额时借出的确为缓存中的块；再用完整加载检验所有节点的累计长度和原文件内容。[会话回归](../desktop/infrastructure/src/project_storage/tests/file_facts/profile/session_preflight.rs) · [恢复回归](../desktop/infrastructure/src/project_storage/tests/file_facts.rs)

## 生产关闭执行的剩余门槛

B1-2O 已分别验证应用内部受控协议的真实 Exit 父子票，以及文件侧真实 Manual 捕获的完整覆盖。B1-2P 增加了安装前配对。生产端通过同一张 Exit 子票完成文件核对仍待验证，当前接口版本维持 API 7／捕获 3／协调端口 1。

下一步应沿完整验证路径逐项核算分配前预留、实际容量和所有者重叠，优先处理历史分页聚合、块缓存与 JSON／恢复模型，再单列 SQLite 工作区和磁盘临时增长。也可另审一条能保留相同验证强度的更窄实现。取得共同 64 MiB 与独立 SQLite 证明后，才能按既定契约审阅生产只读资格及同票贯通。产品保存／关闭／重开、K1、产品性能及 stable 兼容仍沿用各自既有结论。[共同容量契约](P3_2B_START_CONTRACT.md) · [只读验证准入条件](P3_2B1_FILE_FACTS.md)
