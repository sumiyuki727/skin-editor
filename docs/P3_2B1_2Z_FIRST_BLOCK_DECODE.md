# B1-2Z 首次加载块时的原文、解析与摘要

在固定 FileFacts Small 档和已审计的 64 位布局下，从 Rust 取得当前 SQLite BLOB 副本，到首次块解析交出 `Row` 或返回错误，本轮核算的分配合计至多 **12,963,344 B（约 12.36 MiB）**。这个阶段发生在检查点元数据读取之前，两阶段分别计算。B1-2Y 的 59,647,384 B 继续作为后续检查点阶段的具名上界。[首次块解析](../desktop/infrastructure/src/project_storage/blocks.rs) · [阶段断言](../desktop/infrastructure/src/project_storage/file_facts.rs)

## 在当前行中建立和转交所有权

读取器先检查表行数、取消状态、当前列长度、剩余原文额度、哈希列及序号，才取出原文字节。锁定的 rusqlite 将 BLOB 按切片长度复制进 Rust 向量。此前入表的原块与这份向量合计至多 1 MiB。解析函数取得向量所有权，先对原字节校验 SHA，再解码完整 JSON。Small 的首次解码与索引根共用紧凑解析器，支持相同的数组增长、Map 分裂、字符串移交和失败界限。独立宽档继续沿用普通 JSON 解码。[SQL 加载顺序](../desktop/infrastructure/src/project_storage/read.rs) · [锁定的 BLOB 复制](https://github.com/rusqlite/rusqlite/blob/18ee76dbb976d5ef7e37ad5a8fffae678ca21a78/src/types/from_sql.rs) · [紧凑解析器](../desktop/infrastructure/src/project_format/json.rs)

解码返回时，解析器已释放反转义／数值读取的共用字节缓冲，DOM 中的数组与文本容量均已收口。随后按既有次序取种类、模式版本、块引用、原件引用和内容对象，最后检查未知字段。已取出的种类字符串移动到结果；在 Small 路径上其容量已经等于 UTF-8 长度。成功时原文向量直接移入返回行，同一份字节贯穿哈希校验和转交。

## 分配前确定两份摘要容量

每个成功解码的摘要在原文中至少占 66 字节，包括引号和 64 个十六进制字符。JSON 转义只会增加原文长度。设 S = ⌊当前原文长度 / 66⌋。块引用列表按“该数组元素数与 S 的较小值”一次申请输出槽。块引用成功后，原件列表只可使用剩余的 S 减去已接受的块引用数。每次写入前先验证元素类型及完整哈希。不同成功项对应互不重叠的原文片段，因此两个输出向量都无需扩容；成功列表的容量恰等于项数，也无需再申请收缩缓冲。[摘要解码与固定长度检查](../desktop/infrastructure/src/project_storage/values.rs)

坏数组即使含有许多短值，仍按原顺序报告第一个元素错误。一份列表全部成功转换后才检查严格递增顺序，然后才处理下一份列表。失败时，当前列表、已完成的前一份列表、剩余 DOM 及原文随错误退出。已缓存的此前块由外层读取器保管，在整个打开操作失败时释放。

## 分阶段上界

两个阶段共用 5,165,384 B 的块表与原文额度，包括最多 1,639 个树节点、24 B 表句柄、此前原文及当前 Rust BLOB 共 1 MiB、此前派生缓冲至多 1 MiB。当前种类字符串包含在当前 DOM 文本项内；坏列表当前预留的摘要槽单列。下表计算 Rust 请求的布局字节。[块表布局](P3_2B1_2Y_INDEX_ROOT_BLOCK_CACHE.md) · [数组和文本依据](P3_2B1_2V_JSON_TEXT_SCRATCH.md) · [单份 DOM 的 Map 上界](P3_2B1_2W_JSON_MAP_NODES.md)

| --- | ---: | ---: |
| 已加载块表及上述原文／派生额度 | 5,165,384 | 5,165,384 |

数组按 8,191 个非根值、每槽 32 B 计算，增长／收缩时允许三份槽额度。完整 DOM 只需一份。最大 256 KiB 块允许两份摘要输出共用最多 3,971 个 32 B 槽。SQL 内部持有的同一行数据属于 SQLite 的独立成本。
