## 2. 责任、版本与构造资格

生产构造链为“受审infra验证器与目标所有者 → desktop受信组合入口 → application核对不透明安装资格并原子安装authority／绑定”。安装资格将验证器profile、目标注册、物理身份观察、持久工程范围和打开基线绑定在一起，不能将A目标authority配给B目标绑定。不开放new(profile, opening)、From<ArchiveReceipt>或任意成功布尔值作为签发捷径。API附录须列明哪些模块能取得生产工作资格，并有私有封套不可裸造的编译负例和架构边界检查。

跨crate端口的实现者属于受信适配器；类型封装防误接线，不是对同进程恶意Rust模块的安全隔离，也不能证明适配器真的读过文件。验证义务由真实文件回归、源码审查和准确实现profile承担。只传递四字段的SaveCommitFact转换仍只是转换，不产生验证事实。

B1只签发目标完整基线与只读验证资格，不安装能够产生MayWrite的通用生产authority，不取得SaveWritePermit或PreparedFileWritePort。B2写资格必须另经同目标、同q和预算的原子准入，不由“只读验证成功”自动转换。B1附录冻结两条构造链的实际跨crate签名、能力可见范围及错配／越权负例；私有字段不可裸造只是一项检查，不能替代生产接线验证。

## 3. 完整准备、承诺与真实写入

接纳后只消费原q。完整捕获、全部分支、对象首次准入、原节点记录／操作、当前受支持表示、未知配置原文、全部登记原字节和持久元数据均在准备范围内；不能只读取当前头或把未引用素材漏掉。每份原字节核实实际长度与SHA-256，引用／租约不等于已读取内容。

FileCoord-Proof-v1必须在B1接口附录冻结域前缀、版本、整数端序／长度、可选值编码、顺序、重复项拒绝、字符串原字节和算法测试向量。使用现有SHA-256实现；不自行拼接无长度字符串、不依赖Map迭代顺序、Rust内存布局或Debug输出。完整runtime Ticket用于本机关联，文件只能核对其可持久化部分；会话／绑定epoch、路径和本机请求号不得写入工程记录。

| PreparedWitness领域 | 必须覆盖及核对 |
| --- | --- |
| content | 持久工程／history／lineage／根、按规范顺序的全部节点身份／父关系、原记录版本／原始操作／摘要、当前表示、地址映射代次、admissions；不能只摘要head和计数 |
| originals | 所有登记资源的唯一引用、类型／元数据、实际长度和原字节SHA；共享引用计一次，缺字节或同计数替换拒绝 |
| metadata | 完整既有持久元数据、导航、当前选择与打开等价的必要来源；候选新增Manual标记单独绑定其确定增量，不能混淆q之前与确认之后的metadata |
| request | CommitId、expected前次提交／代次、origin、捕获头、完整历史前缀／覆盖及规范导航；同时保留旧格式request_hash的独立映射，不把一个旧hash填满五个领域 |
| baseline | 已验证完整文件链、最新／Manual／保护、原记录与资源范围、默认打开及推导Redo基线；新目标使用明确的未发布基线，不用零hash冒充旧文件验证 |

B2写入链固定为：预留完整工作量及终结／首次查询资格 → 消费q并编码／验证有界准备候选 → 将唯一见证交给独立控制槽 → 核对目标和expected → 取得同任务写许可 → 执行增量事务或首次发布 → 完整核对实际结果 → 发布事实 → 等待Ack及实际所有者退出。准备阶段不得对目标执行BEGIN IMMEDIATE、插入块／原字节或发布目录项；准备数据可放在受限、明确拥有的独立scratch，scratch本身不是已保存工程。是否采用内存或独立暂存必须计入profile并冻结，不能靠隐式全量复制规避预算。

旧write_capture不能接收一个从SaveExecution中偷出的可变capture，也不能在Complete之后重新抓取当前Session。新writer消费已经准备并固定的编码／索引及资源租约；旧节点／原记录／已有媒体和索引页按既有增量语义复用，不每次全量重写工程。新增节点状态与新资源同事务提交。正常保存可有全树验证成本，不宣称常量时间。

MayWrite必须同时具有实际准备好的应用metadata候选、生产见证和文件工作候选；VerifyOnly永远不能获得写许可。候选不足／代次耗尽时，仍可在独立只读配额内判断合格NoChange；确需写入返回RequiresWriteCapacity，读失败不能伪装容量不足或成功。首次Manual空根、Latest无Manual均须真实新增Manual事实。

一旦越过可能写入边界，普通Io／Sql／取消／丢完成／进程退出也默认未知，不能只匹配StorageError::OutcomeUnknown。须覆盖COMMIT成功后FileStamp、PRAGMA data_version、连接重开、清理与发送失败，以及hard_link成功后的错误。确定未提交必须有明确阶段证据或合格完整复核；清理错误单列，已确认事实不回退。

失效RW连接、事务和SQLite写scratch必须先实际退出，SaveExecution执行守卫最后释放；不得把连接留在registry而先通知writer_released。只读目标承诺、q见证、候选及原字节租约可按独立寿命保留。持有最后Snapshot／CapturedNode／query时仍不退槽；Drop顺序要用真实连接门闩和文件锁／删除共享检查证明，不能只看统计标记。

## 4. 只读事实、Unknown与NoChange

FileFactsPort1返回有界事实视图和完整校验结果，不返回活动ProjectSession，不生成Manual，不激活候选，也不打开RW连接或自动恢复原件。可复用完整验证器，但临时模型／缓存必须独立计费并实际释放；只读不是“零内存”或“轻量查询”的承诺。摘要、错误和分页明确区分空、失败及截断，页绑定目标／验证代次，旧页不能混入新目标。

普通只读路径遇已知journal／wal／shm、不支持文件类型、锁冲突或身份变化，保留现场并拒绝；不得靠immutable=1、nolock或删除sidecar绕过。SQLite读取算法会先检查热日志并可能回滚；READONLY打开标志也不等于一个完整的无副作用／目标一致性协议。B1须证明目标稳定读取与原件零写入的具体Windows策略，不能只做一次sidecar检查就声称无竞争。可选受独占冻结的物理副本验证方案，但其scratch写入、磁盘预算和清理须明确，普通核对不触发热日志恢复或发布副本。[SQLite热日志算法](https://www.sqlite.org/lockingv3.html)、[打开标志](https://www.sqlite.org/c3ref/open.html)、[immutable／nolock限制](https://www.sqlite.org/uri.html)只是约束依据，不是本项目已经验证平台行为的证据。

| 核对观察 | 必要证据与结果 |
| --- | --- |
| 找到原提交 | 同目标物理身份／工程范围，完整文件、提交链与原请求持久上下文匹配；保留更高代次。真实提交与后续绑定冲突可并存，不能因此允许新写或关闭 |
| ID不存在但原请求NoChange | 独立验证原q已完整覆盖、当时意图成立及打开／导航基线；无新Manual、无新代次，保留原Manual A／保护C |
| 确定未提交且q仍未覆盖 | 同目标完整有效，并有足够的同次事务阶段／目标连续性证据排除已提交后被替换、回退或删除；明确保留待保护范围。若证据链不足，即使ID不存在也必须归下一类 |
| 证据不足／冲突 | None、目标消失／替换、只读失败、日志待恢复、摘要矛盾、取消及仅路径／head相等，均保持Unknown／冲突，不盲换ID重写 |

第一次发布目标不存在不能证明过去从未发布。物理身份、mtime和头部匹配不等于密码学不可回退证明；B1必须给出第三类在其受控模型内可成立的具体条件及反例，不能承诺识别任意外部恶意回滚。没有证据时允许长期Unknown，禁止为了让所有场景“可重试”降低判据。

NoChange分开验证CurrentManual、CurrentProtection和VerifiedOpening。CurrentProtection核对保护头；VerifiedOpening按完整默认打开基线保留Manual A／保护C，含加载推导Redo，真实导航／新增分支立即失效。底层零修订和same_redo只能作为被核对的实现细节，不单独授权成功。完整文件读取与用户活动头选择分开；Manual缺位须诊断“需显式恢复Latest”，损坏Manual不能回退掩盖。

未知任务的查询使用独立token与attempt；先等待真实writer退出，不能等刻意保留的q承诺全部释放才允许查询。取消查询不解决Unknown，迟到合法主完成可确认但仍等待query实际Drop。读取端口不得顺带修复索引、完成发现记录或重新发布文件；这些是另有资格的写操作。

已经完整确认的真实事实不因迟到矛盾观察、查询取消或关闭取消而回退；可以独立锁定绑定并禁止新写／关闭，不能改报“未提交”或删除事实。进程中断测试证明的是已提交文件的保全／可核对状态，不承诺应用崩溃后恢复尚未落盘的内存q；q见证只有在仍有合法所有者时才可用于该次运行核对。

## 5. 目标附加、首次发布与验证复制

B1只验证初始组合时已经选定的ExistingVerified目标，不声称已有未命名工程的产品保存入口。后续B2b／B3增加受控“无目标→有目标”，B4增加“恢复目标→首次命名目标”协议：校验原会话／来源、目标资格、新绑定代次、当前Close及实际在途所有者；不重建Coordinator，不重置Save／Close水位或清Unknown。

无目标附加只在无在途保存／核对、无未结束草稿，且协调器空闲或同一Close处于NeedsTarget／RecoveryUnavailable时准入；等待目标的原CloseTicket保持，附加后仍重新完成最终捕获，不能套旧q。目标选择取消保持已完成编辑；旧选择结果不得附加给新Close。已有目标更换不是本片的通用功能，恢复首次命名另用独立TransferTicket及完整来源。

新空工程首次发布保留NewUnpublished原义：目标及sidecar不得已存在，准备完整后向唯一拥有的同目录暂存写入、完整复验并不覆盖发布。目标物理身份与发布token绑定；失败不降级覆盖复制。发布前取消与发布后未知分开；已发布目标即使回执丢失也不自动删除。所需文件系统能力不满足则Unsupported，网络盘／未验证平台不通过回退策略偷偷开放。

已有origin／已恢复历史绝不能清origin、换新根或伪装NewUnpublished。B4采用独立VerifiedCopyPrepared资格：完整复制／校验源的所有历史、原始记录、资源、admissions及导航；新目标的实际发布与后续真实Manual分别取证。是否保留Project／history／lineage身份见U3，不把普通recover_copy或publish_new当作这项能力已实现。

首次命名至少有“源冻结与复制候选 → 新目标不覆盖发布 → 新目标真实Manual → 单写者绑定转交 → 旧恢复入口状态记录”五个可观察阶段。TransferRecord须在不可逆步骤前保管源／目标定位资格和预期身份，使重启后可解释两个副本；本机私密定位数据独立于工程文件／公开诊断，不进入Git或测试fixture。原恢复副本完整保留；任何失败保留已提交事实和有效副本，不删除新目标伪装未保存。

源盘仍是C、恢复后当前已编辑到E时，复制C仅提供基线；随后真实Manual必须消费一次已冻结的q=E，包含恢复后的全部已完成编辑。若允许q后继续编辑，q+1仍未覆盖。内部Transfer任务持有限定阶段的独占写许可，供复制／Manual使用；交接完成后才向宿主发布活动目标写资格，两者不是同一权限，不以目标尚未激活为由提前放行普通写者。

单写者保证限定受支持宿主／目标注册与恢复根租约，不宣称能禁止用户在别处复制文件后由任意外部程序写入。转交期间源写资格关闭，目标资格在全部必要准备成功后才发布；旧绑定完成不推进新绑定。绑定或入口更新失败不得让两边同时可写，结果未知只核对，不自动重做Manual。C负责最终活动会话／宿主激活，本片只定义文件及目标资格交接。

按U3推荐的连续命名方案，未决TransferRecord跨重启暂停源和目标的普通写资格，包括从旧Ready重新请求源写者；只允许同一Transfer的限定步骤或只读核对。可先暂时冻结稳定源，但任何目标发布或其他不可逆步骤前必须已有可核对的持久TransferRecord。取消、进程退出或目标暂时消失均不自动解冻源；只有充分证明未发生目标发布且实际任务已退出，才可撤销转交并恢复源资格。已完成交接的旧恢复入口保持只读；这些条件并不代表U3已获批准。

普通recover_copy产生不同物理文件，不继承源的Ready、TargetBinding或写资格。B只复用其保全原件／验证副本语义；副本若要成为受管恢复目标，须经显式登记取得自己的Intent／Ready、配额及源关系。登记失败保留副本并报告未接入，不自动提升为可写工程；普通副本恢复不经过首次命名的真实Manual步骤，也不伪造Manual换取资格。

## 6. 持久恢复区与可发现保护

恢复根是本机持久数据，不是缓存／临时目录；位置与总配额见U1／U2。RecoveryEntry使用独立版本、RootId／EntryId、工程持久身份及受限固定相对名，禁止输入路径穿越、跟随重解析项或把记录中的任意绝对路径交给扫描器。发现扫描不读取根外用户磁盘；正式目标复核另凭已授权目标资格，不从发现记录中的任意路径扩展扫描。工程文件与私密目标定位元数据分开，公开日志只输出有界不透明标识。

本轮选定有界固定槽目录作为发现技术契约：根记录固定其槽数和版本，逐槽识别自己保管的Intent／Ready／Transfer记录；RootId／EntryId、下表状态顺序、所有权及中断语义在本契约确定，主索引只作可重建加速，不能是唯一发现途径。槽数实际值仍待U2决定；固定子目录／名称、字段字节布局、记录大小、校验和发布API在B3附录冻结，不得届时更改已审阅语义。根或记录损坏不自动重建覆盖；未知孤儿只诊断并从自动发现结果逻辑排除，绝不自动移动、改名、重写、提升为项目或删除。槽满、枚举超界或占用不可核算时拒绝新写，不能假定未登记内容不占容量。

| 阶段 | 持久事实与中断后行为 |
| --- | --- |
| Reserve／Intent | 先取得根／槽资格并持久保管版本化Intent，绑定EntryId、工程身份、目标相对名和待发布请求；未完整保管Intent前不得发布唯一工程文件 |
| FileCommitted | 完整自包含Exit文件已提交／发布；确认这项真实文件事实，但不等于可发现关闭。保留Intent及文件，未知结果按完整只读核对 |
| Ready | 完整复验文件与Intent匹配，再不覆盖发布Ready发现记录；Ready绑定稳定文件／工程身份及提交链锚点，不能只存当前路径字符串 |
| LaterAppend | 同文件后续增量仍须包含Ready锚点且完整验证；发现记录不得迫使每次重写工程。涉及绑定变化则另走Transfer，不假定旧Ready覆盖任意新文件 |
| Restart／IndexLost | 有界枚举固定槽、完整核对已拥有的记录；可发现FileCommitted但Ready缺失的精确待核对条目，不能把它默认为可关闭／已恢复成功 |

文件已提交而Ready失败时保留文件事实和“发现未就绪”状态。协调2必须把文件覆盖与目标可发现性分开：对恢复目标，Close满足还需同目标Ready证据；不能把Committed丢弃来掩盖目录失败，也不能复用binding_conflict假装发现状态已经表达。读取查询只读；完成自己已接纳Intent的Ready需要独立、明确的RepairDiscovery／继续保护资格及保留容量，不在查询中暗写。有效Intent的受控补全与未知孤儿提升分开，前者也须完整验证且可取消。

索引丢失时固定槽发现仍能定位已保管文件；Intent／Ready缺失或损坏时给出该槽精确诊断和后续显式受控验证入口，不宣称已经证明可恢复，禁止扫描任意磁盘或自动相信孤儿。根记录丢失不自动创建空根覆盖旧目录。只清理由当前任务确实拥有且未发布的scratch；发布后的自有临时硬链接别名，仅在正式目标已完整验证、物理身份相同且不会移除唯一有效副本时可解除，失败则保留别名并计占用，不据此清理旧恢复入口。其他清理失败同样保留token、占用与诊断。正式恢复记录、旧完整副本和历史不以容量不足为由删除。

B承诺只到受控进程中断与已验证本地文件语义；目录项断电持久性、物理断电／扇区撕裂及真实介质故障仍须独立证据。sync_all、SQLite同步模式或进程门闩本身不能提升这些结论。

## 7. 共同容量与最后保护资格

先冻结FileCoord-Small-v1，沿用A的小型工作负载并增加真实文件边界；不把各默认常量或10000层旧实验当共同profile证明。下表是拟议初始上限，不是实际RAM测量或已能同时兑现的容量。B1在测试实现中建立逐项计费manifest，**任何生产工作资格启用前**取得对应路径的证明；若无法满足，停止并修订契约，不静默提高上限。

| 资源／范围 | 拟议初始profile／证明要求 |
| --- | --- |
| Session与捕获 | 64节点、128普通回执、每请求16命令；256admissions；8份原字节、总256KiB、单份64KiB；capture metadata1MiB；单状态逻辑128KiB、累计状态逻辑2MiB |
| 持久增长 | 检查点／提交最多128，普通提交至少预留最后一次保护；Manual标记按实际条数计；原操作规范字节总1MiB、标签／扩展原字节总64KiB；每检查点Redo及全部索引分别有界 |
| codec与文件 | 单块256KiB、单状态bundle1MiB／展开2MiB、全准备编码8MiB；文件32MiB／8192块，累计状态闭包8MiB；单状态items／JSON values各8192，深32；实际UTF-8／转义及重复引用展开分别计量 |
