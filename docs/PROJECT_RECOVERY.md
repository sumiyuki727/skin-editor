## 恢复步骤

1. 先取得私有仓库访问权限及另存密钥，阅读其RESTORE.md，按已验证步骤从固定源码bundle克隆到全新目录，核对CommitId和树身份。主仓库固定tag可用于查看源码，但从日后仓库克隆再检出旧tag可能仍保留较新的同名分支引用，不等同于完整原件恢复；不要强制改写这些引用绕过恢复器。私有仓库的同名tag仅标识备份容器，也不是应用源码提交。
2. 从私有发布下载RECOVERY-RECEIPT.json、源码bundle、全部三个历史分卷、local-git加密包及最终恢复脚本，按回执检查每个文件长度和SHA-256。缺卷或散列不符时停止，不覆盖现有项目，也不要尝试修补证据。
3. 使用7-Zip打开首卷，按交互提示提供另存的密钥；不要把密钥粘贴进终端命令或脚本参数。解压到新恢复工作区根目录，使包内artifacts相对路径落到原来的对应位置，不覆盖任何尚未审查的已有工程。
4. 将local-git包解压到同一全新工作区，按RESTORE.md运行RESTORE-LOCAL-REFS.py，再运行VERIFY-RESTORED-v2.py。恢复器仅补缺失引用、拒绝覆盖冲突；校验器分别核对Git提交／暂存树、全部原件字节／时间、引用及历史文件清单。原件中两份研究JSON的既有CRLF／Git LF差异按私有回执保留，不能为“干净工作区”改写证据；schema.rs也可能保留规范化空差异标记。旧v1曾误以为原件与Git字节必须完全一致而停止，不追认其通过。
5. 核对解密清单与逐文件结果，不能只看解压成功或抽查几个文件。冻结程序不因下载而重建，恢复不重新运行成本测量。按私有说明重新绑定主origin及仓库本地hook，认证／作者由所有者配置；密钥、诊断与生成目录不暂存。按README准备工具链及依赖，再使用现有check_core.py／check_desktop.py检查；不从恢复成功推导性能、stable兼容或新平台达标。

恢复密钥应在项目目录之外再持有一份可靠副本。只有密文而没有密钥时，原始材料不可恢复；只有源码克隆而没有全部加密分卷时，也不应宣称已恢复历史测量原件。
