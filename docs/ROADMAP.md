- 每个实际发布平台分别执行 smoke test：导入 → 编辑 → 分叉 → 保存重开 → 导出 → 场景预览 → 游玩 → 返回。先验收 Windows、Linux；macOS 有实机结果后再纳入发布范围。
- 完整记录当前支持元素/玩法、已知差异和未支持功能，README 的命令在干净环境执行验证。
- 分发资源清单逐项检查来源；不得包含 stable 原版默认素材或用户本地皮肤／头像／音乐，未来自制默认皮肤单独验收。

退出条件：R14 发布版本通过；不存在已知项目损坏、分支丢失、静默丢配置或错误导出的阻断问题。功能不足时发布范围较小的预览版并说明范围，不以此宣称最终产品完成。

## 日常开发流程

1. 选择一个具体用例和验收编号；记录涉及模块、数据变化和未知兼容行为。
2. 对基础行为先定义可验证的输入/输出与失败情况；需要调整公开契约或数据格式时先同步设计。
3. 做最小实现，经 Command 进入项目；避免把一次 UI 便利性改动扩成架构重写。
4. 运行受影响层的测试与静态/依赖检查；涉及图形、平台、文件或时序时增加对应验证，说明未测范围。
5. 复查跨模块方向、资源生命周期、历史和修订、旧格式/未知数据、性能及错误恢复；更新功能状态和运行说明。
6. 交付可审查差异和证据；每轮开始按最新AGENTS检查并提交已有可审查工作作为回退点，并同步到核对过的私有origin，用户明确要求不提交／推送时除外。只暂存审查过的路径、通过相关检查与hook，新增工作保留待下轮检查保存，保留无关修改。发现需求超出原范围时先完成独立部分，明确新增范围和依赖。

## 检查能力建设顺序

| 引入时机 | 必须同时建立的检查 | 避免的问题 |
| --- | --- | --- |
| P1 首个语言工程 | 格式、静态检查、无窗口测试、依赖规则、Windows／Linux 构建检查；Linux 实机延期，构建缺少环境时如实记录并补齐，macOS 条件独立记录；保留平台边界检查 | 文档边界落不到代码中 |
| P2 图像与 UI | 合成对照、暂停刷新、输入隔离、基本平台 smoke | 游戏冻结连带编辑器冻结、两套合成行为 |
| P3 文件系统 | 保存/导出故障测试、fixture、schema 迁移检查 | 静默丢数据、历史资源提前删除 |
| P4/P5 兼容与游玩 | 证据关联、场景/时间/输入脚本、真实客户端对照 | 将占位行为或 lazer 行为视为 stable 事实 |
| P6 外部 API | schema/契约、去重、冲突、不同入口一致性 | AI 绕过命令或覆盖用户编辑 |
| 每次依赖升级 | 锁定版本、受影响回归、平台/资源成本复查 | 库升级悄悄改变行为或最低系统要求 |

P1-0 建立核心包检查、真实禁止依赖 canary 和私有访问编译拒绝测试；K1-1已将检查扩展到三个根核心包及桌面禁止边。后续模块／行为继续同步规则与测试。CI 配置尚未远程运行，不能替代平台实测。P0 契约探针仍是独立历史证据。采用明确验收和自动检查降低维护风险，不能承诺未来永远不会出现违规代码。
