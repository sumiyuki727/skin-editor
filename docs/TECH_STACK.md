# 技术栈评估与性能验证

状态：2026-10-20 采纳 Rust 无窗口核心，egui／eframe＋wgpu 为 P2 集成基线；生产低延迟音频后端仍待验收。[P1-0](P1_PROGRESS.md)已建立独立工作区、锁定工具链及检查，无第三方核心依赖。当前选型决定见 [P0 收口评审](p0/P0_EXIT_REVIEW.md)，数值与口径以 [资源预算 v1](p0/RESOURCE_BUDGET.md)为准。版本来自本机已锁定实验，不宣称是上游最新版本或产品最低系统要求。

## 本次选型结论

| 层／组件 | 本次决定 | 理由、成本与重审条件 |
| --- | --- | --- |
| P1 核心 | **采纳 Rust 1.95.0、2024 edition**，domain／application 独立于宿主 | 已有同语言契约与状态机、类型和依赖边界经验；不以无 GC 推导总内存较低。P1 新工程建立工具链锁、检查和规模基线 |
| P2 UI | **egui／eframe 0.37.0 为集成基线**；普通可折叠面板，布局不定稿 | 已有本机键鼠／IME／剪贴板／全屏和中央画布证据；完整布局、不同原生 DPI、无障碍及发布仍需验收。出现关键宿主缺口时重审 |
| 渲染／图像 | **wgpu 30.0.1＋image 0.25.10 的 PNG 子集为基线**，共享合成语义 | 现有锁与 CPU／GPU 像素对照、无回读呈现和标准组合负载支持继续；Vulkan 为本机已测路径，DX12／其他后端不自动继承结果 |
| 媒体解码 | **Symphonia 0.6.1 为候选**，WAV／PCM、可选 MP3／Ogg Vorbis | 已测有限自制文件、定位与取消；真实音乐／特殊容器及分发清单在产品引入前核对。不进入 P1 依赖 |
| 平台音频 | 采纳设备时钟、源格式 PCM、有界队列、代次／显式暂停重建的职责；**生产后端不定案** | Windows shared 转换有证据；100 ms 轮询、阻塞 I/O、系统引擎成本和端到端延迟在 P5 前重审，Linux／macOS 分别验证 |
| AI 控制 | P1 先做可序列化的进程内值契约 | 不接模型 SDK 或聊天面板；外部 CLI／IPC／MCP 后续选择，不重复业务规则或新增跨语言核心 |

决定继续单一 Rust 模块化单体，不启动第二套 UI 原型。C#／Avalonia、Qt、Tauri 目前没有同负载测试，不作性能排名；选中路线出现关键能力缺口或可复用组件收益明确时才重开候选。非开源旧 stable 不提供可复用的 C# 内核或资源。

## 平台与依赖基线

当前仅有 Windows x64 参考机：Windows 10 build 19045、Ryzen 7 4800H／16 逻辑处理器、约 15.87 GiB 内存、RTX 2060／NVIDIA 560.94、Vulkan。该配置说明证据环境，不是最低要求清单；最低 OS、集显／UMA、较低显卡、DX12 fallback 和安装包在正式桌面发布前验证。

Linux 实测按用户要求延期，macOS 待设备；P1 核心不接平台对象，保留适配边界。[egui／eframe](https://github.com/emilk/egui)与 [wgpu](https://github.com/gfx-rs/wgpu)的官方平台覆盖只说明候选路线，不替代本项目实机验收。

本机 eframe 0.37.0 manifest 声明 Rust 1.95，wgpu 30.0.1 声明 1.87，image 0.25.10 声明 1.88，Symphonia 0.6.1 声明 1.85；沿用已可用的 1.95.0 避免未经验证降版。Cargo 的 [`rust-version`](https://doc.rust-lang.org/cargo/reference/rust-version.html)与锁文件分别控制编译器要求和包解析；P1 已建立自己的锁和工具链文件，不让 `.p0-tools` 或实验目录成为产品依赖。当前本机仅将已存在的 1.95.0 二进制目录作为显式工具参数使用，来源路径不写入产品源码、锁文件或构建配置。

P0 当前 Windows／compressed feature 可达元数据为 186 包，其中 182 个 registry 包，其余四个是 publish=false 的本地实验包；这不是正式产品依赖清单。直接组件 eframe／egui／wgpu／image／windows 的本机元数据为 MIT OR Apache-2.0，Symphonia 为 MPL-2.0（亦见[上游](https://github.com/pdeljanov/Symphonia)）。正式引入时按实际 feature 重查传递依赖、平台条件、字体／默认素材及 notices。产品自身许可尚未指定，本轮不添加 LICENSE 或作发布合规结论；本地无窗口核心可继续，首次分发前须决定并核对实际产物。

P1 初始只引入确有需要的核心依赖。UI／GPU／媒体／音频包不进入 P1；不因实验锁里已有就默认批准产品依赖。私有 FFmpeg／libsndfile 仅作离线参考，不进入产品、核心测试或原生播放进程。

## 选型依据与历次实验

以下按实验顺序保留证据与当时未决项，当前决定以上述表格、[范围](p0/PREVIEW_SCOPE.md)和[资源基线](p0/RESOURCE_BUDGET.md)为准。各实验有独立源码／二进制／feature 身份，不能合并成完整产品验收。单一语言支持共用模型、命令、历史与合成语义；不默认引入 Rust＋C# 或 Rust＋Qt 混合核心。

后续[文件与时间线](p0/MEDIA_TIMELINE.md)用默认关闭的 Symphonia 0.6.1 WAV／PCM 适配，把自制短文件接到既有设备输出与只读单击对象时间线；WASAPI 包不依赖解码器，纯时间线不依赖墙钟。只验证了短 WAV 与同采样率／声道输出，压缩音乐、流式／重采样、真实输入延迟及整体预算仍开放；该进展不自动确定最终音频或游玩后端，也没有得到跨平台实测结论。

[有界按需 WAV 解码](p0/STREAMING_AUDIO.md)补上长文件读取的独立证据：三次 180 秒负载的无 GUI／设备进程提交峰值约 0.840–0.844 MiB，同解码器保留整段 PCM 的对照约 66.898–66.914 MiB，全部样本和双向定位通过独立哈希。显式输出／缓存／源缓冲合计 128 KiB，其他解码及分配成本另计；未新增依赖。该批仅测读取，原生接线单独验证，不能据此确定正式音频栈。

[后台原生输出](p0/STREAM_OUTPUT.md)现已用单解码线程及五块池完成三轮十秒连续播放、暂停／定位旧块拒绝、受控欠载冻结和显式恢复。Windows 仍只用既有 bindings／shared 100 ms 轮询，库依赖不变；默认 GUI 不编译解码器。提交峰值约 13.168–13.477 MiB 包含验证记录和 JSON，不与旧纯解码结果直接相减，也不当作图形组合预算。压缩格式、重采样、物理输入及声学延迟、设备切换和正式后端继续开放。

[长时组合](p0/COMBINED_SOAK.md)进一步完成相同版本的两轮五分钟 WAV／WASAPI＋标准 PNG／50 层 GPU 合成，每轮 20 次文档切换、约 1.8 万次命令草稿更新，报告欠载为 0。播放 CPU 约单逻辑核 7.58%，正常采样工作集峰值约 263.4–263.7 MiB，全流程历史工作集约 268.5–270.1 MiB、历史提交约 390.7–395.2 MiB；两段稳定空闲 CPU 均低于 2%。本次可测预算通过，不能当作完整素材库／历史／真实游玩的总预算；私有提交与 GPU 上限未定，GPU 利用率和物理显示延迟未测。更长及真实音乐／系统压力继续开放，不因两个五分钟片段决定正式后端。

[重复资源寿命](p0/RESOURCE_CYCLES.md)另完成同版本两组各 20 次文档／解码／原生流打开、编辑、暂停和关闭，所有 PCM 池归还，报告欠载为 0；最终约 64 秒空闲 CPU 分别约单逻辑核 0.049%／计数未增加。关闭基线私有提交首尾增加约 2.60／2.13 MiB，前后五轮中位数差约 0.55／1.13 MiB，GPU dedicated 基线未增长。组件回收行为及本次预算通过，但少量保留尚未精确拆分；该组没有同时保留两个文档，不能与五分钟切换峰值相减来宣称优化或无泄漏。正式栈与完整产品预算仍未定案。

[压缩音频首轮](p0/COMPRESSED_AUDIO.md)与[独立 Ogg 续篇](p0/VORBIS_TAIL_AND_SEEK.md)验证默认关闭的 MP3／Vorbis 读取与后台原生输出。独立 libsndfile 和相同音频包的 24 个分页／边界控制，已将短 Ogg 差异定位到固定 FFmpeg 7.1 参考的单音频末页路径，无裁切或补偿。Vorbis 准确定位后，180 秒文件半程离线跳转约 0.33–0.35 ms、原生 90 秒数据预备约 22.4–42.0 ms；当次六轮原生报告欠载为 0，Vorbis 原生私有提交约 14.9–18.1 MiB，含设备和诊断，不是图形组合预算。MP3 仍使用前缀路径，当次原生 90 秒预备约 119 ms；后续[取消交接](p0/MP3_CANCELLATION.md)将前缀工作拆步，由组装层检查代次，未将总定位成本视为已解决。未新增 Cargo 包或扩充平台 API；私有 libsndfile／FFmpeg 只作离线工具，核心测试依靠冻结参考。真实音乐／非零起点／链式流、MP3 总定位成本及阻塞 I/O 取消、重采样、物理输入／声学延迟、跨平台及完整预算继续开放，未定案正式后端。

[同源压缩与图形组合](p0/COMPRESSED_COMBINED_SOAK.md)补齐六轮各五分钟的组件级长时证据：同一压缩构建、标准 PNG／50 层活动文档、持续草稿及每轮 20 次切换，180010 个接受包全部核对，欠载／解码失败为 0，54 项既有预算检查通过。播放 CPU 为单逻辑核 8.20–8.67%，正常采样工作集峰值 256.11–267.13 MiB，CPU 帧 p95 0.981–1.020 ms，稳定空闲低于 0.025%。正常私有提交峰值 388.59–394.45 MiB，后段窗口末值约 295–298 MiB，关闭后约 196–200 MiB；与 GPU 指标分开记录，播放 CPU／提交／GPU 尚无正式数值上限。MP3 轮次有孤立长帧，最大 CPU 帧 64.761 ms、框架回调间隔 86.999 ms，未作因果归因。该子项已收口，不据此声称完整产品、严格 60 Hz、声学低延迟或跨平台已通过；优先明确重采样／声道转换、设备变化及预览路线后再定案，避免无限重复相同负载。

若第一个原型暴露主要是桌面控件/平台交互问题，且 .NET 方案没有可复用预览收益，可用 Qt 候选替代第二原型。最多比较两个有代表性的原型，不同时维护四套产品实现。

[源格式与设备变化](p0/AUDIO_ADAPTATION.md)验证 Windows 可选 shared 引擎转换路线，源 PCM 池与设备混音格式分开；旧严格入口仍拒绝不匹配。十六轮覆盖 32／44.1／48／96 kHz 及单／双声道源，实际混音均为 48 kHz 双声道；11517 个接受包完整核对，欠载为 0。一次真实模拟耳机插拔返回 AUDCLNT_E_DEVICE_INVALIDATED，接回后重建保持原位置暂停，显式播放后继续；听感未确认。播放阶段本进程工作集约 8.77–10.63 MiB、私有提交约 4.32–6.30 MiB，短段 CPU 计数未增加至单逻辑核 0.684%，两个长空闲轮通过既有门槛。系统共享音频服务成本及转换后采样未计入，无图形负载，不与前轮峰值相加。无新依赖／绑定 feature／线程，轮询和 100 ms 缓冲仍为 P0 限制；转换接口与低延迟后端、未测硬件及平台分别验收，不自动定案正式音频栈。

## 候选比较

表中的“预期”是工程判断，不是基准测试结果。团队对语言和图形栈的实际维护经验也是选型输入，目前未知。

| 候选 | 与本项目相关的能力/预期 | 必须验证的成本 | 当前定位 |
| --- | --- | --- | --- |
| Rust + egui/eframe + wgpu | egui 提供原生即时模式 UI 与 wgpu 集成；可用单一语言表达命令、历史和渲染边界 | 完整面板、不同原生 DPI、无障碍、产品预算与升级；已有本机输入／合成证据 | Rust 核心采纳；P2 UI／图形基线，集成待验收 |
| C#/.NET + Avalonia；按需评估 osu!framework | Avalonia 提供三大桌面平台 UI；与 osu!framework 同语言，有潜在的游戏组件复用路径 | 是否真的能复用必要行为、图形表面与输入/音频整合、GC 停顿及资源驻留、最低系统与平台支持层级 | 有实际复用收益时作为第二原型 |
| C++ + Qt 6 / Qt Quick | 官方支持三大桌面平台，Qt Quick 场景图及 RHI 提供跨图形 API 路径 | 团队 C++/QML 维护能力、图形整合与内存所有权、部署、使用的具体模块和许可条件 | 桌面交互优先时的替代候选 |
| Rust + Tauri + Web UI | Web UI 便于面板开发；Tauri 使用各平台 WebView | WebView/图形共享或像素复制、平台差异、多进程总内存、复杂画布及游戏输入延迟 | 暂不优先，团队或实测有收益再考虑 |

上述框架能力可在官方资料核对：[egui](https://github.com/emilk/egui)、[Avalonia 平台支持](https://docs.avaloniaui.net/docs/supported-platforms)、[Qt 平台支持](https://doc.qt.io/qt-6/supported-platforms.html)、[Qt 图形架构](https://doc.qt.io/qt-6/topics-graphics.html)、[Tauri WebView](https://v2.tauri.app/reference/webview-versions/)。Tauri 在 Windows 使用 WebView2，在 macOS/Linux 使用 WebKit 系列组件，因此不能把某一平台的测试直接视为所有平台结果。

没有选择 Electron 作为首轮原型，是为了缩小比较范围并优先验证原生画布路径，不是已经证明它无法满足资源预算。同样，不因 Rust 没有托管 GC 就认定总内存一定更低；纹理、解码图、缓存和历史数据更需要测量。

## 预览实现路线的决策点

| 路线 | 能提供什么 | 不能先行假定什么 |
| --- | --- | --- |
| 用户提供的非开源旧 stable 源码 | 只读定位历史行为、耦合及待测问题 | 不作为可接入内核或 C# 复用收益，不复制/移植，不代表当前行为 |
| 自建 stable 兼容预览 | 能按编辑器需求设计暂停、素材刷新与交互接口 | 高精度布局、谱面/音频/判定需要持续验证，不能低估为普通图片预览 |
| 复用 osu!framework / lazer 的部分组件 | 有候选图形、输入、音频或玩法实现可研究 | 不等于 stable；与桌面框架共用窗口、时钟、GPU 和资源的成本未知 |
| 调用用户安装的 stable | 真实输出验证、外部游玩测试 | 不能替代内置可编辑场景，也不假定能控制其时间或实时刷新 |

官方 [ppy/osu README](https://github.com/ppy/osu/blob/master/README.md)将该仓库定位为 lazer。用户提供的本地旧 stable 快照已完成部分只读研究，其版本与当前行为尚未对齐；它不增加任何候选技术栈可直接复用的产品代码。主线采用独立兼容实现，来源索引与研究边界见 [P0 报告](p0/REPORT.md)。

[osu!framework 的官方说明](https://github.com/ppy/osu-framework)提供跨平台框架信息，并单独提示 BASS 音频依赖的使用条件。[Qt 官方许可说明](https://doc.qt.io/qt-6/licensing.html)也区分不同模块和分发选项。选择复用组件前应清点实际代码、资源及依赖条件；不能仅凭主仓库采用 MIT 或某框架支持桌面平台就认为完整产品的分发和平台问题已经解决。

## P0 原型必须包含的真实负载

不能只测空窗口，也不需要先造完整编辑器：

1. 相同的自制 PNG 集合、嵌套图层合成参数和透明度；固定中央画布尺寸与 60 Hz 测试设置。
2. 资源列表、缩略图、图层列表、一个参数输入区；能拖入素材并修改变换。
3. 一个独立模拟时钟与简单动画；暂停后改素材，像素更新而动画时间保持。
4. 开始/结束一次拖动只提交一个事务，取消能还原；后台解码结果不会覆盖更新的请求。
5. 中文/日文路径与输入法、高 DPI、缩放、窗口失焦、文件拖入和全屏返回。
6. 关闭窗口和连续打开/关闭资源后检查 CPU/GPU 内存；静止暂停时按需刷新。
7. 对候选游戏组件做小型音频/时钟/输入验证，确认能由外部编辑控制暂停与素材替换；记录能复用和仍需实现的内容。

原型只用于验证选择，不将未经验证的 stable 布局、判定或文件规则变成产品常量。

## 初始性能预算（待 P0 校准）

这些数字是讨论与验收的初始目标，不是当前性能，也不是未经实测的发布保证。P0 记录参考硬件、系统、显卡/驱动、分辨率、构建模式、数据集与采样方式后再定正式阈值；调整必须说明原因，不能悄悄放宽。

当前数值、负载、口径与阶段门槛统一维护在 [资源预算 v1](p0/RESOURCE_BUDGET.md)。保留空闲 200 MiB、标准工作集 512 MiB、空闲单核 CPU 2%、CPU 帧 p95 16.7 ms 和已解码编辑到 GPU 完成／回读 p95 50 ms 的原目标；新增私有提交、GPU、组合 CPU 上限标为待测。以下历史数据不回填为新预算通过。

首次解码、磁盘导入、导出和真实游玩负载分别测量，不混入已解码交互指标，也不能省略它们的耗时。真实 stable 外部进程资源单列，同时报告整条工作流总资源。内存比较尽量使用各平台一致口径；必须列出 OS 指标差异，不能只比较主进程数字。

候选 GUI 的性能脚本和负载 fixture 在原型阶段加入仓库。现有 P0 契约探针只验证合成输入变化、时钟与刷新控制，不测 GUI/GPU/真实音频，也不用于上述预算排名。优先做可重复采样，避免用单次“感觉流畅”作为选型依据。

原生候选现已提供 `python tools/check_p0_gui.py --run-standard`：自制 100 张 PNG/10 文档/500 层，300 次脚本变换及 GPU 回读、60 秒暂停、20 轮资源切换。它只包含平移、等比缩放和继承 opacity，不包括正式事务、隔离组合成、实际拖动或音频。回读会增加框架绘制及复制成本，实际编辑间隔另列；CPU 帧耗时与编辑到 GPU 回读延迟已测，独立 GPU 时间戳仍未测。进程工作集、私有字节、GPU Dedicated/Shared 和缓存 payload 分开，不因工作集通过就认定整体资源成本已可接受。

后续的[同素材对照](p0/RESOURCE_COMPARISON.md)补齐了无回读成本与关闭后 60 秒观察。无回读时 CPU 帧 p95 约 1.2 ms；MemoryUsage 在本机降低了 GPU 驻留和保留容量，但未降低本次工作集峰值，加载私有提交仍高。回读使编辑阶段单核 CPU 开销明显增加。该提示只是后端可选参数，部分平台可能忽略，不因本机结果决定产品栈、GPU 总预算或跨平台默认值。

[后台加载对照](p0/ASYNC_LOADING.md)进一步验证了元数据后台读取、单线程 PNG 解码、旧代次结果丢弃与每帧两张/8 MiB 上传限制。无回读加载 CPU 帧 p95 约 111.8 → 2.74 ms、私有提交采样峰值约 843 → 739 MiB；但加载阶段总 CPU 均值上升，最长帧仍约 21 ms。整体低资源目标、完整合成和跨平台门槛保持开放，不将实验队列直接作为正式导入/Command 实现。

[加载 CPU 与提交峰值诊断](p0/LOADER_TUNING.md)验证了合并通知＋两项预取可减少约 11.7% 样本 CPU 工作量，但文档等待增加、提交峰值略升，尚不作为产品默认值。路径消减中，停用原图绘制仍有高提交；停用原图 GPU 上传后显著下降，且原图存活像素相同。调查已缩小到原图 GPU 资源／上传生命周期，仍未精确区分上游临时分配、堆保留和驱动。页面分类、wgpu reserved 与 PrivateUsage 不能混为一个计量。

后续 [GPU 上传记录](p0/GPU_UPLOAD.md)补充 Rust 请求统计、逐轮 GPU 等待、纹理槽复用、后端与堆事件对照。完整无回读对照中，80 MiB GPU 纹理池将提交采样峰值约 691 → 615 MiB、GPU Dedicated 约 242 → 162 MiB，文档完成 p95 增加约 12.5 ms；CPU 原图预算、分辨率和绘制内容保持相同。活跃 staging 约 8 MiB，不能独自解释提交增量；原生堆／驱动／外部图形层仍有未归因部分。带回读诊断的峰值也受同步节奏影响，不挑选最低诊断值作为预算或据此确定技术栈。可选分配统计只用于诊断构建，默认运行不承担计数成本。

最新[三次重复验证](p0/ALLOCATION_ATTRIBUTION.md)中，80 MiB 的提交峰值为 545.9–617.2 MiB，循环加载 p95 为 92.6–94.6 ms，未重现首轮单测的固定延迟代价；128 MiB 复用组也有明显提交波动，不能声称容量越小总峰值就一定越低。独立 Vulkan API 诊断看到约 128 MiB 显存申请所伴随的提交／PRIVATE 区域，以及显存释放后三秒检查点的回收；关闭 OBS 隐式层没有消除它。仍未取得完整程序的直接虚拟分配调用栈或干净 NVIDIA 覆盖层对照，正式默认值保持未定。

[完整流程寿命收尾](p0/UPLOAD_LIFETIME.md)进一步观察到纹理清除后约三秒的百 MiB 提交回落。有界上传候选虽将 GPU 峰值约 162 → 154 MiB，修正通知后仍增加循环 CPU，提交量也无稳定收益，保持现有默认路径。性能与回读／时间线诊断分别运行，驱动内部未知量不阻止转入其他 P0 门槛验证。

[合成原型](p0/COMPOSITION.md)已验证小型仿射、隔离组与透明采样；[标准扩展](p0/COMPOSITION_SCALE.md)进一步顺序合成全部 10 文档／500 层，每文档 1024²、50 层。两次 GPU 温热 p95 为 5.530／5.513 ms，最大通道差均为 1／255；CPU 参考约 1.5 秒／文档，不能当作实时路线。约 48 MiB 显式缓冲不含驱动等总成本；300 次派发复用静态计划，尚未验证持续编辑与呈现组合成本，不据此定案 compute 后端。新增直接引用的 pollster 复用现有锁定版本，不新增第三方包版本。

[连续编辑](p0/EDIT_COMPOSITION.md)已将同一 egui 控件／命令会话路径接入 50 层文档的 GPU 合成和直接纹理呈现；两次逐次界面回读 p95 为 9.377／9.724 ms，像素与显示适配最大通道差均为 1／255。普通路径没有 CPU 像素往返；测得的 host 处理时间不等于完整帧时间。初次加载仍同步，物理输入、IME、DPI／全屏及完整资源预算待验证。

[音频诊断](p0/AUDIO_DEVICE.md)已实际打开默认 WASAPI shared 输出流，三次静音测试的暂停位置跨度均为 0，恢复后继续前进且不补跑。该批只验证独立流，未连接编辑器模拟／输入；它是 Windows 平台能力证据，不是跨平台音频库选型、可听延迟或实际游玩验证。仅使用标准库和公开 ABI，没有新增产品依赖。

后续[同进程联动](p0/TRANSPORT.md)已连接设备位置、模拟／输入门控与 GPU 编辑：三轮均在约 8.5 秒暂停中完成 300 次变换、取消／单次提交，设备位置跨度及恢复首读增量均为 0。新增可选 Windows 适配器直接复用锁定树中的 `windows 0.62.2`，无新第三方包版本；仅平台文件允许原生 unsafe，UI／纯逻辑继续禁止。一个工作线程、8 项队列、5／100 ms 轮询与 100 ms 缓冲是能力实验成本，不是低延迟方案或待机预算成绩。后台接入还需保留 straight 像素／隔离组并限制 GPU 上传；不能直接复用旧 UI 缓存和展平文档。可听输出、物理输入、设备恢复和跨平台门槛保持开放。

[后台合成交接](p0/ASYNC_COMPOSITION.md)进一步以新原始 RGBA 结果接入同一合成器，单工作线程和有背压的结果通道限制在途工作；旧视图保持至候选上传及 GPU 首帧完成。每帧两张／8 MiB 是源写入限额，整块 GPU 缓冲申请／清零、暂存和驱动另计；最坏可同时保留三组 CPU 原图 payload，不能照搬旧纹理池成绩。新实验不新增依赖，不与真实音频流共享切换入口；完整资源预算及 Linux 实机门槛仍开放。

后续已定位加载长帧的主要来源为首次 pipeline API 创建约 52–55 ms。一次性后台预热／复用候选在同版本两次诊断中将最大框架 CPU 帧约 52–64 ms 降至约 19 ms，预热本身仍约 56–59 ms，首文档约 185–191 ms；剩余启动成本与完整预算保持开放。该候选显式选择，不改变正式栈或原有默认路径。[共享音频与后台切换](p0/SWITCH_AUDIO.md)另完成三轮真实静音流的冻结、编辑、恢复及关闭验证；尚无可听低延迟、物理设备恢复或 Linux 实测结果。

[静音流重建](p0/AUDIO_RECOVERY.md)新增不依赖 UI／原生 API／墙钟的音频端口，Windows 通过专用线程显式释放、重开自有流。三轮各两次重建保持冻结位置，故障中编辑与像素保留通过；失败开流与阻塞清理使用无窗口 fake stream 回归。复用既有一个线程和 8 项控制通道，无新第三方依赖或 unsafe。它没有 PCM 定位、物理设备切换、声学延迟或 Linux 后端，不能据此定案低延迟游玩库。

[后续 PCM 实验](p0/AUDIO_PCM.md)显式提交自制非零 float32 音调，并将内容起点纳入流替换端口。定位与故障恢复先打开暂停的新代次，普通暂停保留原队列；模拟仍消费设备位置，提交前沿单独计量。原生写入新增在既有平台文件内，依赖／feature／线程数未增加；单／双声道、每包至多 1 MiB。本机一次用户确认提示音可听、暂停恢复正常，未测声学延迟；没有音频解码／重采样／混音和谱面解析，不能据此关闭整个游玩可行性门槛。

## 资源成本控制策略

- 原始压缩字节按内容共享；同图多实例不重复解码。一个 1024×1024 RGBA8 解码平面约 4 MiB，不能用源 PNG 文件大小估算运行内存。
- 资源目录先读元数据与缩略图，原图按需解码。缩略图、CPU 解码图、GPU 纹理和合成结果分开计量并设置上限。
- 初始可用 CPU 解码缓存 128 MiB、GPU 纹理缓存 128 MiB 作为实验参数；中间纹理、场景缓冲和当前活跃纹理也计量，不能假装它们都属于这两个上限。
- 历史只记录必要的参数变化与资源引用，不为每个节点复制整套像素。历史可达字节存储与可随时重建的内存缓存分开。
- 仅重算受影响文档/组；暂存预览和已提交渲染分别标识，过期工作可取消。无变化的暂停场景不循环重画。
- 解码、导出与缩略图使用有界工作队列，不把每个素材都同时解码上传；限制尺寸和资源占用时给出明确错误。
- 不因早期微基准引入线程池框架、复杂持久化结构或跨进程复制；先定位实际热点。

## 分阶段的选型与验收条件

P0 的记录至少包括：候选版本与锁定方式、Windows 的构建和实际运行结果、Linux／macOS 的延期状态及适配边界／未来验证项、基准数据、交互缺陷、预览演进可行性、依赖与分发条件、团队维护成本，以及未解决的问题。Linux 实测延期允许先形成 Windows 范围的候选结论，跨平台支持须待各平台实际验证。

以下是后续集成与能力声明的门槛，不能靠综合分数掩盖，也不应全部前置到不使用 UI、图形或音频的 P1：

- 在声明支持的目标平台上实测，并建立最低系统／图形要求；当前参考机不代表最低配置，未在实机验证的平台标记未验证，不能仅用交叉编译代替。
- 暂停和素材刷新能够独立控制，游戏输入与编辑器输入可隔离。
- 中央画布与图层合成语义可和导出统一验证；不需大批量逐帧复制像素才能实现基本交互。
- 输入法、字体、高 DPI、文件路径与基本桌面交互在预定支持范围内可用。
- 有可解释且可接受的资源成本和依赖升级路径，能够维持模块边界与无窗口测试。
- 实际游玩路线可行，或有明确、可审查的剩余验证项；不能只选择 UI 最容易的方案后把核心目标无限后移。

本次已据有范围的实验、资源数据和维护边界采用 Rust 核心及 P2 桌面集成基线；未测的第二候选不作性能排名。正式 UI 的交互／预算在 P2/P3 验收，实时音频与实际游玩在 P5 验收，其他平台在各自支持声明前验收，具体阻断位置见 [P0 收口评审](p0/P0_EXIT_REVIEW.md)。关键缺陷触发相应层重审，不能隐藏到后期。正式工程落地后在 README 中加入真实安装、启动、测试命令。
