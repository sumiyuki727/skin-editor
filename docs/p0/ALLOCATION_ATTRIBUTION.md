# 驱动路径、虚拟分配与纹理池重复验证

测量于 2026-10-18，整理于 2026-10-19。延续 [GPU 上传实验](GPU_UPLOAD.md)，使用同一默认 release 构建重复常规负载，并另设无窗口 Vulkan 分配诊断。P0 仍进行中，技术栈、正式缓存容量和兼容内核均未定案。

可复核摘要见 [windows-allocation-attribution.json](windows-allocation-attribution.json)。本轮确认了显存申请所伴随的私有虚拟区域与延迟回收路径；仍未获得完整程序中每一次直接虚拟分配的调用栈，不能把全部差额归给某个驱动或覆盖层。

后续已补充[完整加载流程的寿命对齐与有界上传对照](UPLOAD_LIFETIME.md)，并开始[独立图层合成验证](COMPOSITION.md)。下文保留为本批三次重复与 API 诊断的历史记录，不将其峰值范围作为所有后续构建的保证。

## 测量范围

常规组按三个顺序块执行：新建 128／复用 128／复用 80；复用 80／新建 128／复用 128；复用 128／复用 80／新建 128。每种配置有三个独立进程，各占一次块内位置。全部使用真实 PNG、MemoryUsage、Vulkan、合并通知、两项预取、每帧两项／8 MiB 限额和 128 MiB CPU 缓存。

每次保留 300 次脚本编辑、200 次循环加载、60 秒暂停及关闭后 60 秒观察。没有堆追踪、页面扫描或 GPU 回读；启动约两秒时只记录一次模块元数据。没有并行运行其他 GPU 诊断；原始数据来自自有测试进程，不采集其他应用的画面。Rust 源码、锁文件、测量脚本、exe 与 PDB 在批次开始时固定，逐次核对身份，输入的 201 个文件逐次校验。

文档加载延迟指请求到纹理全部排队，尚未包括 GPU 完成或显示呈现。每次 p95 仅取本次 200 个循环文档，排除初次加载和快速切换完成项；不把三次实验合并成 600 个独立观测，也不以三个样本估计可靠置信区间。

## 分配诊断方法

另一个 Python 标准库工具通过 Windows x64 的 Vulkan 1.0 公共 ABI，依次创建实例／设备、申请 80／128 MiB 非 HOST_VISIBLE 的 DEVICE_LOCAL 内存、释放、申请并映射触写 8 MiB HOST_VISIBLE／COHERENT 缓冲，最后释放并销毁设备。分别比较 16 MiB 内存块和独立 1024² RGBA8 图像；记录真实 memory requirements、内存类型与堆，找不到指定类型时失败，不悄悄换类。

默认与 `VK_LOADER_LAYERS_DISABLE=~implicit~` 分别启动独立子进程，三轮交替前后顺序。父进程在每个 API 检查点等待子进程确认，仅读取自己的子进程计量、模块清单和虚拟页面元数据。另设显式 `VirtualAlloc` 64 MiB／释放对照，验证已知地址范围的识别；不读取页面内容。

这个诊断没有窗口、PNG、wgpu、着色器、绘制或队列复制，因此能检验显存申请本身是否伴随提交成本，但不能代表实际上传／编辑性能。检查点差值包括 loader、图形层、驱动与系统活动，并不是纯驱动的逐字节账本。图形模块存在只说明被载入，不证明正在录屏或覆盖绘制。

`MEM_COMMIT` 的 PRIVATE／MAPPED／IMAGE 页面分类与进程 PrivateUsage 分别保留；区域大小、显存申请量和进程提交量不能相加或互相替代。地址扫描不是原子的，前后两次进程样本与完整性标志一起记录。[Microsoft VirtualQueryEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualqueryex)、[进程内存计数](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)及 [Vulkan 内存规范](https://docs.vulkan.org/spec/latest/chapters/memory.html)分别定义这些接口，不提供本机驱动成本的自动归因。

没有启用全局 VirtualAlloc 内核追踪。公开文档中的 System Memory Provider 属于系统 logger；通用 PID enable 过滤也不自动等于对内核来源事件的目标进程过滤。本轮未验证可靠的单 PID 虚拟分配调用栈采集，改用已知申请与 API 边界对照，不把事后筛选全局日志描述为采集范围隔离。参考 [System Providers](https://learn.microsoft.com/en-us/windows/win32/etw/system-providers)、[EVENT_FILTER_DESCRIPTOR](https://learn.microsoft.com/en-us/windows/win32/api/evntprov/ns-evntprov-event_filter_descriptor)。

## 已定位的成本与回收时序

十二组分配对照为两种申请方式 × 默认／关闭隐式层 × 三次。显式 64 MiB VirtualAlloc 对照中，已知地址范围恰好被识别为 64 MiB committed PRIVATE，释放后进程提交回到基线。它验证了页面分类与释放观察，不提供未知区域的调用者。

| API 路径，均相对于设备已创建 | 默认环境提交增量范围 | 关闭隐式层提交增量范围 |
| --- | ---: | ---: |
| 五块 16 MiB，共 80 MiB DEVICE_LOCAL | 80.191–81.566 MiB | 80.312–81.066 MiB |
| 八块 16 MiB，共 128 MiB DEVICE_LOCAL | 128.285–129.660 MiB | 128.406–129.160 MiB |
| 20 张图像，共 80 MiB 实际申请 | 81.270–83.254 MiB | 80.875–83.852 MiB |
| 32 张图像，共 128 MiB 实际申请 | 129.430–131.398 MiB | 129.004–132.000 MiB |

16 MiB 块组从 80 增到 128 MiB，六次都额外增加约 **48.094 MiB** 提交，其中页面分类约增加 48 MiB PRIVATE；图像组略有额外元数据成本。没有 PNG、wgpu staging、着色器或绘制也会出现这个量级，因此上传临时像素不是这条成本路径的必要条件。该结论限于本机 Vulkan API 路径，不能直接解释完整应用的数百 MiB 差额。

关闭隐式层后 OBS `graphics-hook64.dll` 消失，NVIDIA `nvspcap64.dll` 与 `NvCameraAllowlisting64.dll` 仍存在。实例创建相对 loader 的提交增量约 38.3–38.6 MiB，接着创建设备约 17.4–17.6 MiB；移除 OBS 隐式层没有消除约 128 MiB 的资源申请成本，不支持 OBS 是该成本主因。仍没有无 NVIDIA 覆盖层的干净对照，不能把这些值全部称为纯驱动成本。

最初的短检查点发现 vkFreeMemory 后提交量不降；随后增加四组 3 秒观察及两组缓冲释放观察。以下为追加观察中的关闭隐式层、16 MiB 块组，单位 MiB：

| 检查点 | 进程 PrivateUsage | GPU Dedicated |
| --- | ---: | ---: |
| 设备创建完成 | 65.320 | 4.750 |
| 申请 128 MiB 后 | 193.855 | 132.973 |
| 释放显存后的短检查点 | 193.855 | 4.750 |
| 再等待 3 秒 | 65.320 | 4.750 |
| 申请并映射触写 8 MiB 上传源缓冲 | 73.320 | 4.766 |
| 释放缓冲并再等待 3 秒 | 73.320 | 4.750 |
| 销毁设备／实例并再等待 3 秒 | 32.703 | 0.000 |

六组延长观察都看到显存申请对应的约 128–130 MiB 提交在 3 秒后的检查点退回设备基线附近，页面元数据也同步减少。**显存计数下降、提交页回收和 API 对象销毁不是同一时点。** 没有测得准确释放延迟，不能断言恰好需要三秒，或称这些页为持续泄漏。

8 MiB 上传源在无等待组能复用先前已申请的 PRIVATE 地址范围，没有额外提交增长；显存释放并等待后再创建它，则明确增加约 8 MiB。映射触写没有再次增加提交，不代表上传缓冲免费。两组追加观察中，这 8 MiB 增量在释放后三秒仍保留；最终总提交仍高于 Python 基线约 23 MiB，未逐字节区分其堆保留、模块私有页与原生缓存。此处没有执行 GPU 复制，不能拿它代替实际上传测量。

## 堆证据与仍未归因的部分

为一个自建 Vulkan 子进程在阻塞的初始检查点开启独立命名、单 PID 的 HeapAlloc／HeapRealloc 会话，在加载 Vulkan 前开始，finally 中只停止该会话。关闭隐式层运行，无事件或缓冲丢失。模块清单取各检查点并集，解析时区分 NVIDIA 驱动与覆盖层。

该记录观察到堆请求峰值约 **5.720 MiB**，其中 NVIDIA 已识别栈的独立存活采样峰值约 **5.074 MiB**，未知约 **0.226 MiB**；未出现大小匹配 16 MiB 块的 HeapAlloc。与此同时，API 检查点及地址扫描仍看到约 128 MiB 的提交增长。这支持“存在常规堆请求记录未覆盖的独立 PRIVATE 虚拟区域”这一解释，但没有直接 VirtualAlloc 调用栈，不能把未记录到的字节机械相减后标成驱动。驱动私有分配器、系统图形内存机制与 NVIDIA 覆盖层内部还未分开。

复核上一轮原始 ETL 发现，移动 realloc 会发出内部 Alloc／Free 和完成事件。解析器 v2 合并重复完成，保留已识别的新块来源；新增回归测试。两份记录分别合并 19805／19997 个完成事件，地址碰撞从相同数量降为零，请求峰值保持约 141.1 MiB。旧版摘要保留，修正结果另存。未知存活采样峰值仍约 84.0／88.0 MiB，没有因修正解析器就获得新归因；已识别的 NVIDIA 小额栈也不代表驱动总量。

本轮把资源容量、API 申请成本、显存释放后的短时虚拟区域保留与上传缓冲的复用分别观察到了；**仍未建立完整程序峰值的逐字节分解**。下一步应把这些寿命与完整程序的纹理／提交时间线对应，验证具体限流或回收方案，并在可确认图形层状态的另一环境复测。不通过频繁重建设备、强制压堆或清空工作集制造低值，也不把 80 MiB 固定为正式产品默认值。

## 复核入口

先生成一个新的自制数据集目录，再执行重复常规负载；同名 fixture 不覆盖：

```text
python tools/p0_workload.py artifacts/p0/gpu-fixture
python tools/p0_gpu_repeats.py --fixture artifacts/p0/gpu-fixture
python tools/p0_vulkan_memory.py --repetitions 3
python tools/p0_vulkan_memory.py --settle-seconds 3
```

前两项使用已有原生实验依赖，最后一项只需要 64 位 Windows Python 与已有 Vulkan loader／驱动。新增工具无第三方依赖，不修改用户的 OBS、NVIDIA、注册表或系统环境；隐式层开关仅传给对应子进程。工具不是产品接口，不向 domain／application 引入平台依赖。
