# 后台原图、候选合成与文档交接

2026-10-19，P0 将标准 fixture 的后台加载接入隔离组合成与原生呈现。当前优先 Windows、Linux；本批只在 Windows x64／Vulkan 实测，Linux 待有环境，macOS 延后至具备设备。本实验仍不是正式项目模块或 stable 内核。

## 实现边界

```text
最新文档请求 → 单工作线程：元数据、完整组树、straight RGBA 原图、计划校验
                           ↓ 有背压的带代次结果
旧活动视图 ← 保持显示    候选源缓冲：每 egui 帧最多 2 张／8 MiB 原图写入
                           ↓ 全部上传、首帧 GPU 合成、完成回执
                    匹配最新请求才替换活动视图
```

`composition_fixture` 提取共用只读元数据与 PNG 解码路径，不经过 `ColorImage` 预乘缓存或旧 `Workload::flatten`。原始 straight RGBA（包括透明像素内的 RGB）保留至合成器；嵌套组、共享素材索引、采样和变换使用既有 CPU／WGSL 计划语义。同步入口也通过同一文件适配器读取，没有建立第二套合成规则。

`composition_loading` 使用一个线程、一个最新请求槽、一个零容量结果通道。新的排队请求替换旧请求；PNG 开始前、每张完成后和交接前检查代次。结果接收前工作线程不能开始下一文档，取消不会抢占正在执行的 PNG／文件调用。公共查询不提供可变项目引用，工作线程不依赖 UI／GPU。刷新回调只传递唤醒信号。

逻辑取消不代表物理工作结束：即使当前请求已清除，仍跟踪工作线程 busy 状态并轮询回收旧结果。发送前通知与 UI 接收可能交错，不能只依赖一次唤醒。Drop 先断开接收端，再通知退出并 join，解除结果发送的背压；操作系统 I/O 的强制中断和退出上界尚未验证。

`PreparedPlan` 不暴露未完整上传的可派发计划；`PendingComposition` 在 GPU 上合成首帧并等待回执。`DocumentSwitch` 管理只读派生视图的代次和交接，不拥有项目、Command 或历史。当前过期 GPU 候选仍完成剩余源上传和首帧合成、收到回执后丢弃，再准备下一候选；没有提前停止尚未提交的上传。这样限制同时存在的 GPU 候选数，但可能多写入一份 40 MiB 并增加最新请求等待，后续可按回执细化提前退休。原活动视图不会被旧候选替换。错误或取消保留旧图，关闭解除活动绑定并排空旧任务。实验切换入口取消旧文档的未提交手势，每文档使用独立手势拥有者；不是正式多文档或持久历史实现。

## 资源与计量口径

每文档 10 张 1024² 原图（40 MiB）、50 层与 1024² 输出，来自既有 100 原图／10 文档／500 层 fixture。单 GPU 候选分五个 egui 帧上传源数据，限额按全局帧号共享，重复调用和候选交替不能重置当帧余量。

此限额只约束显式原图写入字节和次数，不限制源缓冲的整块申请／安全清零、操作参数、输出纹理、GPU 合成、驱动分配或暂存保留。没有声称整个加载帧最多 8 MiB 总成本。当前 GPU 计划仍申请约 48 MiB 显式缓冲及 4 MiB 显示纹理，候选与活动文档同时计量；正常呈现没有 CPU 像素回读。

最坏原始 CPU payload 可同时包括活动文档、GPU 候选和一个较新的工作线程结果，共 120 MiB；PNG 解码／格式转换、单张上传打包、元数据、框架和驱动成本另计。没有复用旧 80 MiB 纹理池或 128 MiB CPU 缓存，不能把过去的池预算当作本路径上限。历史原始字节与这些可重建派生缓冲是不同寿命，本实验没有历史资源回收行为。

请求耗时只包围发出后台请求；文档完成耗时到合成可用并交接，包括调度、磁盘、解码、分帧上传和 GPU 回执，不是解码微基准。eframe 的上一帧 CPU usage 单列，不等于显示器端到端延迟。原生脚本的完成延迟按目标约 60 Hz 的请求刷新采样，不以不受控忙轮询压低成绩。

## 验证方法与入口

```text
python tools/check_p0_switch.py --fixture artifacts/p0/gpu-fixture
```

fixture 须已生成且哈希有效；本轮实际复用 `standard-fixture-2cb51994`。自动入口仅在 Windows 计量，使用自有 Vulkan 窗口；顺序运行一个像素诊断和两次无像素诊断的完整观察。`--smoke` 只执行像素诊断，不提供待机预算。构建、无窗口测试、格式和 Clippy 通过后才打开窗口。

脚本首次后台打开文档 0 → 文档 1 已准备 GPU 后改请求文档 2 → 检查 1 不成为活动视图 → 取消文档 3 → 请求缺失 fixture 并保留 2 → 顺序重新读取／切换 20 次（两轮遍历全部文档）→ 静止 → 关闭。未读取用户资源或 stable 客户端。

像素诊断分别对照文档 0、文档 2、取消／错误后的文档 2 和最终文档 9 的 CPU／GPU 输出与显示适配。相同文档取消／错误前后的 PNG 要求逐字节相同，不同文档须发生像素变化。CPU 参考会阻塞 UI，诊断不进入性能预算。

完整观察不执行像素参考或回读；暂停静止及关闭后各稳定 3 秒，再分别观察 60 秒。采样仅针对 runner 创建的进程，记录工作集、私有字节及 GPU Dedicated／Shared；相邻阶段不混算 CPU。原生阶段标记由文件采样，因此边界会有约一个采样周期的不确定性，要求 60 秒窗口内至少 59 秒样本跨度。GPU 对象释放不代表驱动已归还提交页。

每轮固定可执行文件和源码身份并检查运行期间未变化，保存输入 inventory、源码／锁文件／脚本快照、PNG 哈希与样本。输出目录必须是新的 `artifacts/p0` 直接子目录；越界和覆盖既有结果均须失败。

无窗口新增测试覆盖：原始半透明／透明 RGB、坏 PNG、尺寸错误／缺失文件、开始前取消；工作线程最新请求、无效请求不取消有效请求、旧结果与错误、取消后排空、结果背压和退出；Python 分析器拒绝超限上传、错误文档／像素／代次和非有限样本，CPU 只取同阶段样本。此前的命令、手势、暂停和合成测试继续保留。

## 本机结果

结构化结果及原始证据身份见 [windows-async-composition.json](windows-async-composition.json)。最终三轮使用相同 exe／源码／输入；一个像素诊断、两个常规观察分别保存。原生 55 项、契约 10 项、Python 41 项无窗口测试及默认格式／Clippy／构建通过，可选音频适配器另有 1 项测试。

| 指标 | 常规第一次 | 常规第二次 |
| --- | ---: | ---: |
| 完整文档完成 p95 | 183.243 ms | 172.608 ms |
| 发出请求 CPU p95 | 0.0079 ms | 0.0066 ms |
| 加载 eframe CPU 帧 p95 | 13.385 ms | 8.364 ms |
| 加载 eframe CPU 帧最大值 | 60.241 ms | 59.345 ms |
| 工作集采样峰值 | 234.0 MiB | 231.7 MiB |
| 私有字节采样峰值 | 545.1 MiB | 545.7 MiB |
| OS 累计提交峰值 | 556.9 MiB | 561.8 MiB |
| GPU Dedicated 采样峰值 | 146.2 MiB | 146.2 MiB |
| 静止／关闭同阶段采样跨度 | 59.922／59.922 s | 59.922／59.922 s |
| 静止／关闭单核 CPU 采样 | 0.0%／0.0% | 0.0%／0.0% |
| 静止／关闭 UI 帧数 | 1／1 | 1／1 |

两轮均完成 20 次切换，过期 GPU 候选丢弃 1 次，接纳 22 个完整文档（首次 0、替换 2、再切换 20 次）。23 个候选各上传 40 MiB／5 帧，每帧原图最多两张／8 MiB；两次常规观察的上述阶段检查均通过。请求 CPU 与文档完成是不同测量口径，不能用约 0.008 ms 代表文档已可见。

像素诊断的四个检查点最大通道差为 1／255，无超出 2／255 的像素；取消／缺失 fixture 前后的文档 2 原始输出及显示 PNG 均逐字节相同，文档 0 与 2 有像素变化。所有视图的模拟时钟、游戏输入和历史节点数始终为 0、0、1。该轮含阻塞 CPU 参考，不进入上表性能统计。

加载 p95 在初始 16.7 ms 帧目标内，但约 60 ms 最大帧仍未归因，不能宣布加载无卡顿。全新读取 40 MiB、分帧上传与合成的完成 p95 不属于已解码素材变更的 50 ms 目标；尚无相应的文档切换产品预算。没有把旧纹理池成绩与此新合成路径做因果比较。

静止结束后两轮私有字节约 212.7／213.2 MiB，关闭结束约 130.9／131.7 MiB，GPU Dedicated 从活动文档约 98.1 降至约 58.0 MiB。活动视图与候选已解除，进程仍保有框架、图形设备及可能的底层保留；这些值不表示全部资源归零，也没有完成剩余分配归因。两轮没有持续增长的证据，不据短测宣称无长期泄漏或完整产品预算已通过。

首个预备像素目录 `composition-switch-dbf06b66` 不计入最终统计。随后在正式测量前复查出“取消后仍有结果发送者，不应视为空闲”的边界，停止了一次未产出结果的运行（`composition-switch-aab2973f`），增加 busy／排空跟踪并扩充原队列测试。最终三轮全部在修正后重跑，原始失败／中断目录不覆盖。

共享文件适配和 GPU 构造的回归另用 `check_p0_transport.py --repetitions 1` 执行，结果 `artifacts/p0/transport-3fc07040` 通过；格式、Clippy、55 项原生测试及可选适配器 1 项测试也通过。该回归仍使用同步载入的音频入口，没有将其作为后台切换与音频已组合的证据。

## 加载长帧归因与可选后台预热

后续逐帧诊断见 [windows-pipeline-warmup.json](windows-pipeline-warmup.json)。锁定的 eframe 0.37.0 源码 `epi.rs::IntegrationInfo` 将 `cpu_usage` 定义为上一帧 CPU；原生 `epi_integration.rs::report_frame_time` 写入该值。分析器只关联连续且唯一的帧号，重复、缺帧或非有限样本拒绝自动归因，避免把上一帧 60 ms 分给当前帧上传。

两次初始定位均看到首个 pipeline 创建约 52–53 ms，对应 eframe 帧约 61–62 ms。随后用同一 exe／源码／fixture 做两次同步控制与两次后台预热诊断：

| 指标 | 同步控制 1／2 | 后台预热 1／2 |
| --- | ---: | ---: |
| 加载 eframe CPU 最大帧 | 64.108／52.033 ms | 18.864／19.372 ms |
| 加载 eframe CPU p95 | 7.947／7.763 ms | 7.774／8.017 ms |
| UI 内单次候选准备最大值 | 55.257／51.797 ms | 1.304／0.952 ms |
| 首文档墙钟（包括预热） | 212.902／229.769 ms | 191.086／185.436 ms |
| 后台 pipeline 工作墙钟 | 不适用 | 59.348／55.587 ms |

同步组的长帧主要位于 pipeline API 调用：约 54.582／51.256 ms；计划编译与缓冲准备约一毫秒。上传仍有独立的单帧峰值，预热后的最大帧约 19 ms 也仍超过 16.7 ms。该帧约 17–18 ms 位于 App::logic／ui 的计时区间之外，具体框架／驱动成本保持未知；没有通过平移时间标签或丢弃启动帧使指标通过。

候选增加一个一次性 `PipelineTask`，使用克隆的同一 wgpu Device 在独立线程创建两个固定 WGSL pipeline，完成后由预览会话持有并复用。它不读项目或文件、不依赖 UI，仅以完成通知请求刷新；原图 worker 继续独立。UI 等待期间显示旧图或空预览，文档结果受原有背压约束，不能在预热未完成时启动候选 GPU 准备。创建失败进入可见错误并取消当前请求，不自动回退到 UI 编译；恢复需重新建立预览会话。

预热工作仍消耗 CPU／驱动时间，并增加一个短暂线程；退出会 join，底层编译阻塞的上界尚未验证。pipeline 缓存属于预览设备会话，关闭文档后仍可保留，不含原始素材或历史内容；更换设备、shader 或渲染配置需要重建会话。没有增加通用 shader 缓存框架、依赖或 unsafe。此选项未成为正式产品默认值，历史无预热入口保持原样。

```text
python tools/check_p0_switch.py --fixture artifacts/p0/gpu-fixture --profile
python tools/check_p0_switch.py --fixture artifacts/p0/gpu-fixture --profile --warmup
python tools/check_p0_switch.py --fixture artifacts/p0/gpu-fixture --warmup
```

前两项各做两轮短诊断并保存帧关联，不能用作待机预算。第三项是预热候选的像素诊断及两次完整静止／关闭观察，使用后续冻结版本；与上述同版本短诊断分别记录。[共享音频与文档切换](SWITCH_AUDIO.md)显式使用该候选，新增的原生组合验证不再受同步初次 PNG 入口限制。

后续预热候选的一个像素诊断、两次完整观察也已通过，原始目录 `composition-switch-fd66f8cc`、`composition-switch-c7970192`、`composition-switch-48b590f9`。像素最大通道差仍为 1／255；两次常规加载帧 p95 为 **8.374／8.249 ms**、最大值 **18.731／19.142 ms**，首文档墙钟 **185.191／186.590 ms**，20 次文档完成 p95 **169.492／169.191 ms**。每轮静止和关闭各 60 秒，CPU 采样均为 0.0%，UI 帧数各 1；阶段样本跨度约 59.86–59.95 秒。

两次 OS 累计提交峰值约 **567.4／566.6 MiB**，GPU Dedicated 采样峰值均约 **146.2 MiB**，关闭结束私有字节约 **138.6／137.8 MiB**。pipeline 缓存仍属于存活的预览设备会话，派生图像已关闭；没有宣称总资源归零或降低了提交峰值。该后续版本与上文同版本短诊断分别保存，不把跨批次差异归因于单一优化。

共享绘制内核另通过旧单文档真实音频入口回归一次（`artifacts/p0/transport-de363e35`），300 次连续编辑、取消／提交、冻结输入及像素检查通过。最终原生 57、契约 10、Python 43 和可选音频适配器 1 项无窗口测试通过，默认／feature 格式、Clippy 与构建通过；后续证据均附在 [windows-pipeline-warmup.json](windows-pipeline-warmup.json)。
