# 有界后台加载验证

2026-10-18。这是独立 P0 实验，不是正式素材导入器、项目格式或 stable 内核。前一轮资源基线见[资源对照](RESOURCE_COMPARISON.md)。本轮比较首次读取、PNG 解码、切换取消和每帧纹理提交，继续分别记录工作集、私有提交及 GPU 计量；不以缓存 payload 冒充整个进程内存。

结构化摘要与文件身份：[windows-loading-comparison.json](windows-loading-comparison.json)。三组已完成，输入、exe、源码、脚本与原始耗时统计均复核。

此页保留单在途、立即刷新路径的历史结果；后续通知合并、有限预取及提交峰值定位见[加载调优记录](LOADER_TUNING.md)，不同批次不混为同一因果对照。

## 无回读对照结果

同机同 exe 的两个无回读组均使用 MemoryUsage，包含后文列出的标准负载与压力请求。加载的 UI 阻塞明显降低，内存有所降低，**加载期间的总 CPU 均值增加，瞬时私有提交仍高**。不将后台化概括成所有性能指标同时改善。

| --- | ---: | ---: |
| 加载阶段 CPU 帧耗时 p95 | 111.848 ms | 2.736 ms |
| 加载阶段 CPU 帧耗时最大值 | 1049.494 ms | 20.895 ms |
| 加载 CPU 帧样本数 | 202 | 4277 |

| 20 轮遍历阶段单核 CPU 均值 | 75.65% | 88.92% |

| OS 累计工作集峰值，截至末次采样 | 348.3 MiB | 296.1 MiB |

后台组提交请求的 CPU 耗时 p95 为 **0.026 ms**，205 个请求中两个在快速切换中失效，旧结果未覆盖最终文档 9；有 19 个未派发条目被替换，1 个旧代次回执被丢弃。仍只接纳首个文档的 10 张原图，没有预解码全库。缓存重新上传也受两张/8 MiB 限额约束。

同步组加载 p95 超出初始 16.7 ms 目标，尽管编辑阶段与工作集检查通过。后台组加载 p95 达标，但仍有 20.895 ms 的最长样本，不承诺每帧都不掉帧。加载期间帧数明显增加，20 轮遍历 CPU 均值也上升；合并完成通知、调整加载期间刷新节奏是后续优化点。活跃解码/上传阶段的 CPU 与 60 秒静止观察使用不同口径。

两个无回读组均完成 300 次脚本编辑、20 轮资源遍历、60 秒暂停及关闭后 60 秒观察。暂停、关闭静止阶段均只有一次状态帧，采样 CPU 差值为 0.00%；结束时已跟踪原图和自有纹理引用均为 0，后台线程空闲。无回读组没有做像素和回读延迟判定，相应字段为 null；引用为零不构成整个驱动无泄漏证明。

本轮私有提交峰值仍约 739 MiB，未完全归因，不能宣称低资源目标已整体解决。文档“纹理全部提交”是排队到 egui，两个路径的 GPU 工作分布不同，不代表完整上传完成或显示延迟。首次打开用时还受到顺序运行及文件缓存影响，不据其墙钟差异声称后台更快。

## 后台回读与暂停刷新

第三组同样完成 300 次编辑、20 轮遍历、60 秒暂停与关闭后 60 秒观察，并执行 302 次 GPU 回读。编辑到回读 p95 **7.992 ms**、最大 **31.265 ms**；冻结前后画布像素改变，模拟时钟均为 **9329 ms**，两张图片已直接查看，动画标记位置保持。加载 CPU 帧 p95 为 **3.132 ms**、最大 **21.387 ms**。

该组工作集采样峰值 **302.1 MiB**、私有提交峰值 **747.6 MiB**、GPU Dedicated/Shared 峰值 **245.7/29.1 MiB**。关闭后同样释放已跟踪原图/自有纹理，工作线程空闲，没有持续重绘。回读成本只与本批后台无回读组比较，不能用历史同步批次作因果基线，也不把此回读延迟当作物理输入/显示延迟。

## 实验实现与边界

- 首次 manifest、路径边界、PNG 尺寸与引用校验在一次后台任务中完成，再启动像素加载。诊断曾发现这部分同步读取约需一秒；仅搬走像素解码不能解决首次打开停顿。
- 一个常驻 PNG 工作线程，最多一个在途请求和一个结果槽。不消费前一个结果，就不继续派发下一项；不为每张图片创建线程。元数据任务结束后才派发 PNG，两者没有同时解码或读取素材。
- 结果按请求代次校验。新请求替换尚未派发的列表，旧代次的完成结果不能进入当前纹理投影；同一文档的重复素材引用先去重。实验 Asset ID 对应不可变 fixture 字节，未来可变来源还必须带内容修订，不能直接照搬实验缓存键。
- 单张结果上限 4 MiB，同时考虑 UI 交接结果和工作线程结果时 payload 上界为 8 MiB。该数字不包含压缩输入、解码临时内存、缓存、上传共享引用、GPU 暂存或目标纹理，也不应与共享缓存字节简单相加。
- 每个框架帧最多提交两张纹理、合计 8 MiB；同一帧的重复 UI pass 共用限额。CPU 缓存命中而 GPU 缓存缺失的上传也走此限额。缩略图与冻结材质替换同样受限。
- 切换期间保留旧文档显示，目标文档所需纹理全部提交后才切换当前文档。首次打开没有旧画面，可看到加载中的局部内容；每轮资源清空是显式的关闭/重开测试。纹理“就绪”指已提交给 egui，不代表 GPU 已执行或显示器已呈现。
- PNG 解码开始后不能强制中断，只在执行前后检查取消。关闭时释放接收端并等待工作线程退出，没有分离遗留线程。元数据文件 I/O 也没有硬中断保证；正式产品的超时与关闭体验仍需独立设计。

工作线程没有 SkinProject 写权限，只产生可重建的派生数据。历史可达的原始字节存储与这些缓存的释放完全分开。实验未增加第三方依赖，也未引入线程池框架、事件总线或正式项目核心。

## 同素材比较方法

入口为 `python tools/check_p0_gui.py --run-loading-comparison`。同一 release exe、源码、测量脚本、数据集和适配器依次运行三组：MemoryUsage 同步/无回读，MemoryUsage 后台/无回读，MemoryUsage 后台/逐次回读。两个无回读组是加载方式对照，两个后台组用于区分回读成本。

每组仍为 100 张 1024×1024 原图、100 张缩略图、10 文档/500 层、当前 50 层共享 10 原图，CPU/GPU 原图缓存各 128 MiB。每组 300 次编辑、60 秒暂停、20 轮文档遍历与清空、关闭后 60 秒观察。另按同一顺序立即请求文档 1、2、9，验证最后请求胜出；之后仅清空 GPU 缓存再请求文档 9，验证缓存像素也不会整批绕过上传限额。这段压力场景单列为 RapidSwitch。

`loading_cpu_frame_ms` 对首次读取和切换期间的框架上一帧 CPU 报告取样，包含阶段边界，保留 p95 和最大值；不能只看编辑阶段 p95 掩盖加载卡顿。原始 CPU、编辑间隔、文档完成、请求提交及每帧上传样本存入 `timing-samples.json`。文档完成的墙钟等待与 UI 请求函数耗时分别计量；后台化的目的不是承诺文件解码变快。

所有进程/GPU 数字仍按目标 100 ms 间隔采样，不保证抓住每个瞬时峰值。系统工作集、私有提交、GPU Dedicated/Shared、wgpu allocated/reserved 不同，可能有重叠。GPU 回读检查和物理输入、桌面显示延迟不同；无回读组的像素/回读延迟保持 null。

每组只运行一次，依次执行，没有控制 OS 文件缓存或反向顺序复测。首次打开的墙钟差异可能受文件缓存与新文件检查影响，不能归因为后台解码本身更快；加载帧耗时与重复文档切换另外列出。内存峰值包含新增的快速请求和重新上传场景，不拿前一轮不同脚本的数字当作本轮基线。

本轮结果使用实验 schema v3，增加后台任务、上传上限、取消与原始耗时样本，异步情况下旧 `document_load_cpu_ms` 为 null，改用 `document_load_wall_ms`。历史 v1/v2 及中止诊断保留，不迁移、填造或覆盖；这些是实验记录版本，不是产品项目格式。

后台组的 `original_decode_count` 计入已被 UI 接纳到原图缓存的解码结果，丢弃的旧任务不会计入此值；`loader` 另记录实际执行、解码前跳过和旧结果丢弃，并单独统计含缩略图/冻结替换的工作耗时，不能拿缓存接纳次数冒充全部解码工作量。

## 验证与后续范围

无窗口行为覆盖队列背压、执行中请求被替换、排队任务淘汰、无效计划不覆盖旧计划、错误回传、取消、未消费结果时关闭、损坏/缺失 PNG、尺寸变化、非 ASCII 路径和 alpha，以及帧间/同帧上传限额。元数据后台任务沿用同一验证入口，成功和失败均有测试。

共 **35 项无窗口行为测试通过**：10 项契约、12 项 Rust PNG/缓存/UI/加载、13 项 Python 工具/统计；依赖边界、格式、Clippy、release 构建和输出路径保护通过。三组原生流程均成功；同步加载的 p95 仍超目标，功能流程成功不等于所有性能门槛通过。汇总另明确标出三组的加载帧预算结果。

三组原始目录为 `load-sync-none-c831a4f3`、`load-async-none-ce783b9d`、`load-async-readback-12c1bd55`，共用 `comparison-fixture-af71d49b`，均位于 `artifacts/p0`；完整比较为 `loading-comparison-af71d49b.json`。三个 exe/源码/脚本/适配器/数据集身份一致，201 个输入哈希保持不变，原始耗时统计与逐帧上传限额已重算复核。进程样本分别为 1411、1407、1434 条。原始目录不提交，摘要保留输入、输出及实现身份 SHA-256。

早先 `load-diagnostic-6bf26fec` 用来发现同步元数据阻塞；`load-diagnostic-metadata-86b4a0da` 是修复后的短运行。中止的 `load-sync-none-e5a6f59e` 没有完整正式比较，不进入本表；相关目录均保留。没有用短诊断替代 300 次编辑或 60 秒观察。

本轮不读取旧 stable 工程，不运行真实客户端，不需要 F12 或系统窗口捕获。完整合成与导出、独立 GPU 时间戳、真实输入/音频/游玩、IME、高 DPI、macOS/Linux 仍未验证。P0 和产品选型保持开放。
