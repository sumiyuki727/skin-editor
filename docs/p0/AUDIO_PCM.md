# 生成 PCM、内容定位与编辑联动

P0 Windows 实验从静音扩展到真实非零 float32 PCM 提交，验证播放、暂停、双向定位和受控重建时的内容位置。它仍是独立能力原型，不是正式播放器、谱面解析器或 stable 游玩内核。Linux 实测暂缓，macOS 待设备；本轮没有改变平台范围或确定正式音频后端。

## 内容与端口

`p0-wasapi::pcm` 是纯计算模块：六秒自制音调，每半秒前 200 ms 发声、后 300 ms 静音，440／660／880 Hz 轮换，边缘各 5 ms 渐变，最大样本幅度 0.04。按输出采样率直接计算单声道内容，再复制到经过校验的单／双声道 float32 输出。没有读取私人文件、客户端声音、外部音乐或非开源素材，没有音频解码器、重采样器或混音系统。内容结束后填零，不自动循环或推进游戏结算。

普通入口继续输出静音；只有显式 `spawn_pcm`／新诊断入口写入非零 PCM。沿用既有 `windows 0.62.2`、同一工作线程和 8 项控制队列，不新增第三方依赖或 API feature。每包至多 1 MiB，无整曲解码缓存，也不按包分配暂存像素／样本数组。新增少量固定大小的包摘要与快照字段；这些上限不代表完整应用预算。

平台中立 `Output` 仍只有三个方法：读取快照、提交暂停意图、替换流。替换请求统一携带 `{epoch, position_us}`，恢复由 Transport 产生最后确认位置，定位由已暂停的 Transport 产生指定位置；省略内容位置的恢复接口不再向预览端口暴露。协议是未发布的 `0.0.0` 实验接口，没有持久化项目或外部调用方迁移；旧证据保留其冻结源码，不重写旧结果。

普通恢复使用原流及其尚未消费的队列，不重置内容游标。定位或受控故障恢复由同一线程释放旧流，再打开新流，丢弃旧队列。新流从暂停／请求 0 开始，先建立设备位置锚点，再等待显式播放。向后定位仅在明确的暂停定位请求获得新代次确认后改变模拟位置；普通样本倒退仍然故障。失败定位保持最后确认的旧时间，故障后可显式重试；输入门控与文档历史独立。

## 设备消费与提交边界

模拟位置跟随设备时钟及内容起点：`内容起点 + 设备流位置`，不跟随已提交帧数。已提交帧通常领先设备消费位置，暂停同时保持设备位置与提交游标。若设备时钟已经越过提交内容，检测为欠载故障，冻结并等待明确恢复；整数换算边界允许一帧，不用墙钟填空或继续假装同步。这个检测不是完整的音频 glitch 监测。

内容位置向下取整到采样帧，误差小于一个采样周期；模拟记录保留请求的微秒位置。故障恢复以最后一次有效 UI 观察为锚，可能重播故障前尚未确认的短段，不能宣称无缝切换或声学精度。真实端点、驱动阻塞、设备自动切换和低延迟事件调度尚未验收。

Windows 原生缓冲仅由 `platform.rs` 访问。先验证混音格式确为 IEEE float32、有效位、通道、字节率与帧对齐，再按可用帧数计算有界长度；扩展格式的长度足够后才读取其子格式。取得缓冲后完整初始化全部字节，同线程成对释放；准备失败释放为静音，成功 ReleaseBuffer 后才推进提交游标。默认静音路径仍不解引用样本指针，主 UI 工程继续禁止 unsafe。

依据为微软的 [GetBuffer 边界与配对要求](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiorenderclient-getbuffer)、[ReleaseBuffer 语义](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiorenderclient-releasebuffer)、[设备位置与频率](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition)、[停止流](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-stop)及[扩展混音格式](https://learn.microsoft.com/en-us/windows/win32/api/mmreg/ns-mmreg-waveformatextensible)。float 子格式身份也核对本地锁定 bindings 中的 SDK 定义；它是 Windows API 数据，不是 stable 兼容常量。查询记录不等于原生内存安全证明。

## 验证入口

```text
python tools/check_p0_pcm.py --fixture artifacts/p0/gpu-fixture --repetitions 3
```

此入口会短暂播放低幅度自制音调，使用默认 shared 输出，不改变系统音量或默认设备，不录音或使用 loopback。先执行无窗口检查／构建，再顺序运行原生窗口。已有 GPU fixture 继续校验哈希，拒绝输出越界与覆盖证据，保留源码、锁文件、工具及 PNG 身份。

每轮播放 → 暂停并编辑 30 次、提交一次 → 普通恢复 → 暂停后定位到 1050 ms → 播放／暂停 → 向后定位到 50 ms → 播放中受控退休 → 从最后确认位置重建、暂停就绪 → 显式播放及最终暂停。各关键暂停至少三条新鲜读数；旧流故障拒绝三次，恢复与定位不重放 held／repeat。

包记录包含内容起点、提交前沿、首／末包来源帧、哈希、峰值和前八帧探针。Python 用独立音调公式对照探针，并检查各代次位置、提交单调性及暂停冻结。四个 1024² CPU／GPU／显示检查验证暂停改图及定位／重建后的图像一致，诊断参考仅在暂停执行，不当作帧或预算测量。

自动验证只证明设备接受已初始化的非零 PCM、模拟／内容位置关系和图像结果；扬声器可听性需用户确认，声学延迟需另行测量。原始结果固定写入 `human_audibility: unconfirmed`，后续人工确认单独登记，不改写自动证据。听到提示音也不能证明低延迟达标。

## 本轮结果

[windows-pcm.json](windows-pcm.json)登记同一 exe／源码／输入身份的三次自动重复，以及一次用户在场复核。自动目录为 `pcm-103f05cb`、`pcm-50bc841a`、`pcm-11b87455`；在场复核为 `pcm-0a1c8c62`。四轮均完成四个内容代次、双向定位、普通恢复与受控重建；暂停提交不前进，旧代次拒绝 3 次，接纳按下 2 次，30 次拖动提交一个节点。每轮四个 CPU／GPU／显示对照最大差 1／255，重建及定位后 PNG 保持一致。

用户明确确认在场轮“可听，暂停和恢复正常”，独立记入汇总的 `human_confirmation`，不改写四轮原始自动字段。首轮 `pcm-1a6b09c5` 内部流程完成，但漏导出旧代次计数字段，外部验收失败；补齐字段并增加缺字段回归后重新运行，上表不含该轮。未用内部成功标记替代外部证据检查。

无窗口共 128 项：原生 62、契约 10、Python 47、可选适配器 9。新增覆盖字节／通道布局、已知音调与静音、失败提交不跳帧、定位量化、格式拒绝、欠载、显式后退及定位失败恢复；证据检查拒绝错误内容探针、播放头、暂停写入、旧样本及未经支持的听觉声明。格式、Clippy、默认／feature 构建及原有静音入口另行回归，身份登记在汇总中。

剩余音频门槛包括物理输入同步／延迟、音频文件解码与最小谱面时间线，以及后端选择；本机基础听感已取得，声学延迟仍未知。完整对象判定与游玩仍属 P5。本轮无需 stable F12，兼容案例数保持 0，未提交或推送 Git。
