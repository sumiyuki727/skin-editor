# 图层合成语义与 CPU／GPU 对照

这是独立 P0 实验，代码在原生候选的 `composition.rs` 与 `composition-proof` 入口中，不构成正式 rendering 模块、项目格式或 stable 兼容规则。其目的是验证图层变换、隔离组透明度与预览／PNG 合成能否共用明确的语义。

2026-10-19 的 Windows／RTX 2060 Vulkan 对照通过：九组样例，共 12960 个像素，最大通道差为 **1／255**，没有超出预定 2／255 容差的像素。身份、逐项结果与 PNG 哈希见 [windows-composition.json](windows-composition.json)。已直接查看嵌套组的 CPU／GPU 输出；没有系统窗口捕获。

## 本轮语义

- 位图边界是整数坐标，目标像素在中心 `(x + 0.5, y + 0.5)` 采样。局部二维仿射矩阵按父乘子组合，包含非等比缩放、旋转、反射与斜切，不通过分解 TRS 丢掉信息。
- 图层按列表顺序从底到顶 source-over。组先将子项合成，再对组结果应用一次 opacity；嵌套组逐层执行。组的几何变换作用于子项的文档空间几何，不先烘焙一个低分辨率组贴图。
- 受控 PNG 输入假定为 straight RGBA8／sRGB。采样与混合在 linear-light、premultiplied RGBA 中执行，PNG 输出转换回 straight RGBA8／sRGB；量化后 alpha 为零的输出统一为透明黑，原始资源不被覆盖。
- nearest 使用局部像素索引；bilinear 在 premultiplied linear 值上插值，图像内部采样 clamp-to-edge，位图范围外透明，最终裁到文档画布。尚未实现几何边缘的覆盖率抗锯齿。
- CPU／GPU 统一将距离整数 ≤ 0.0001 源像素的坐标吸附到该整数，再应用半开位图边界和采样规则。它用于明确近边界的浮点判定，不能省略为两端各自判断。极端矩阵的精度仍需更大范围验证。
- CPU 编译器生成只读合成计划；CPU 参考解释器与 GPU WGSL 执行相同的计划。计划借用已验证的不可变素材，公开读取接口不提供变更入口。
- 小图默认预算限定画布／素材边长 ≤ 256、素材与节点各 ≤ 128、嵌套组 ≤ 8；[标准规模扩展](COMPOSITION_SCALE.md)显式选择 1024 边长及 40 MiB 活跃源预算。非有限参数、不可逆变换、缺失引用与畸形像素在编译阶段失败；这些是实验上限，不是正式产品限制。

色彩策略是编辑器实验的显式选择，尚未用当前 stable 的 F12 图像验证其混合／采样行为。未来若需要兼容差异，应在合成策略及兼容证据中表达，不能在 UI 中插入未验证的修正。

## 验证范围

无窗口 CPU 测试使用可手算结果验证组重叠后的透明度、嵌套 alpha、linear-light source-over、旋转与非等比缩放、裁切、透明彩色边缘、仿射往返及失败输入；不只依赖两套执行器互相比对。

当前十项 CPU 行为测试通过，包括显式规模／总源字节预算。最初的浮点边界分歧由共同的近整数判定规则修复，并增加专门的半开边界回归样例；没有通过移动原始样例、屏蔽边缘像素或放宽颜色容差来通过检查。当前结果仍不能证明任意极端矩阵下都达到该容差。

原生 GPU 入口生成五张混合尺寸 PNG，重新解码后作为共享源素材，执行九种 40×36 画布样例：空画布、恒等变换、一般仿射、反射、隔离组重叠、嵌套组、画布外裁切、零组透明度与近整数边界。分别输出 CPU／GPU PNG，并检查 PNG 像素往返。每个 RGBA 通道容差预先固定为 2／255，任一像素超出即失败。

GPU 使用无窗口 compute 原型和直接缓冲回读；每个目标像素解释合成计划，组使用线程内栈。这是语义验证路径，没有验收正式渲染后端的离屏纹理方案、500 层标准负载或最终性能。CPU 墙钟与 GPU 设置／提交／回读墙钟只作诊断，不称为 GPU 执行时间。

后续标准扩展已另行验证 10 文档／500 层、显式缓冲及 GPU pass 时间戳，结果见[规模记录](COMPOSITION_SCALE.md)；小图历史成绩保留原口径。实际拖动与取消在另一[交互原型](INTERACTION.md)中验证，没有把两者描述为完整产品闭环。

P0 工程新增直接引用 `pollster 1.0.1`（Apache-2.0／MIT），用于无窗口 GPU 初始化的异步等待；它已经存在于锁定的 eframe 依赖树中，不新增第三方包版本。只在实验原生入口使用，未引入产品核心或增加 UI 工作线程。现阶段实际验证平台为 Windows，其他平台仍需实测。

未单独量化该等待封装的二进制成本；它复用现有依赖版本，不另起常驻服务。维护上随原生候选的锁文件管理，升级 GPU 依赖后重新执行无窗口检查与原生像素对照，不能把本轮原型的依赖选择直接作为产品栈。

蒙版、效果、额外混合模式、色彩配置文件、实际编辑拖动、Command／历史、真实音频和 stable 逻辑仍未在此入口实现。

## 复核入口

```text
python tools/check_p0_composition.py
python tools/check_p0_composition.py --run-native
```

第一项运行依赖边界、格式、Clippy、release 测试及构建，无需 GPU／窗口。第二项额外执行无窗口 GPU 对照、PNG 往返、新目录及输出边界验证，检查已有输出不会被覆盖。需要现有的项目私有 Rust 1.95、MSVC／SDK 与原生实验缓存；Windows 准备方式仍见原生实验 README。其他平台尚未实测。

CPU 模块增加常见 UI／GPU 与平台导入的静态 guard，并用人为注入的反向引用验证能够拒绝；它与 Cargo 依赖白名单配合，不替代源码审查，也不是完整 Rust 依赖证明器。
