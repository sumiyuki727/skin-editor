# 原图 GPU 上传与私有提交峰值

2026-10-18。延续[加载调优](LOADER_TUNING.md)。本轮增加 Rust 分配统计、物理纹理复用、GPU 完成等待、后端对照和指定 PID 的原生堆事件。**P0 仍进行中，产品技术栈与默认缓存策略未定。**

可复核的身份、样本摘要和原图校验见 [windows-gpu-upload.json](windows-gpu-upload.json)。旧报告与旧成绩保持原样；本轮的因果比较使用本轮构建，不拿历史峰值作为基线。

后续的[三次重复与分配寿命验证](ALLOCATION_ATTRIBUTION.md)发现复用组的进程提交有显著波动，未重现下文首轮单测约 +12.5 ms 的加载 p95 代价，并定位到显存释放后延迟回收的 PRIVATE 区域。下文保留为首轮记录，当前结论以重复报告的范围和限制为准；堆解析器修正也另存新结果，不改写原始证据。

## 完整负载下的降峰方案

同一默认 release exe、Vulkan / NVIDIA RTX 2060、MemoryUsage、合并通知和两项预取，对比新建纹理的 128 MiB GPU 原图缓存与复用纹理的 80 MiB 缓存。两组 CPU 原图缓存均为 128 MiB，保留真实 1024² PNG、全部绘制和每帧两项／8 MiB 上传限额。

| 指标 | 新建纹理，GPU 128 MiB | 复用纹理，GPU 80 MiB |
| --- | ---: | ---: |
| 私有提交采样峰值 | 690.859 MiB | 614.629 MiB |
| OS 累计提交峰值，截至最后采样 | 699.656 MiB | 618.684 MiB |
| 工作集采样峰值 | 249.609 MiB | 246.418 MiB |
| GPU Dedicated 采样峰值 | 242.070 MiB | 162.035 MiB |
| 200 次加载的样本 CPU 时间 | 19.281 s | 18.547 s |
| 循环墙钟 | 28.542 s | 28.654 s |
| 文档到纹理全部排队 p95 | 93.413 ms | 105.915 ms |
| 加载 CPU 帧 p95 / 最大 | 13.237 / 21.854 ms | 12.336 / 19.792 ms |
| 原图纹理创建 / 更新次数 | 2030 / 0 | 20 / 2010 |
| 关闭后 60 秒私有提交末值 | 111.090 MiB | 109.391 MiB |

本次完整对照的私有提交峰值下降 **76.23 MiB（约 11.0%）**，OS 累计峰值下降 **80.97 MiB（约 11.6%）**。样本 CPU 时间下降约 3.8%，墙钟基本持平；文档完成 p95 增加约 **12.5 ms**，最长加载帧仍超过 16.7 ms。这个方案降低了本负载的峰值，不能据此宣称所有交互都更快，或资源目标已经全面通过。

两组都完成 300 次编辑、20 轮切换、60 秒暂停与关闭后 60 秒观察。静止阶段无连续绘制，样本单核 CPU 为 0–0.03%；结束时所跟踪原图、自有纹理和队列资源均已释放。字体、窗口目标与 GPU 设备仍存在，进程提交末值不应为零。

80 MiB 在这个固定负载中可容纳当前与下一文档的 20 张 4 MiB 原图。空闲物理槽也计入预算，关闭时释放；没有缩小素材、漏画图层、回收原始资源或改写输入文件。正式产品有不同尺寸、效果和多场景需求，不能直接采用这个固定容量。

## 上传临时分配、堆保留与后端成本

以下为另外的诊断构建，启用可选 Rust System 分配统计，每组 30 次编辑、20 轮切换，缩短静止观察。其原子计数、页面扫描与额外记录开销不混入上面的完整性能成绩。

| 诊断路径，无回读 | 私有提交峰值 | Rust 存活请求采样峰值 | 活跃 wgpu Staging 峰值 | wgpu reserved 峰值 |
| --- | ---: | ---: | ---: | ---: |
| Vulkan，新建 128 MiB | 689.5 MiB | 137.4 MiB | 8.09 MiB | 224 MiB |
| Vulkan，复用 128 MiB | 682.1 MiB | 136.2 MiB | 8.09 MiB | 208 MiB |
| Vulkan，仅解码，不上传原图 | 241.3 MiB | 139.7 MiB | 0.09 MiB | 16 MiB |
| DX12，复用 128 MiB | 522.3 MiB | 139.9 MiB | 8.19 MiB | 244 MiB |
| Vulkan，每轮等待 GPU 完成 | 698.6 MiB | 140.1 MiB | 8.09 MiB | 224 MiB |

第一批 128 MiB 复用实验将创建数降至 32，更新 1998 次，但无回读峰值只小幅下降。第二批同构建的新建基线约 698.7 MiB，80 MiB 复用方案约 547.4 MiB；其 CPU 存活像素与缓存仍相同。降低 GPU 容量比单独减少创建次数有更明确的收益。不同组的独立峰值发生在不同时间，不能相加构成一个“总成本分解”。

**上传临时空间。** 固定版本 egui-wgpu 的普通 RGBA 上传借用 `ColorImage` 像素并调用 `queue.write_texture`；上传队列与 CPU 缓存保持 `Arc<ColorImage>` 共享，提交阶段没有额外克隆整幅 RGBA，PNG 解码／转换临时量另计。20 次逐轮 GPU 等待都成功，最长约 0.232 ms；等待前后活跃分配减少约 4–8 MiB，reserved 保持不变。可确认这部分为短时在途资源；它不能独自解释数百 MiB 提交增量。逐轮阻塞等待也未降低该诊断的全程峰值，不作为编辑路径优化。

**Rust 请求与堆保留。** 有／无原图上传时，已接受原图像素峰值均为 128 MiB，Rust 存活请求约 136–140 MiB。关闭时请求量回到几 MiB，累计申请／释放量已达十几 GiB。`stats_alloc` 的请求差额不包含分配器已空闲但仍保留的页，也不包含原生库和驱动；不能用进程提交减去它就得到“驱动成本”。计数快照非原子，负差值会记录为未知，不填零。

另用 xperf 的独立命名堆会话跟踪自有 PID，未启用全局内核跟踪或修改注册表。两组对照均正常停止会话、无丢失事件／缓冲区。默认环境的一轮跟踪中，观察到请求峰值约 141.1 MiB，已报告堆段的 committed 采样峰值约 159.3 MiB；关闭阶段的一次相邻观察中，堆段仍 committed 约 18.2 MiB，free counter 约 1.35 MiB，进程私有提交约 132.2 MiB。这分别记录了堆段提交保留和空闲计数，没有把整个 18.2 MiB 当作空闲。段计数缺少未变化堆与直接虚拟分配，不拿它们与 PrivateUsage 相减做全量归因。

堆跟踪附加到运行中进程，会漏掉此前的分配；不含全局进程元数据时，xperf 内建聚合显示 Unknown，不能声称获得完整的符号级堆报告。单独的无窗口解析器按申请／释放／重分配配对，并使用该 PID 模块地址解释已识别栈。默认组仍有约 84 MiB 的存活请求样本未识别来源；NVIDIA 已识别栈只是一小部分，既不代表驱动总量，也不能据此排除驱动成本。

**后端、驱动和外部图形层。** 128 MiB 复用的 Vulkan／DX12 无回读诊断相差约 160 MiB，但 DX12 工作集约 316 MiB，高于 Vulkan 约 248 MiB，reserved 也更高。后端确实影响分配路径；这个差值不等于纯驱动开销，不能据此将 DX12 定为跨平台默认值。

模块清单发现额外的 OBS 图形钩子与 NVIDIA 覆盖层。按 [Khronos Loader 调试说明](https://github.com/KhronosGroup/Vulkan-Loader/blob/main/docs/LoaderDebugging.md)仅给一个新子进程设置 `VK_LOADER_LAYERS_DISABLE=~implicit~`，OBS 钩子消失，NVIDIA 覆盖层仍在。一轮相同堆跟踪的提交峰值约 598 → 622 MiB，没有下降；不支持 OBS 隐式层是主因。它是独立的一轮探查，不是干净驱动环境的完整性能对照；未改动其他应用、系统环境或注册表。

**观察方式影响峰值。** 同一诊断 exe、128 MiB 复用策略，额外 14 次画面回读时约 520 MiB，无回读时约 682 MiB；80 MiB 的画面验证组也低于无回读诊断。同步节奏／分配复用状态会影响峰值，尚未精确拆解这一差异。因此最终降峰结论使用独立的完整无回读对照，不挑选最低的画面验证成绩作为常规预算。

## 像素、暂停与测试

128 MiB 和 80 MiB 的复用策略都与新建纹理基线比较了 12 张 748×520 画布：全部 10 文档、重置后再次访问文档 0、第 200 次切换。PNG 字节完全一致，像素容差为零；排除 y=570 的时间标记，不缩放或重采样。每轮故意清空逻辑缓存是压力测试，未据此验收切换过程的视觉连续性。

完整 80 MiB 回读组完成 300 个编辑延迟样本，p95 **7.539 ms**、最大 **15.848 ms**；冻结前后图片发生变化，时间标记位置不变，模拟时间均为 **9277 ms**，两图已直接查看。该组提交采样峰值约 616.0 MiB，OS 累计峰值约 624.1 MiB，关闭末值约 144.9 MiB。额外回读资源与保留成本另列，不当作物理输入／显示延迟。

本轮 **48 项无窗口行为测试**通过：10 个契约、18 个 Rust 图像／加载／纹理测试、20 个 Python 工具测试。新增覆盖固定预算、受保护纹理不被覆盖、复用 ID、partial delta 的共享像素、重置与关闭，以及堆事件配对、未知旧分配、失败重分配、模块来源和覆盖层区分。格式、默认及诊断构建的 Clippy／release 测试与构建、输出目录保护通过。

13 组原生负载流程成功，其中 3 组为完整观察，相关可测预算通过；10 组诊断有意缩短编辑和静止观察，对应检查仍为 false。另有两组指定 PID 的堆事件对照；前期工具探路不作为性能成绩。201 个输入文件哈希均保持不变。记录包括两批构建、默认／诊断 exe、Rust 源码、脚本、Cargo.lock 与输入／输出哈希；第一批一组探索记录过仅元数据列表变化的脚本磁盘哈希，结构化证据明确说明，完整对照使用之后的固定脚本。

## 保留的限制与下一步

已将上传短时资源、Rust 存活请求、部分堆保留与后端差异分别测量，**尚未完成纯驱动／覆盖层／直接虚拟分配的逐字节归因**。本批是单机、每配置一次的观测，不能代替重复统计或跨平台结论。下一步优先取得指定 PID 的虚拟分配调用点与驱动映射证据，在明确图形层的环境重复常规对照；不通过强制清空工作集、压堆或频繁重建设备来制造低值。

新增 `stats_alloc 0.1.10` 为 MIT、无传递依赖，仅在可选 `heap-profile` feature 中使用；默认应用路径没有计数成本。纹理复用仅为固定形状的 P0 派生缓存实验，不改变原始 Asset、历史资源或 Command 边界，也不修改上游库。产品的变尺寸合成／导出、GPU 时间戳、真实音频／游玩、IME／高 DPI 和 macOS/Linux 仍未验证。本轮未访问旧 stable 工程或真实客户端，不需要 F12 图片，未提交或推送 Git。

分配计量参考：[stats_alloc 源码](https://docs.rs/stats_alloc/0.1.10/src/stats_alloc/lib.rs.html)、[Microsoft 堆事件](https://learn.microsoft.com/en-us/windows/win32/memory/memory-management-tracing-events)、[xperf 指定进程堆记录](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/xperf/quick-start---enabling-data-capture-on-an-existing-process)。原始资料保留在忽略的 `artifacts/p0`，固定结果整理脚本也保留于该目录，不把它作为产品接口。体积较大的派生 CSV 在分析后移除；原始 ETL、校验和及重建 CSV 的命令保留。
