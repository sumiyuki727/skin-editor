# 加载 CPU 与提交峰值定位

2026-10-18。延续[后台加载实验](ASYNC_LOADING.md)，本批优化加载期间的通知与绘制节奏，并用独立诊断区分 CPU 像素处理、原图 GPU 资源与绘制路径的资源成本。仍为独立 P0 实验，产品技术栈、项目核心和 stable 兼容范围未定案。

结构化结果、实现身份与逐文件校验见 [windows-loader-tuning.json](windows-loader-tuning.json)。

后续的[GPU 上传与提交定位](GPU_UPLOAD.md)增加分配统计、纹理复用、堆事件及降低 GPU 预算的验证。本页保留本批原始成绩，不将后续构建的峰值混入比较。

200 次文档加载的样本 CPU 工作量下降约 **11.7%**，UI 帧数减少约 **71.4%**。CPU 百分比降幅更大，部分来自阶段变长，不能将它冒充工作量降幅。样本跨度分别为 21.875 / 28.375 秒，首末采样点略短于整个循环。

代价也明确：加载循环墙钟增加约 **29.7%**，文档完成 p95 增加约 **21.2 ms**；双纹理批量上传增加单帧工作，加上预取成本，提交峰值也略增。加载帧 p95 仍在 16.7 ms 初始目标内，但最长样本仍超目标。这个组合是 CPU／等待／内存之间的可选参数，**不能宣称为全面更快、更省内存或自动成为产品默认值**。

两组均完成 300 次编辑、20 轮遍历、60 秒暂停和关闭后 60 秒观察；静止时只有一次必要状态帧，无连续重绘，样本 CPU 差值为 0.00%。关闭末值私有提交约 185.7 / 186.7 MiB，所跟踪原图与自有纹理为零，工作队列空闲。无回读组的像素和回读延迟保持 null；纹理排队耗时也不是 GPU 执行或显示延迟。

合并通知的回读组完成 300 次编辑回读，p95 **7.079 ms**、最大 **16.198 ms**；冻结前后画布改变、动画标记位置保持、模拟时钟均为 **9311 ms**，两张原生回读图片已直接查看。该组工作集采样峰值约 312.2 MiB、私有提交约 782.6 MiB，OS 累计提交峰值约 782.7 MiB；回读开销与无回读组分开，不当作物理输入／显示延迟。

## 私有提交的归因结果

以下三组都保留真实 PNG 解码、20 轮切换及 128 MiB CPU 原图缓存，开启相同诊断。峰值为各自独立峰值，不相加，也不将短观察算成完整资源验收。

| 指标 | 上传并绘制原图 | 上传但不绘制原图 | 不上传原图 |
| --- | ---: | ---: | ---: |
| 私有提交采样峰值 | 776.1 MiB | 755.1 MiB | 318.0 MiB |
| OS 累计提交峰值 | 776.1 MiB | 759.1 MiB | 318.1 MiB |
| 工作集采样峰值 | 299.4 MiB | 305.7 MiB | 298.0 MiB |
| GPU Dedicated 采样峰值 | 251.7 MiB | 235.7 MiB | 43.6 MiB |
| 已接纳原图存活像素的观察峰值 | 128 MiB | 128 MiB | 128 MiB |
| wgpu 存活分配的观察峰值 | 137.91 MiB | 137.91 MiB | 5.90 MiB |
| wgpu 保留容量的观察峰值 | 224 MiB | 208 MiB | 16 MiB |
| wgpu Staging 存活分配的观察峰值 | 8.09 MiB | 8.09 MiB | 0.09 MiB |

停用原图绘制仍有高峰，而停用原图 GPU 上传使提交峰值降低约 **437–458 MiB**，约为完整路径的 **59%**。在此次采样中，三组已接纳原图像素都不超过 128 MiB，工作集又相近。**新增的大部分提交与原图 GPU 资源／上传路径相关，不能由 CPU 原图缓存本身或单纯绘制原图来解释。** 这是屏蔽路径的实验归因，没有把“没有原图画面”的诊断组列为可用预览器。

目前还不能把这部分全部命名为 GPU Staging：观察到的 Staging 活跃分配只有约 8 MiB，wgpu reserved 也不是完整进程提交。页面扫描确实看到较多 MEM_PRIVATE 提交，但分类不能确定它来自 egui/wgpu 的上传临时分配、通用堆保留还是 NVIDIA/Vulkan 驱动。没有分配调用栈或另外的后端对照，不能将差额直接归给某一个组件，更不能把不同计量相减得出的差额当作精确归属。

完整绘制诊断的采样提交峰值约在 32.95 秒；最近一次完整页面扫描在约 0.125 秒后，查询前后私有提交约 772.1 / 768.1 MiB，MEM_PRIVATE 页面合计约 742.4 MiB。该变化说明扫描和进程计量不是同一原子快照；摘要保留时间差和查询前后值，不声称该页面分类精确拆解了 776.1 MiB 峰值。

本批已将后续调查缩小到原图 GPU 资源／上传生命周期：优先进一步区分上传临时分配与后端／驱动保留，再评估是否需要公开图形后端的对照。不通过压低缓存、去掉正常画面、手工裁剪工作集或重建设备来制造低数字。当前合并通知策略仍为可选实验参数，P0 的整体资源目标保持开放。

## 改动和验证口径

原有路径每个解码结果完成便立即请求重绘。新路径将完成通知合并到目标 60 Hz 的加载刷新节奏，避免为每个结果请求即时帧及后续补帧。一次 UI 处理最多取两项完成结果；缓存命中、缩略图及冻结替换仍共用每帧两张／8 MiB 素材上传限额。用户输入仍可触发界面刷新，游戏模拟时钟与加载节奏分开。

PNG 解码仍只有一个工作线程。为了减少等候 UI 消费结果的空档，新路径最多保留两个在途请求（包括已完成但未取走的结果），结果槽也为两个。加上 UI 暂持的一张图，受限结果 payload 上界由 8 MiB 增至 **12 MiB**；这是明确的 4 MiB 预取成本，不降低 128 MiB 原图缓存或隐藏队列持有的像素。压缩数据、解码 scratch、GPU 暂存和目标纹理另计。

旧请求的两个回执都必须经过代次检查。取消不会强制中断已开始的 PNG 解码，关闭时等待线程退出；没有增加线程池、第三方依赖、通用事件总线或项目写入通道。帧合并、两个结果槽的背压／取消／关闭均有无窗口测试。

入口：

```text
python tools/check_p0_gui.py --run-loader-tuning
```

同一 release exe、源码、脚本、适配器和自制数据集，按以下顺序执行，GPU 测量不并行：

| 组 | 加载方式 | 绘制/上传 | 观察范围 |
| --- | --- | --- | --- |
| tuning-immediate | 单在途、立即通知 | 完整 PNG，无回读 | 300 编辑、20 轮、60 秒暂停和关闭后 60 秒 |
| tuning-paced | 两项有界预取、合并通知 | 完整 PNG，无回读 | 同上 |
| tuning-paced-readback | 两项有界预取、合并通知 | 完整 PNG、302 次回读 | 同上，另验证冻结下更新 |
| memory-upload-draw | 合并通知 | 原图上传并绘制 | 20 轮，短观察，开启内存诊断 |
| memory-upload-only | 合并通知 | 原图上传，不绘制原图 | 同上，仅归因诊断 |
| memory-decode-only | 合并通知 | 解码原图，不上传原图 | 同上，仅归因诊断 |

三组完整运行各保留 100 张 1024² 原图、100 缩略图、10 文档／500 层、当前 50 层共享 10 原图、CPU/GPU 缓存各 128 MiB。三组诊断保留相同的 20 轮资源遍历与缓存预算，只将编辑缩为 30 次、暂停缩为 1 秒、关闭观察缩为 3 秒。屏蔽路径仅为定位原因，不能作为正常功能或预算通过证据；字体、缩略图、窗口和渲染目标仍然存在。

降低 CPU 百分比不等于减少工作量。本批同时记录整个 20 轮区间的样本 CPU 时间、墙钟、样本跨度、每文档 CPU 时间及 UI 帧数，保留文档完成 p95 和最大帧耗时。CPU 时间跨线程相加，不按机器逻辑核数稀释；首末采样点略短于完整阶段，相关字段明确标为 sampled，不将 idle 或 RoundEnd 边界丢失的时间混入。

每组只运行一次，OS 文件缓存与后台负载没有隔离，不作跨机器或统计排名。初次打开墙钟可能受顺序和缓存影响，不能据此断言某种加载方式更快。新结果使用实验 schema v4、进程记录 v3；旧记录原样保留，不是产品格式迁移。

## 内存诊断方法

常规进程采样继续读取工作集、私有提交和按 PID 的 GPU 计量，并新增 OS 的 `PeakPagefileUsage`，补充 100 ms 目标采样可能错过的峰值。`PrivateUsage` 和生命周期提交峰值的含义见[微软结构说明](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)。提交、工作集、GPU 驻留及缓存 payload 不同，可能重叠，不能相加后当作总内存。

仅诊断组另记录：

- 自有 renderer 的 wgpu allocated/reserved，按原图纹理、Staging、其他分配聚合，目标间隔 100 ms。记录位于当前帧提交前，不伪装为 GPU 执行时间戳。
- CPU 缓存、自有 GPU 纹理 payload、已接纳原图的存活像素、UI 暂持像素和在途请求数。尚在工作线程内的解码临时分配没有被完整跟踪，不能将这些计数视为完整进程堆。
- 仅对 runner 创建的进程执行 `VirtualQueryEx` 页面元数据扫描，目标间隔 500 ms，记录 private/mapped/image 分类、较大分配区间和扫描耗时；不读取内存页内容。查询前后各记录私有提交，扫描不是原子快照，页面分类不能直接标出某个库或代替 PrivateUsage。写时复制页也可能仍报告 mapped/image，见[微软 API 说明](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualqueryex)。

`memory-trace.jsonl`、`virtual-memory.json`、`process-samples.json` 与阶段日志按同一时钟对齐；原始采样和文件身份保留。诊断开销不混入前两组常规 CPU 对照，短观察也不代替完整组的静止验证。

三组诊断的页面扫描分别为 71/71、69/70、70/70 次完整；最大扫描耗时分别约 32、32、16 ms。仅上传组末次扫描在退出期间返回错误 5，作为不完整记录保留并排除，不将缺失分类填为零或宣称扫描成功。
