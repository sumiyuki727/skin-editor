# MP3 前缀定位的取消交接

日期：2026-10-20。默认关闭的 P0 音频实验续篇，不是正式播放后端，也不是 stable 音频兼容结论。前置记录见 [Ogg 尾部与定位](VORBIS_TAIL_AND_SEEK.md)。

## 问题与处理

此前 MP3 定位仍从头解码。代次检查保证旧 PCM 不会提交到输出，但 worker 在同步 `seek` 返回前不能响应新目标或关闭；“拒绝旧结果”没有解决“继续计算旧任务”。

本轮在媒体实验内部增加 `seek_step(frame)`：MP3 每步最多前进 4096 个逻辑 PCM 帧，返回是否到达目标；尚未到达时调用方可以继续、改目标或丢弃该流。同步 `seek` 仍由同一步骤循环完成；WAV 和 Vorbis 保留原定位通路。中间步不增加媒体定位代次，只有到达目标后增加一次；越界请求不变更状态，真实解码失败保持 poisoned，不能重试后伪装成功。

线程组装层在打开源之前、定位步骤之间及读取完成后检查输出请求是否仍为当前代次；过期流丢弃并归还 PCM 租约，下一次只为最新代次重开不可变源。关闭先关闭输入，再发出线程停止信号，避免主动取消被记成当前代次解码失败。检查与提交之间仍可能发生新请求，因此最终 `complete/fail` 的原有代次检查继续负责拒绝旧块。

新增的 `Input::is_current(generation)` 只读取队列状态，不接触文件或解码器。媒体库不接收取消闭包、时钟、线程、项目或设备；线程仍在组装层，设备包仍只接收值类型 PCM。没有新增依赖、锁文件、平台 API、unsafe、线程池或通用任务框架。正式项目的 Command 和模块接口没有变化。

## 回归证据

三个无窗口 worker 用例使用已有自制 0.37 秒 MP3，以每次最多 128 字节的只读源在偏移 6144 处暂停一次 I/O。确认旧目标尚未提交 PCM 后，分别发出多个替换目标、暂停及关闭，再释放这次读取。这里的门闩明确控制竞争发生的位置，不依赖等待某个毫秒数猜测解码进度。

旧实现三个用例均失败：释放 I/O 后仍为旧目标读取到 8192 字节以后。修复后要求首个旧源的最后读取位置不超过 8192，替换／暂停队列的首帧精确为最新请求的第 48 帧，逐声道样本及增益匹配线性参考；解码失败为 0，旧租约计为 stale，关闭后五块 PCM 全归还。6144／8192 是该 fixture 和短读取条件下的回归观察界限，不是任意 MP3 的通用读盘预算。

媒体层另测分步前进上界、完成后的准确样本、途中改目标、无效目标不变更状态，以及截断文件失败后继续保持 poisoned。输出队列另测代次替换、退休与关闭后的只读取消检查。原有线性解码、双向定位、EOF、WAV、Vorbis 与暂停输入用例继续运行。

本机无窗口 **229** 项通过：压缩 GUI 77、WASAPI 23、压缩媒体 22、预览契约 10、Python 97。新增七项为三项媒体分步行为、三项 worker 竞争、一项队列只读代次检查。三个 worker 竞争用例另在 20 个独立测试进程中各重复一次，共 **60** 次通过；它们仍是三项独立回归，不计作额外 60 项测试。默认 GUI 70、WAV GUI 74、默认媒体 12 是相应子集，相关 feature 的格式、Clippy、测试和 release 构建通过。

## 复现入口

```text
python tools/check_p0_compressed.py
python tools/check_p0_compressed.py --skip-checks --run-benchmark --run-native --repetitions 2 --fixture artifacts/p0/compressed-fixture-v2
```

首项只执行无窗口检查／构建，不打开设备；第二项明确打开 Windows 默认音频输出，并要求已有自制 fixture。工具准备见[首轮记录](COMPRESSED_AUDIO.md)。通用入口还包含旧短 Ogg 的单 FFmpeg 参考比较，其历史长度冲突与独立审计结论继续分开；本轮资源复测只取 180 秒三种格式。

离线探针在现有 schema v1 定位行上追加 `steps` 和 `max_step_ms`，不改变原字段语义；它们是实验诊断，不是产品控制协议。实际原生复测仍检查完整 PCM、位置、代次、增益和原生接受包；它验证播放回归，受控取消竞争由上述无设备测试验证，不混为同一证据。

## 固定源码的原生与资源复测

固定同一组 **119** 份源码／锁／fixture／工具，顺序运行两组 180 秒 WAV、MP3、Ogg，各六轮离线和六轮原生。只有四份 Rust 源文件变化（媒体读取器、离线探针、worker、队列），没有新增便携 fixture、Cargo 依赖或锁版本；每轮源码快照副本和二进制已核对。六份完整线性 PCM 哈希均与上一轮一致，离线定位样本也精确匹配线性结果。

MP3 按探针固定前后顺序，半程定位需要 **1055** 步，末尾前 9 帧需要 **2110** 步；半程总耗时 **93.88–94.18 ms**，近尾部 **186.18–189.29 ms**。两次长定位的最长单步约 **0.174–0.283 ms**。这些步骤间可检查取消，但总前缀成本仍在，单步观测包含本机读取和解码调度，不能当作取消的实时期限。

原生探针在约 91 秒播放后暂停，并立即请求后退到 0.5 秒。原路径此时可能还在为旧暂停位置预备数据；本轮两个轨迹均在新代次的首块提交前归还旧租约。对应比较：

| MP3 请求至数据预备好 | 前一轮两次 | 本轮两次 |
| --- | --- | --- |
| 定位到 90 秒 | 119.4–119.9 ms | 117.0–119.2 ms |
| 暂停后立即后退到 0.5 秒 | 97.9–98.7 ms | **22.0–43.6 ms** |

等待缩短与步骤间取消旧前缀工作的机制一致；这是同源文件的顺序观测，未隔离设备确认、系统调度和约 10 ms 轮询开销，不是声学延迟。旧轨迹在完成 4096 帧后记录 stale，本轮为零帧租约归还；零帧字段本身不代表没有做过解码，取消位置的受控证据仍来自源门闩回归。

六轮原生均连续消费至少 30 秒，**12320** 个接受包按源位置、全部声道、代次、增益及哈希核对；**24** 段暂停各至少 650 ms，冻结进度与输入隔离通过。欠载、解码失败、轨迹溢出均为 0，关闭后五块 PCM 全归还。

| 格式 | 原生历史工作集峰值 MiB | 原生历史私有提交峰值 MiB | 整轮观测 CPU 核秒 |
| --- | --- | --- | --- |
| WAV | 20.188–22.465 | 14.711–17.543 | 0.031–0.078 |
| MP3 | 22.895–23.223 | 18.254–18.676 | 0.188–0.219 |
| Ogg | 20.531–23.004 | 14.926–18.078 | 0.063–0.094 |

资源值包含设备、控制／定位、暂停与有界诊断；CPU 受 Windows 计数粒度影响，不是稳态播放 CPU。离线 MP3 历史私有提交约 **1.262–1.266 MiB**，未保留整段 PCM。这里没有 GUI／GPU、重采样或物理输入，不将三种格式峰值相加为产品预算，也不据两次运行宣称长期零泄漏。

测试日志、原始产物／源码／二进制哈希、逐轮资源与前后对照见 [windows-mp3-cancellation.json](windows-mp3-cancellation.json)。旧报告、参考和原始轨迹保留不变。该记录只关闭本轮可取消前缀工作与回归子项，P0 尚未退出。

## 适用范围与剩余工作

4096 帧是一次前缀推进量，不是实时期限；缓存补充可能解码多于本步消费量的压缩包。源工厂、`Read/Seek`、格式探测、单次包解码及 Vorbis 容器定位仍可能同步阻塞，不能通过设置取消标志打断任意正在执行的 I/O。回归中的门闩也必须先释放读取，才验证后续前缀工作停止；不据此宣称慢盘、网络源或设备关闭具有毫秒级保证。

MP3 的总定位工作仍随目标位置增长，没有接入粗定位、MP3 索引或 bit reservoir 预滚。Symphonia [SeekMode 文档](https://docs.rs/symphonia-core/0.6.1/symphonia_core/formats/enum.SeekMode.html)区分粗略与准确定位；本轮另外检查了本地锁定 0.6.1 的 `symphonia-bundle-mp3/src/demuxer.rs`，准确路径可能扫描前缀。不能只切换枚举就把样本准确性或取消成本视为已证明，也没有修改依赖源码。

重采样、真实音乐／标签／非零起点／链式流、压缩音频与图形组合长时、物理输入／声学延迟、设备变化及跨平台实测继续开放。Linux 按用户要求暂缓，macOS 待设备。该取消交接不需要新的 F12；没有读取旧 stable 源码、私人音乐或窗口画面，未提交或推送 Git。
