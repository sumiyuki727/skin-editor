# 有界按需 WAV 解码

日期：2026-10-19。独立 P0 解码实验已通过，不是正式播放器或 stable 内核。此前的[短文件到设备时间线](MEDIA_TIMELINE.md)保持原接口，本轮新增长文件的按需读取、固定容量缓存、定位和资源对照，没有把新路径接入 WASAPI、GUI 或游戏时间线。Linux 实测暂缓，macOS 待设备。

本批保留纯读取原型的历史范围；后续[后台解码与原生输出](STREAM_OUTPUT.md)另行接线和验收，不回写本批资源结果。

## 接口与范围

`p0-media::stream::Stream` 接收调用方提供的 `Read + Seek` 源，不打开文件、创建线程或访问项目。调用方每次提供一个可复用的 float32 块；没有消费请求就不继续读取／解码，不积累后台队列。`read` 返回代次、起始帧、有效帧数和 EOF；不足一块的 EOF 尾部清零，重复 EOF 不再解码。

成功定位先重置解码器并清掉旧缓存，下一块属于新代次。使用上游准确定位，再解码／丢弃到请求的精确帧，不能把容器返回的位置当作精确样本起点。无效请求不改变位置、代次或缓存；I/O／解码失败清空待交付输出，使该流失效并要求重开，不发布部分块。已交付块由调用方拥有，未来异步交接必须按代次丢弃旧块。

仅接受自制 fixture 使用的 **44 字节头、PCM16、无额外 chunk 的 RIFF/WAVE**。单／双声道、8–192 kHz、最长 600 秒且编码源不超过 128 MiB；两项上限同时生效，不保证所有格式都能达到最长时长。拒绝未知布局、格式和不一致的长度，不称为完整 WAV 导入器。兼容性规则未增加，当前 stable 实测案例仍为 0。

| 缓冲 | 上限与所有权 |
| --- | --- |
| 调用方输出 | 每次最多 4096 帧；双声道 float32 为 32 KiB，可复用 |
| 解码后缓存 | 固定 32 KiB，不随文件时长扩大 |
| 编码源缓冲 | 显式 64 KiB，内部允许有界预读；没有消费请求时不继续预读 |
| packet／解码器／分配器 | 独立成本；校验单包不超过 4096 帧，当前实际 1152 帧 |

前三项合计 128 KiB 只是显式缓冲，不是进程总内存承诺。输入源由调用方持有文件句柄，不能先把长文件读成 Vec 再排除其成本。未验证任意恶意输入的总 CPU／内存上界，也没有重采样、压缩格式或流式音频输出。

依赖与锁文件没有新增或升级：继续使用关闭默认功能的 Symphonia 0.6.1，只启用 WAV／PCM。准确定位／重置语义依据[公开的 0.6.1 FormatReader 接口](https://docs.rs/symphonia-core/0.6.1/symphonia_core/formats/trait.FormatReader.html)，实现独立编写。库继续禁止 unsafe；文件打开、计时和进程采样位于独立探针／tools，不进入库或项目模型。

## 复现与对照方法

```text
python tools/check_p0_streaming.py
python tools/check_p0_streaming.py --run-benchmark --repetitions 3
```

第一项检查媒体库及探针的格式、Clippy、12 项无窗口测试和 release 构建。第二项额外在 Windows 生成并读取自有 `stream-fixture-*` 中的 3 秒／180 秒、48 kHz 双声道 PCM16 文件，依次运行短文件按需、长文件按需、长文件保留 PCM 三种负载，各重复三轮。不会播放声音、打开 GPU 或捕获窗口，也不读客户端、私人音乐或旧源码。

保留 PCM 的对照使用**同一个按需解码器**，另将所有有效样本收集到预分配 Vec，以隔离整段样本常驻成本。它不是旧短文件 API 的大文件支持或正式播放策略，也没有计入编码文件常驻与 Arc 转换的额外复制。

标准库 WAV 读取独立计算全部 float32 字节的 FNV 哈希，并校验中段未对齐定位、向后定位、末尾九帧和精确 EOF 的哈希／代次／零尾部。读取耗时不含探针哈希和保留复制，完整循环耗时另列。探针与采样器显式握手，先取得十个基线采样，再开始解码；工作后持有状态 350 ms，核对读取计数、位置、解码统计均不变。

采样器仅查询自有进程，记录提交峰值、工作集、CPU 时间和原始采样。CPU 时间分辨率较粗，短负载的 0 读数不等于没有工作。未控制磁盘冷缓存，批量离线吞吐不代表音频回调 deadline 或播放欠载表现。

## 本机结果

最终冻结版本的九轮均通过，二进制、源码、锁及 fixture 身份一致。明细与哈希见 [windows-streaming-audio.json](windows-streaming-audio.json)。

| 负载，每项三轮 | 进程提交峰值 MiB | 相对基线增长 MiB | 峰值工作集 MiB |
| --- | --- | --- | --- |
| 3 秒按需 | 0.715–0.746 | 0.141 | 3.441–3.449 |
| 180 秒按需 | 0.840–0.844 | 0.234 | 3.523–3.527 |
| 180 秒保留 PCM | 66.898–66.914 | 66.289–66.305 | 69.453–69.480 |

长文件编码大小 34560044 字节，float32 总输出 69120000 字节；按需模式不保留这些总量。打开仅读取 **1068 字节**，完整顺序处理累计读取 **34560088 字节**（含头部重新读取），解码 **7500 包／8640000 帧**。全部 PCM 和定位的独立哈希通过。顺序完成后，350 ms 无请求期间没有额外读取、解码或位置变化。

180 秒按需的读取 p95 为 **27.1–28.5 µs／最多 4096 帧**，单次最大 **70.5–98.0 µs**；含探针完整哈希的循环为 **110.98–113.63 ms**。这些数值仅覆盖本机自制文件的离线读取。“时长增长提交不超过 16 MiB”和“保留样本成本可见”只是诊断门槛，均通过，不替代产品总资源预算。

首轮 `stream-3bd5ab9f` 因计数器初始化错过固定时窗、缺少基线而被外层拒绝；保留原结果，不纳入通过样本。先加入复现测试，再改为握手采样。首批有效比较也保留原身份；补充时长上限测试和递归库边界检查后，最终九轮重新执行并单独登记，不混作同一源码版本。

当前 Windows 无窗口检查合计 **168** 项：GUI 默认 70、可选文件读取 1、媒体 12、输出适配器 11、契约 10、Python 64。新增测试覆盖分块／声道／EOF、未对齐定位、代次、无效请求不变性、背压、源故障、格式／长度／时长限制；工具覆盖独立参考、错误证据、采样基线及资源对照拒绝。可选 GUI 媒体构建也单独检查，未重复无关 GPU 预算或打开音频设备。

## 剩余工作

压缩格式、重采样、解码 worker 与有界交接到原生输出仍开放。按需文件读取会阻塞调用线程，不能直接放进音频实时回调；下一步在明确的后台所有者中准备块，再验证原生输出的欠载、暂停／定位时旧块丢弃和连续播放。组合资源预算、物理输入时序、玩法与后端路线尚未关闭，P0 未结束。
