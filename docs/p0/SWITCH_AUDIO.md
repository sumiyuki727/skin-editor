# 共享音频时钟与后台文档切换

2026-10-19，Windows x64 原生实验完成三轮“真实静音输出 → 共享模拟／输入门控 → 后台文档交接 → GPU 编辑”的组合验证。结果与冻结证据身份见 [windows-switch-audio.json](windows-switch-audio.json)。它推进了 P0 联动风险验证，没有实现 stable 玩法或正式项目核心。

## 所有权与数据流

一个应用级 `Transport` 消费独立 WASAPI worker 的只读快照；十个文档的 `GestureView` 各自保留编辑会话／快照，只在绘制时借用同一个 Transport。切换活动文档不新建模拟时钟、不重新打开音频流、不清除 held 按键，也不增加编辑历史节点。

```text
默认静音输出 → 设备确认／位置 → 单一 Transport → 模拟、动画标记与游戏输入门控
                                      ↑ 活动文档 UI 仅借用
文档请求 → 后台原图／组树 → 候选 GPU 上传／合成／回执 → 替换活动视图
编辑操作 → 对应文档的命令会话 → 草稿／提交投影 → 同一 GPU 合成器
```

活动文档有变化时取消旧文档未提交的手势；已提交快照保持不变。暂停、音频控制和文档请求各有自己的序号与寿命，不能混用。加载失败和逻辑取消只影响派生文档请求，音频状态不随之变化；GPU 过期结果仍按原来的有界策略排空。关闭活动文档也不重置共享流位置。

旧的单文档音频实验仍可使用视图内部的实验 Transport。公共绘制内核现在也接受外部借用，禁止同一视图同时拥有和借用两套 Transport。新入口的设备与时钟由桌面组装代码持有，没有把设备对象、项目指针或 UI 控件放入 Command。

文档仍是只读 fixture 下的 0–9 索引和独立手势拥有者，不是正式 SkinProject、ElementDocument 或历史节点 ID schema。模型／模块设计见 [ARCHITECTURE.md](../ARCHITECTURE.md)，本实验不替代 P1。

## 场景与实测结果

每轮新建输出流和原生进程，使用经过哈希校验的既有标准 fixture。音频为默认 shared endpoint，48 kHz／双声道／32 bit、4800 帧缓冲，时钟频率 384000 单位／秒；流样本始终为静音。设备开流／COM 接口仍留在已有可选 Windows 适配器中。

1. 后台加载文档 0，同时启动播放，接纳一次 Z 按下；等待约 450 ms 后请求并确认暂停。
2. 在暂停中拖动文档 0，再切换文档：取消草稿且不提交；文档 1 已进入 GPU 准备后改请求 2，确认 1 不发布。
3. 在文档 2 上通过同一 egui 输入路径做 30 次草稿更新并提交一次。请求缺失 fixture，保留文档 2；再请求并取消文档 4，排空旧任务。
4. 恢复播放，旧 held／repeat 不重放，释放再新按下才接纳第二次 Z。播放中切换到文档 5，记录至少一个对应新文档的设备播放样本后再暂停。
5. 文档 6 已进入 GPU 准备时关闭活动视图，排空候选，确认不会重新出现活动文档，音频继续保持第二次暂停的位置。

所有新鲜样本的模拟位置都等于对应设备位置，跨文档单调不倒退。两次暂停均有至少三个新鲜读数且位置保持；暂停中按键不进入游戏输入。最终文档节点数依次为 `[1,1,2,1,1,1,1,1,1,1]`，只有文档 2 的有效提交增加了一个节点。

六个关键状态各做 1024² CPU／GPU 输出及 GPU 显示适配对照，容差 2／255，无超差像素。文档 0 的基线／取消后、文档 2 的提交／加载失败后，各自的三种 PNG 逐字节相同；文档 2 提交前后像素有变化。每轮五个 GPU 候选各写入 40 MiB 原图，仍是每候选五帧、每帧最多两张／8 MiB。播放期间不运行阻塞 CPU 像素参考。

三个最终目录为 `switch-audio-f8e78ae2`、`switch-audio-3e8b2308`、`switch-audio-81a602d4`，在 `artifacts/p0` 下。它们使用同一 exe／源码／输入身份；此前 `switch-audio-e4443e78` 是预备运行。正式脚本补上“等到新文档实际播放样本后再暂停”的时序门槛，避免慢加载时只记录旧文档的最后一条播放样本。

## Pipeline 预热与资源边界

新组合入口使用[后台 pipeline 预热候选](ASYNC_COMPOSITION.md#加载长帧归因与可选后台预热)，GPU 程序每个预览会话创建一次并共享，不按文档重新创建。这里设备 worker、原图 worker 与一次性 pipeline worker 各自独立；短暂增加一个预热线程，不增加第三方依赖或 unsafe。

本轮预热的 worker 墙钟约 61–78 ms，仍需支付 CPU／驱动成本。六个像素参考共阻塞 UI 约十秒，只在真实暂停下进行；上表暂停墙钟包括这些检查，不是编辑延迟。进程采样保存为诊断，不作为声学延迟、待机 CPU 或完整应用预算。原图、候选、暂存与驱动的边界继续按 [ASYNC_COMPOSITION.md](ASYNC_COMPOSITION.md)计量。

## 复核与限制

```text
python tools/check_p0_switch_audio.py --fixture artifacts/p0/gpu-fixture --repetitions 3
```

入口仅 Windows，显式打开默认静音输出和自有 Vulkan 窗口；默认 feature 关闭。先检查／构建再顺序运行，拒绝目录越界及覆盖已有证据，保留源码／锁文件／脚本快照与 PNG 哈希。无窗口测试不会打开设备。

新增无窗口测试验证多个文档借用同一 Transport 时保留时钟、请求号、held 输入与 Faulted 状态，取消编辑不影响时钟／其他文档；pipeline worker 的失败与退出；Python 拒绝错误时钟、错误文档／像素／输入、超限上传和含糊帧关联。原生 57、契约 10、Python 43 和可选适配器 1 项测试通过，格式、Clippy、默认／feature 构建分别验证。

使用合成 egui 键盘／指针事件，未验收物理输入、IME、全屏、扬声器可听输出、低延迟或默认端点是否为物理设备。失败场景是缺失 fixture，不是拔出／切换真实音频设备；故障重建和异步 I/O 退出上界仍待验证。没有 stable 规则、谱面、判定或当前客户端兼容案例。Linux 未实测、macOS 延后；本轮不需要 F12，未访问旧源码或客户端资源，未提交或推送 Git。
