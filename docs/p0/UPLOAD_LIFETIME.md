# 完整加载流程的资源寿命与有界上传

2026-10-19。延续[分配与重复验证](ALLOCATION_ATTRIBUTION.md)。本轮收尾目标是将回执、纹理释放与进程提交放到同一时间轴，并对一项有界上传方案作出取舍；驱动内部的未归因部分保留为已知限制。

本轮结论：**保留现有默认加载路径，有界上传仅保留为显式实验选项**。身份、原始结果位置、释放检查点及逐项预算见 [windows-upload-lifetime.json](windows-upload-lifetime.json)。

## 方法与边界

使用同一只读标准 PNG fixture、80 MiB 复用纹理池、128 MiB CPU 缓存、两项预取和每帧两项／8 MiB 限额。基线继续使用原有异步加载；候选额外要求上一帧上传的 queue completion 回执到达后，再排队下一帧的素材更新。它不阻塞 UI，不主动等待 GPU，也不重建 GPU 设备或清空系统工作集。

回执在上一帧已提交后注册，由非阻塞 device poll 推进。单帧内的两次图片更新共用一个 ticket；文档取消和旧代次失效不清除物理工作回执。回执的 payload 上限与驱动内部的保留页、原图纹理池和全部 GPU 内存是不同计量。

常规性能组无页面扫描、无 PNG 回读和逐项日志。时间线诊断另行运行，记录上传排队／回执、逻辑绑定重置、纹理清除、allocator 快照与父进程 100 ms 样本；关闭后额外按 100 ms 请求诊断刷新，观察到十秒以上。这会增加 CPU 与绘制，诊断的关闭空闲检查保持 false，不拿它替代正常空闲预算。

回调时间包含帧提交、GPU 工作和主机 poll 调度，不等于 GPU 执行耗时。释放检查点取目标时刻之后、最多迟 250 ms 的真实样本，并保留实际偏移；没有合适样本就记录未知，不使用释放前的旧值或插值补造数据。

## 已对齐的延迟回收

在首批同构建诊断中，清除纹理后原图像素引用和自有纹理均释放，GPU 计量先进入平台，但进程提交仍有一次明显的延迟下降：

| 诊断组 | 相对清除事件的相邻采样区间 | 私有提交变化 | 同期 GPU Dedicated |
| --- | --- | --- | --- |
| 原有加载，观察回执 | 3.072–3.181 s | 222.680 → 109.703 MiB | 41.961 MiB，不变 |
| 有界上传，首版回调 | 2.889–2.982 s | 221.230 → 100.238 MiB | 33.941 MiB，不变 |

这与独立 Vulkan 实验中“显存计数下降后，PRIVATE 页稍后回收”的现象一致，说明 GPU 完成、逻辑资源释放和进程提交回收需要分开观察。没有直接调用栈和区域逐一配对，仍不能断言整段差额由同一驱动机制产生，或排除堆保留等其他来源。

首批时间线的未回执 payload 峰值从 16 MiB 降到 8 MiB，两组结束时均为零。它是排队像素的记录值，不能直接当作同时存活的原生 staging 分配。对应完整性能组的 GPU Dedicated 峰值从约 162.035 降到 154.035 MiB，原图池容量与绘制内容保持相同。

## 回调刷新修正

首版候选的回调直接请求刷新。两次完整运行的循环样本 CPU 时间为 23.766–26.141 s，高于本批基线的 18.188–19.375 s；私有提交采样峰值分别为候选 596.516–609.832 MiB、基线 617.707–618.609 MiB。该实现的代价不支持作为默认路径。

之后将回调统一接入现有的 60 Hz 合并通知函数，保留相同的有界策略，在新的固定二进制中重新对照。首批成绩与源码快照保留，不与修正后的结果混作同一构建。已有的完成通知测试约束合并行为，新增两项纯状态测试覆盖 ticket、实际完成前的阻塞、重复回执、乱序回执和取消后物理工作仍存活。

修正后的一对完整进程得到以下结果；每组仍含 300 次脚本编辑、200 文档加载、60 秒暂停和关闭后 60 秒观察，无回读或页面扫描：

| 指标 | 原有加载 | 合并通知后的有界上传 |
| --- | ---: | ---: |
| 私有提交采样峰值 | 449.746 MiB | 611.789 MiB |
| OS 累计提交峰值，截至最后采样 | 449.805 MiB | 611.871 MiB |
| 工作集采样峰值 | 248.363 MiB | 248.160 MiB |
| GPU Dedicated 采样峰值 | 162.039 MiB | 154.035 MiB |
| 200 文档加载 p95 | 93.851 ms | 95.017 ms |
| 循环样本 CPU 时间 | 20.031 s | 25.000 s |
| 循环墙钟 | 28.559 s | 28.921 s |
| 加载 CPU 帧 p95 | 12.923 ms | 13.144 ms |

合并通知修正了刷新方式，但该次候选仍多用约 4.97 s 循环 CPU 时间，没有获得进程提交净收益。回执、非阻塞轮询和调度的单独成本未进一步拆分，不把增加量全部归给一个 API。两个构建的原图池均为 80 MiB，创建／更新数均为 20／2010，输入文件哈希保持一致。

本批新基线峰值也明显低于先前独立进程，进一步说明提交峰值受原生分配／回收状态影响。单对数据不足以估计稳定均值或宣称候选必然增加固定大小的内存；但当前证据没有可重复的净收益，且出现 CPU 代价，足以决定不采纳为默认。六组完整运行的可测预算均通过，最长加载帧仍可能超过 16.7 ms，不能因此宣布整体产品预算已完成。

修正版时间线仍保持 8 MiB 未回执上限且结束为零，排队到回调的观察 p95 约 21.05 ms。这是包含主机调度的回执墙钟，不是 GPU 时间戳。其额外关闭刷新仍是诊断行为。

## 图像与维护边界

首批基线／候选的 12 张画布 PNG 字节完全一致，覆盖全部十个文档、重置后的再次访问和第 200 次切换。冻结时素材更新检查也通过；这些是另行运行的短观察回读，不混入常规加载性能，也不声称重新完成了 300 次编辑回读。

修正版候选再次比较相同 12 张画布，仍与首批基线字节完全一致，冻结更新检查通过。70 项无窗口行为测试通过：10 个契约、20 个原生加载／纹理／回执、9 个合成及 31 个 Python 工具测试；新增工具用例约束时间对齐、缺失样本、回执配对及 CPU 合成的常见反向／平台引用。格式、Clippy、release 测试／构建与输出保护通过。

新结果为 standard-load schema v6，旧记录不改写。新增字段区分是否启用回执、有界策略、未完成 payload 峰值／末值与等待帧数；未观察的基线字段为 null。它们不是项目文件或 AI 编辑接口，不影响 Command、历史资源引用或原始素材。

该实验不包含真实图层合成的新语义；其窗口仍使用原有的只读负载绘制。新的 CPU／GPU 合成验证在[独立记录](COMPOSITION.md)中，避免在同一性能比较中同时改变图片合成与资源调度。

本轮到此收尾，后续重心转向合成规模与真实编辑交互。直接虚拟分配调用栈、驱动／覆盖层内部来源和跨机器波动仍未解决，在出现具体预算阻塞或取得新的测量条件时再重开，不据当前结果选择最终技术栈。

## 复核入口

```text
python tools/check_p0_lifetime.py --fixture artifacts/p0/gpu-fixture
```

fixture 须先用现有 `p0_workload.py` 创建。入口检查并固定二进制和已参与构建的源码，先执行短流程，再以相反顺序运行基线／候选各两次完整观察，最后单独做时间线和画布验证。只使用自建进程与自有回读；未访问当前 stable、旧源码、系统窗口捕获或系统图形设置。
